# 第 9 章 harness
智能体持续执行任务的时候，模型不断输出动作指令，工具返回观测结果，文件，外部业务状态也会随之变化。在两次模型调用之间，必须由一套程序持久记录这些变化，判断任务该继续执行，等待外部反馈还是直接终止；遇到网络中断，进程崩溃，还要能够恢复任务。这套包裹在模型外围，负责承载全部运行逻辑的支撑系统，就叫做 agent harness。

最早的实现只是一层简单循环，串联模型与工具。随着任务变长，这个循环会逐步叠加状态管理，上下文组装，任务调度，权限校验，资源预算，结果验证等模块。harness 决定模型每一轮能读到哪些信息，也决定模型的输出会怎样作用于外部环境。哪怕使用同一个模型，只要搭配不同的上下文策略，工具集，故障恢复逻辑，最终任务表现也会明显不同。运行层的核心职责，就是把每一次模型决策和已经发生的历史动作串联起来，保证模型在下一轮拿到准确，完整的任务状态。

## 9.1 任务状态
对话消息只能记录交互文本，不足以完整描述正在推进的任务。工具可能已经发起调用但还没有返回结果，文件已经生成但模型还没有重新读取，用户也可能中途修改原始需求。运行系统需要额外保存这些确定的事实。

一份基础任务记录可以写成下面的结构：
```json
{
"task_id": "task-042",
"status": "running",
"revision": 8,
"goal_ref": "requirements-v3",
"message_cursor": 27,
"pending_calls": ["call-17"],
"artifact_refs": ["report-v2"],
"remaining_model_calls": 12
}
```
task_id 唯一标识整条任务，revision 代表任务记录的版本号，message_cursor 标记已经生效的消息和事件位置。pending_calls 存放尚未完成的工具请求，产物引用指向任务生成的文件或者业务对象。模型可以读取其中和决策相关的字段，调度器则使用完整记录管控执行流程。

任务状态可以划分为 ready，running，waiting，completed，failed，cancelled。waiting 细分两种场景：等待工具返回，或是等待用户补充输入，二者的恢复条件完全不一样。completed 代表交付标准已经达成；failed 代表当前路径已经无法继续推进。清晰的状态区分，才能让前端界面，上层调度器正确解释任务结果。

除了瞬时状态，系统还可以追加式记录事件流。事件包含模型请求，模型输出，工具准备，工具返回，产物创建，用户修改需求，附带时间戳，调用标识和结果引用。当前任务状态，全部由这些事件逐步推演得到，既方便故障恢复，也方便事后排查问题。

事件落地时要做去重。服务重复推送完成通知，网络重连后重复投递旧消息，都是常见情况。给事件分配稳定唯一ID，状态记录保存已经处理完成的事件标记，就不会把同一份工具结果重复应用多次。多进程同时更新任务时，还需要版本校验或者锁机制，防止状态互相覆盖。

产物尽量绑定版本或者内容哈希。如果只保存文件路径，文件后续被修改之后，旧事件里的引用就会指向新内容，无法还原当时的执行结果。不可变快照或者内容摘要，可以保证核查，交接的时候，对应到确定版本。对于需要反复修改的工作文件，单独维护当前工作副本和已经提交版本之间的映射关系。

## 9.2 决策循环
harness 的每一轮循环，先处理已经抵达的事件，再判断是否满足继续调用模型的条件。如果关键工具还在运行，可以进入等待；如果存在互不依赖的独立子任务，也可以并行推进。之后组装本轮上下文，调用模型，解析模型输出是工具调用，向用户提问，还是最终交付答案。

核心流程可以用伪代码表达：
```python
def run_task(task):
    while not task.is_terminal():
        apply_ready_events(task)
        enforce_budget(task)
        if task.is_terminal():
            break

        if task.requires_external_event():
            persist_wait_state(task)
            return

        context = build_context(task)
        decision = model_call(context, task.generation_limit())
        persist_decision(task, decision)

        if decision.kind == "tool_calls":
            for call in decision.calls:
                prepared = validate_and_prepare(task, call)
                persist_prepared_call(task, prepared)
                dispatch_or_recover(prepared)

        elif decision.kind == "need_input":
            persist_question(task, decision.question)
            task.wait_for_input()

        elif decision.kind == "final":
            check = verify_artifacts(task, decision)
            if check.accepted:
                task.complete(check)
            else:
                add_verification_feedback(task, check)

        persist_task(task)
```
这段伪代码只表达职责划分，线上服务还需要额外处理中断，流式输出，异常捕获。预算检查放在循环的入口，就算验证失败，也不能无限制反复重试；系统可以根据剩余预算继续修正，或是直接保存终止原因。

模型输出本身需要解析。正常结束，触发输出上限，网络连接中断，对应不同的完整性。不完整的参数片段可以保留用于诊断，但是不能直接提交执行。结构化输出接口能够降低解析失败概率，但依然要校验参数语义，任务约束。

结果验证优先依靠客观产物事实。生成报告可以检查文件是否存在，必填章节和引用字段是否齐全；代码任务校验变更范围，执行测试用例；外部业务操作主动查询远端对象状态。开放式主观质量可以交给模型或者人工评价，但“文件是否存在”和“内容质量好坏”，要分开校验。

用户新消息同样进入事件流。新消息可以补充条件，修改目标，取消任务。运行程序先记录事件，更新版本，再在合适的循环边界交给模型读取。已经执行完成的外部操作不会自动回滚，后续决策必须同时兼顾新目标和已经形成的真实状态。

## 9.3 上下文管理
任务日志会持续变长，每一轮送入模型的输入，只保留当前决策必需的内容。稳定指令，工具描述，目标约束，任务进度，近期交互记录，关键证据优先级更高。早期原始材料只保留引用，需要的时候再按需读取。

输入预算可以写成：
\[
C
=
C_{\mathrm{rules}}
+C_{\mathrm{tools}}
+C_{\mathrm{state}}
+C_{\mathrm{recent}}
+C_{\mathrm{evidence}}
+C_{\mathrm{output}}
\]
所有分项加起来，不能超过模型上下文窗口上限。同时必须预留输出token空间，不然读入大量材料之后，模型没有余量生成动作。工具目录，超长工具返回很容易挤占窗口，按需加载工具描述，对返回结果做摘要，直接决定任务可以持续多少轮。

压缩上下文不能简单按时间丢弃旧记录。用户一开始给出的全局约束，全程都不能丢失；刚刚返回的一大段无关日志，却可以立刻精简。取舍标准，是当前决策是否依赖这条信息，证据是否有效。如果模型反复读取同一批材料，往往说明任务状态层没有缓存已经得到的结论。

接近窗口上限时，可以生成交接摘要。摘要里面写清楚目标，约束，已经验证的进度，关键证据，现有产物，未解决问题和下一步计划。固定字段由程序填充，模型负责梳理逻辑关系。后续恢复任务时，先读取摘要，再核验文件和状态，继续推进。

交接摘要本身允许出错，摘要里的结论最好绑定原始证据，区分哪些是确定事实，哪些只是临时推测。一旦摘要写错，比如把“计划运行测试”写成“测试已经通过”，后续所有决策都会建立在错误前提之上。原始事件，产物版本，就是用来修正这类摘要错误的依据。

Anthropic 长任务 harness 的实践思路，就是把初始化和后续执行拆开：先搭建环境，加载能力清单，后续会话一步步推进，持续留下进度记录和可核验产物。上下文切换之后，连续性不靠单条聊天窗口承载，而是由外部状态，摘要，工作文件，验证记录共同支撑。

前缀缓存可以减少固定内容的重复计算，属于性能优化手段。模型版本，token序列，配置改动，或是服务重启，都会造成缓存失效。所以任务的可靠恢复，不能依赖缓存，必须依靠持久化记录，并且按用户，权限隔离可共享内容。

## 9.4 调度与并发
模型一轮可以同时输出多个工具调用。这些调用读取独立对象，就可以并行发起；如果后面的调用依赖前面的返回结果，就必须等待。调用依赖关系可以抽象成一张图，调度器只启动前置条件全部就绪的节点，同时根据工具配额，系统资源上限控制并发规模。

并行只能减少独立任务的等待时长，总的计算开销并不会减少。多个请求共享同一个后端限额，并发发起容易触发限流；多个写入操作修改同一份资源，还会产生冲突。依赖关系除了数据依赖，还包含共享资源，对象版本，副作用约束。

工具结果通过 call_id 和原始请求一一绑定。结果返回之后，可以立刻触发新一轮模型决策，也可以等待一批关联调用全部收齐再继续。前者响应更快，后者减少模型反复读取残缺结果的次数，策略取决于后续任务能不能利用部分返回。

后台耗时任务返回持久句柄 job_id，调度器定时轮询进度，记录截止时间，保存取消入口。模型可以先去处理别的工作，等任务完成之后，以事件的形式唤醒决策循环。服务重启之后，依靠句柄查询远端真实状态，而不是盲目重新发起任务。

如果调用依赖可以显式表达成图，运行程序就可以主动调度，减少模型逐次选择工具的负担。LLMCompiler 把这部分拆成规划，分派，执行：规划器输出调用和依赖，分派器等待输入就绪，再派发可运行任务。模型只负责制定计划，处理异常结果，固定的依赖流转交给程序。

举个例子，三个独立查询可以同时发起，某一项分析只依赖其中两个查询结果，那两个结果返回之后就可以启动分析，不用等待第三个查询。汇总节点如果依赖全部三个结果，则继续等待。调度器维护 pending，running，completed 三类状态，每一条结果抵达，只检查受它影响的下游节点。

规划器也可以流式输出任务，分派器拿到合法节点就开始准备执行。计划生成和工具运行可以重叠；但是参数不全，依赖缺失的节点，依旧需要等待。遇到空结果，调用报错，调度器先保存异常，不阻塞互不相关的分支，受影响的分支再交给模型重新规划。

错误按类型差异化处理。临时网络故障交给程序自动重试；参数错误需要模型修正指令；权限拒绝直接终止对应动作；环境缺失则调整任务方案。重试策略要设置次数，间隔，总超时，避免大量失败请求同时密集重试。

异步任务还会遇到过期结果。用户中途修改目标之后，旧查询依然可能返回数据；结果可以存入事件日志，但是能不能用于当前版本的任务，需要重新判断。调度器给每一次调用绑定任务版本，输入摘要，用来识别这条结果对应的是哪一版需求。

## 9.5 中断与恢复
最难处理的恢复场景，发生在外部服务和本地记录不同步的时候。远端已经写入数据，但是 harness 还没有保存结果就崩溃。恢复之后，系统只知道请求发出去了，无法确认是否执行成功，直接重发会带来重复副作用。

行业通用方案：发送请求之前，先持久化准备记录，保存稳定操作ID，参数摘要，前置条件；发送完成之后，再保存执行结果。恢复的时候，优先查询外部对象状态，或是使用同一个幂等键尝试查询。能不能可靠恢复，取决于下游服务是否支持状态查询，幂等去重。

本地事务无法把任意外部服务纳入原子提交。对于不支持幂等，状态查询的接口，系统只能标记状态为“结果未知”，再通过其他证据交叉核验。这个不确定状态，比直接判定成功或者失败更贴合事实，方便后续人工介入。

文件类任务可以依靠版本控制，快照，原子替换搭建恢复边界。邮件，支付，发布这类外部操作，撤销逻辑各不相同，需要单独设计补偿流程。补偿动作本身也可能失败，同样要记录状态，不能把“发起取消”等同于“已经撤销”。

暂停，取消，进程崩溃，语义互不相同。暂停只是停止后续调度，保留恢复点；取消还要清理后台子任务，待提交操作；进程崩溃则需要重启之后重建状态。能不能中断正在执行的动作，取决于工具本身能力。前端界面也要区分等待中，正在取消，已停止。

权限，预览结果和操作绑定。预览完成之后，如果对象版本，参数，授权范围发生变化，旧的提交条件就已经失效。提交之前再次校验标识和范围，避免把旧预览，旧授权用于新操作。已经明确授权的范围可以持续生效，不需要每一轮重复询问用户。

以支持幂等的外部写入为例，可以分成五个恢复边界：准备记录尚未持久化，请求不会发出；准备记录已保存但还没发送，可以沿用原操作ID继续；请求发出，结果未知，优先查询状态或者用同一幂等键重试；结果已经保存，任务状态没更新，重新应用结果事件；任务状态更新完成之后，重复通知直接去重。每一个边界对应一套动作，恢复逻辑不需要依赖模型猜测当时发生了什么。

如果提交前需要版本校验，预期版本随操作一起保存。服务返回版本冲突时，任务进入重读，重新准备的阶段，模型基于最新状态判断变更是否还有意义。新参数生成新操作，旧记录完整留存，既能解释失败原因，也支持修正迭代。

故障路径适合在开发阶段主动注入测试。在发送前，服务处理完成后，结果保存前后主动终止进程，再恢复任务，检查外部对象有没有重复修改，任务状态会不会错误结束。正常流程跑通之后，这些故障用例，才决定这套系统能不能扛住长任务里的真实崩溃。

## 9.6 预算与观测
从任务启动到结束，完整记录耗时，单独统计模型请求，工具执行，网络排队时长。多个调用并行时，执行区间会重叠，分项耗时相加，会大于用户实际等待时长。费用统计累计输入输出token，工具调用，后台计算资源，同时设置总超时，模型调用次数，重试上限，约束整条任务的资源消耗。

单条任务的资源开销可以写成：
\[
C_{\mathrm{task}}
=
\sum_j
\left(
C_{\mathrm{input},j}
+C_{\mathrm{output},j}
+C_{\mathrm{tool},j}
+C_{\mathrm{other},j}
\right)
\]
额外记录缓存命中，等待时长，执行时长。价格会随服务商变动，原始token数量，设备运行时长，工具调用次数，才适合跨版本对比性能。预算临近上限时，收缩探索范围，优先完成核心依赖，非关键核验项可以标记延后。

轨迹日志要能回答三个核心问题：模型每一轮读到了什么，做出了什么决策，环境真实发生了哪些变化。模型输入版本，工具参数，错误类型，产物版本，验证结果，共同构成排查依据。敏感内容按访问权限隔离，展示层只返回摘要和引用。

很多低效问题都可以从轨迹定位。反复搜索，往往是状态层遗忘了信息；反复读取长文件，是缺少合适的检索接口；修改之后不验证，是验收规则缺失。针对这些底层组件优化，远比在提示词里增加约束更加有效。

harness 自身也需要测试。可以模拟重复通知，调用超时，进程重启，用户中途改需求，验证状态一致性。模型评测要在可重置的环境里运行，使用独立检查器评判结果。模型，工具，运行框架的版本全部固定，才能判断性能变化来自哪里。

长期运行的任务，从轨迹定位失败点之后，定向调整组件：反复查询就检查状态写入逻辑；交接摘要丢失约束，就优化摘要生成规则；恢复之后重复写入，就完善幂等和状态查询。每次改动瞄准一个可观测问题，再复用同一批任务验证，harness 就可以持续迭代变可靠。

## 9.7 DeepSeek Harness
我们可以借助 DeepSeek 公开的 DeepSeek Harness，直观理解整套设计如何落地成可运行系统。这个项目以 dsh 作为命令入口，使用 Cordis 管理插件，把模型接入，工具，会话，持久化，界面解耦组装。阅读源码的时候，可以顺着一次请求走完控制流程，分清哪些逻辑由插件实现。

启动阶段，程序根据 profile 加载配置。公开实现包含 web，headless，sdk 等运行模式，底层共用 dsh-base 的基础组件，再叠加界面或者调用入口。下面这条命令可以查看 web 模式装配的插件清单，确认模型适配器，工具，持久化模块是否启用：
```sh
dsh --profile web --dump-config
```
profile 决定本次启动启用哪些组件，插件负责把能力注册到运行环境。文件工具注册读取，编辑能力；模型适配器把内部请求转发给模型服务；持久化插件负责会话落盘。主循环依赖这些服务运行，想要更换存储后端，新增工具，只需要调整插件组合。核心组件职责如下：

| 组件 | 负责的工作 |
|---|---|
| core/session | 追加事件流，从事件生成模型可读消息历史 |
| core/system-prompt | 汇总全局指令，当前状态，工具描述 |
| core/agent-loop | 接收输入，组装模型请求，判断是否继续循环 |
| llm | 统一请求，流式返回类型，由适配器对接模型后端 |
| core/tools | 管理工具定义，调度执行，记录调用与返回 |
| session-persistence | 持久化事件，提供读取，恢复接口 |

所有组件共享同一份 Session。用户输入，模型输出，工具调用，工具返回全部追加成事件，每一轮模型输入，都从事件流动态生成消息。系统同时保留完整执行记录和精简上下文，前端界面可以回放进度，重新打开会话时继续任务。

以一次文件修改任务举例：用户要求检查导出逻辑对空数据的处理，修改代码，运行测试。输入进入任务队列，循环启动时创建 turn；一个 turn 里面，每一次模型调用+配套工具执行，称为一个 step。一条用户任务会包含多个 step，工具返回之后，循环判断是否继续请求模型。

第一个 step，system-prompt 组装指令和工具列表，session 生成历史消息，交给模型适配器。模型可能先调用 read 读取源码，read 支持指定路径，偏移量，读取长度，返回带行号的文本。模型拿到结果之后，循环把工具结果追加进事件，下一轮决策就可以读取这份代码。

事件依靠 callId 绑定请求和返回。一轮并行发起多个工具调用，返回结果也能一一对应，不会混淆。默认循环收集模型输出里全部工具调用，批量交给执行器，等待这批调用全部返回之后，再进入下一轮模型推理。普通工具返回之后，模型继续解释结果；如果工具返回结束标记，循环终止当前 turn。

执行器会区分调用是否可以并行。文件 read 标记为可并发，write，edit 属于独占操作。同一步里面多个独立读取可以重叠执行，写入操作串行执行，保证状态稳定。执行完成之后，结果按照模型调用顺序回填。

模型读完源码之后，可以用 edit 做文本替换，或者用补丁工具批量修改多处。文件操作由工具和文件系统服务共同执行，返回变更结果。模型再调用 shell 跑项目检查，读取退出码和日志，判断修改是否达标。测试失败，就基于报错继续修改，不需要依靠记忆推断测试结果。

任务中途用户补充需求，运行循环通过 inbox 接收新消息，区分当前 step 内的即时消息和排队的新 turn。新需求和已经完成的工具结果，共同进入后续上下文。

长任务会遇到上下文膨胀。DeepSeek Harness 把压缩逻辑放在 compaction 组件，根据 token 用量判断是否接近窗口上限。压缩优先精简超长工具返回，再选择合适历史生成摘要；同时保证工具调用和结果配对，后续依然能看懂观测来自哪一次动作。压缩本身也写入事件，记录摘要起止范围。旧事件完整保留，新轮次使用精简历史；需要核验的时候，重读原始记录或者重新读取文件。

事件及时写入存储。公开版本提供 JSONL 持久化后端，session-checkpoint-policy 控制刷盘时机。Session 先追加事件，存储服务接收写入，检查点策略等待落地确认。检查点放在三个关键位置：模型请求发起前，破坏性工具执行前，工具结果进入上下文之前。准备写入文件之前先保存调用记录，写入确认失败就停止推进，保证恢复的时候至少知道准备执行什么动作。

进程在工具执行阶段崩溃，恢复逻辑读取事件，补齐未结束的 step 和 turn。已经记录发起，没有结果的调用标记为 TOOL_OUTCOME_UNKNOWN；还没有发起的请求标记为待执行。模型看到这个状态，再决定重新查询，核对文件，或是重试。

如果 edit 已经修改文件，但是结果还没保存服务就宕机，恢复之后需要重新读取文件真实状态，再判断后续动作。这套逻辑同样适用于外部业务接口：有没有写入成功，不能靠本地记录猜测，必须查询远端状态或者依靠幂等校验。

插件化设计带来很强的可替换性。同一套循环，可以更换模型适配器；模型不变，也可以替换压缩策略，持久化方案，方便对照实验。扩展插件可以在调用前组装上下文，调用后采集指标，在指定生命周期注册逻辑，卸载时清理回调，避免旧逻辑干扰后续任务。

在这个案例里，模型负责根据观测挑选下一步动作；harness 负责组装输入，调度工具，持久事件，故障恢复。排查任务失败的时候，回到事件流，就可以分清问题根源：是模型决策出错，还是工具执行异常，或是运行层没有把状态正确交给模型。

## 9.8 harness 的演进

harness 这个概念不是凭空诞生的，它是从简单的调用脚本，一步步演化成独立的工程体系，术语“harness engineering”在2025年底到2026年才正式普及开来。

**早期（2022–2023，附加式循环阶段）**
最早没有 harness 的叫法，只是一层薄薄的胶水脚本。ReAct，AutoGPT，BabyAGI 这类项目，只是实现了“思考→动作→观察”的简单循环，本质就是提示词+线性调用。LangChain 早期的 chain 也属于这一代。它能串联几次工具调用，但是没有稳定持久化，没有完善的故障恢复，缺少预算管控，并发调度很粗糙。状态只存在对话消息里，一旦上下文溢出，进程中断，任务直接丢失，只适合短，简单的演示任务。这个阶段 harness 是附加在模型外面的简易包装，所有复杂逻辑都指望提示词让模型自己搞定。

**中期（2024，结构化执行阶段）**
随着 SWE-agent，MemGPT，Toolformer，Claude Code 这类面向长任务，代码，终端操作的智能体出现，大家发现：模型本身很难管好状态，版本，重复副作用，上下文压缩。于是开始把一部分确定性逻辑从提示词里抽出来，交给程序。
开始区分消息日志和独立任务状态；引入幂等，版本校验，产物快照；出现显式的调度依赖图，预算控制，自动摘要。这时候大家意识到，模型是决策大脑，而外围的运行系统是决定能不能落地的关键。这个阶段的 harness 已经是独立执行层，但是大多是项目定制实现，没有统一术语，也没有标准化设计范式。

**近期（2025年底–2026，harness工程化时代）**
Anthropic 在2025年底发布长任务智能体的 harness 设计文档，正式把这个运行系统命名为 harness；随后 OpenAI，DeepSeek 跟进，“harness engineering”成为独立研究方向，学界也出现专门综述。
这个阶段的变化有几个核心：
1. 把 harness 当成和模型同等重要的优化对象，同一个模型，换一套 harness 可以显著改变任务成功率；
2. 标准化组件开始成型：MCP 协议统一工具接入，插件化架构，事件驱动，独立状态层成为主流；
3. 区分两类路线：托管式 harness（OpenAI Agents API，Claude Managed Agent），开箱即用，厂商封装调度，权限，恢复；开源可定制 harness（DeepSeek Harness），允许开发者替换循环，调度，压缩逻辑；
4. 研究方向进一步延伸：自优化 harness（self-harness），让智能体可以诊断，修改自身运行框架；训练和 harness 耦合，模型直接在 harness 环境里做强化学习，学习适配这套运行规则。

**当下的发展边界与未来方向**
现在的 harness 还处在快速分化期，并没有统一标准。
短期来看，它会继续往操作系统化的方向走：统一权限沙箱，资源配额，跨工具编排，多智能体协同调度，接管模型和所有外部系统之间的全部交互。
一个重要趋势是边界模糊：一部分原本由 harness 做的工作（自动摘要，判断何时调用工具，基础故障重试），会逐步内化进模型权重；但高风险的校验，幂等，权限，持久化，并发调度，依然会留在 harness 里，不会交给模型。
同时学界也在反思：harness 不是越复杂越好。很多长任务失败，根源不是模型弱，而是 harness 的状态同步，上下文组装，恢复策略存在缺陷。未来的核心方向，是在可控性，可观测性，开销之间找到平衡，而不是不断叠加更多模块。
