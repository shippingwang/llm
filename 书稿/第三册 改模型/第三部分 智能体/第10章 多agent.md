# 第 10 章 多智能体
单个智能体可以持续完成多轮工具调用与推理，但复杂任务往往天然包含多条并行线索，不同领域的专业要求，或是需要校验，评审，落地多条相互约束的产出。这时我们可以把一部分工作委派给其他独立智能体。每一个工作智能体拥有独立的上下文，工具权限和任务状态，聚焦局部目标完成多轮决策，再把结论，证据和产物回传给调度方。多个独立智能体协同服务同一个顶层目标，就构成多智能体系统。

协作模式有两种典型走向：一类是并行分头探查不同方向，比如同时检索不同资料，独立开发互不耦合的模块；另一类是流水线式依次交接，比如需求分析，方案设计，代码实现，测试验收按顺序流转。还有一类是同质智能体独立求解同一个问题，再交叉辩论，评审汇总。无论哪一种，分工本身都会带来额外开销：任务拆解，消息传递，结果对齐，冲突处理。协作方案必须和任务依赖关系一起设计，不能单纯靠增加智能体数量换取效果。

工业界的落地现状需要先澄清：**并不是所有业务都适合多智能体，但是长周期，多角色，多产物，强验收的工程场景，多智能体已经成为主流选型**。简单问答，单次工具查询，短流程脚本，单智能体配合 harness 就足够；而代码工程，知识库调研，端到端产品需求交付，数据治理，自动化运维这类场景，工业界普遍选择多智能体架构，核心原因不是模型本身不够强，而是权限隔离，上下文隔离，责任边界，可审计性，故障隔离这些工程约束，单智能体很难满足。

## 10.1 分工条件
多智能体能拿到正向收益的前提，是任务可以拆出低耦合，独立验证的子分支。不同数据源的调研，接口已经约定好的模块开发，互不干涉的实验复现，都适合分给独立工作者。每个子智能体在自己的上下文里搜集证据，迭代产出，最后由协调者统一验收，对齐口径。

如果任务内部依赖紧密，前一步的输出是后一步的核心参数，多个智能体还要频繁修改同一份共享状态，那么通信等待，冲突对齐会吃掉并行带来的收益。拆分任务之前，应当先梳理依赖图，标记哪些环节可以并行，而不是直接按“产品，开发，测试”这类角色模板硬拆分。

这里可以用阿马达尔定律估算理论上限：设原任务串行部分占比为 \(f\)，剩余部分可以由 \(n\) 个工作者理想均分，加速上限为
\[
S(n)
=
\frac1{f+(1-f)/n}
\]
举例来说，串行部分占 20%，4 个工作者理想加速上限是 2.5 倍。这个估算没有计入任务分发，结果汇总，接口限流，版本冲突的开销。在真实项目里，随着工作者数量增加，协调沟通的串行占比通常会上涨，最终加速比往往低于理论值，必须在完整任务链路里实测。

除了缩短耗时，多智能体另一个核心价值是拓展信息容量。一个子智能体可以加载大量原始文档，在本地完成筛选，精读，摘要，只把相关结论和证据引用交给主协调者。这样避免主上下文被海量原始材料撑爆。但摘要本身有信息损失，子智能体返回结果时，必须附带可追溯的证据引用，未确认的假设项，方便协调者后续复核。

子任务的目标必须具备可验收边界。“调研这个系统”过于宽泛，很容易出现重复探索，漏核查；而“梳理支付模块的3条核心数据流，标注上游调用方，异常返回码，未确认的依赖接口”，边界清晰，更容易标准化交付。

同时子任务要有足够的工作量。如果只是单次固定查询，直接并发调用工具就足够，拉起一套完整智能体（独立上下文，工具权限，状态管理）的开销反而得不偿失。只有子任务本身需要多轮工具迭代，根据反馈动态调整思路时，独立智能体的价值才能体现。

> 工业实例：企业代码库批量重构项目。
> 目标是把老框架的接口统一升级。架构协调智能体先输出接口规范文档，再把不同业务模块分给独立的开发智能体。每个开发智能体只允许读写自己分配到的模块目录，独立读取代码，修改，跑单元测试。模块之间通过预先约定的接口文档对齐。只读调研类子任务可以几十个并行；有写入权限的开发智能体，会控制并发数量避免文件冲突。这个场景选择多智能体，除了并行提速，更关键是权限隔离：单个子智能体故障，写坏代码，只会影响分配给它的模块，不会全局污染。

## 10.2 协作结构
工业落地最主流的结构是**主协调者 + 若干工作者**。主智能体持有顶层目标，全局约束，权限策略，负责拆解子任务，分配输入，设定验收标准。工作者拿到子任务之后，在自己隔离的沙箱，独立上下文里调用工具推进，完成后返回结论，产物，证据清单。主协调者统一校验多份结果是否自洽，判断是否需要补充核查，或是直接合并交付。

这种结构下，工作者不需要读取全部全局历史，但是协调者必须拿到可追溯的依据。如果子智能体只返回一句简短结论，没有附带日志，文件快照，测试结果，后续出问题很难定位。所以子产出必须绑定可打开的产物引用。

第二种常用模式是**接力交接式多智能体**。一个智能体识别到当前环节需要别的专业能力，另一套工具集，就生成标准化交接包，把任务状态，已有材料，下一步目标一起移交，由新的智能体接管。交接完成之后，前序智能体可以休眠，减少资源占用。适合流水线场景：需求评审 → 方案设计 → 编码实现 → 自动化测试 → 缺陷复盘。

早期 AutoGen 奠定了消息驱动的交互范式，把模型，工具，人工评审都封装成可以互相收发消息的代理对象。系统核心不再是模型本身，而是消息路由规则：谁可以接收消息，收到消息之后触发什么逻辑，什么时候停止对话。很多内部平台的多智能体底座，底层依然沿用这套消息事件模型。

当多个智能体需要辩论，交叉评审时，还要有发言调度策略。可以固定轮换，也可以由调度器根据当前分歧点指派发言者。动态调度更灵活，但要增加终止判定逻辑，防止智能体无限循环闲聊，持续消耗算力却不产出新证据。

CAMEL 提出的角色配对范式，适合双向配合的短任务，一个提出需求，一个落地执行，依靠角色提示约束职责。但纯提示驱动的角色很容易漂移，工业项目里一般会叠加工具白名单，子任务 schema 约束，而不是只靠提示词区分角色。

MetaGPT 代表的**固定流程驱动**路线，在标准化软件工程场景落地非常广泛。它把软件开发的固定SOP固化下来，需求，设计，编码，测试各自对应角色，上一阶段产出的文档作为下一阶段的强制输入。优点是流程稳定，产物规范，适合标准化交付；缺点是灵活性弱，需求发生重大变更时，整条流水线都要回滚重跑。

真实工业平台很少只使用单一结构，大多是混合架构：顶层用主协调者动态拆分任务，稳定的子链路使用固定SOP流水线，关键节点派出独立评审智能体交叉校验。

> 工业实例：内部产品需求交付平台。
> 协调智能体拆解需求，分给调研智能体梳理竞品和历史工单，分给产品智能体写PRD，分给架构智能体输出技术方案。PRD和方案产出之后，自动交给评审智能体做合规，边界，依赖评审。评审发现问题，原路退回对应角色修改。整个链路里，调研，产品，架构，评审是不同角色智能体，工具权限互相隔离：评审智能体只读，不能修改文档；开发智能体只能访问指定代码仓库分支。

## 10.3 任务与消息
子任务请求会被封装成结构化对象传递，而不是自由文本。
```json
{
"task_id": "subtask-03",
"parent_id": "task-042",
"goal": "核查导出模块的日期处理与相关测试",
"input_refs": ["requirements-v3", "repository-snapshot-18"],
"scope": ["src/export", "tests/export"],
"allowed_actions": ["read", "run_tests", "write_own_report"],
"output_ref": "findings/date-check-v1",
"limits": {"model_calls": 8, "tool_calls": 20}
}
```
结构化字段明确目标，输入版本，工作范围，允许动作，交付地址，资源上限，同时可以携带依赖，超时策略，失败降级规则。子智能体基于指定版本的材料工作，输出结果标注对应的版本，避免协调者混用新旧版本的分析结论。

子任务返回结果分为四类字段：结论，证据引用，产物，未决事项。状态标记为 completed，partial，failed，waiting。partial 非常实用：子任务还没有做完，但已经产出一部分可用结果，可以先回传给协调者，由上层判断是继续追加算力，还是先使用已有成果。失败的返回必须写明失败步骤，已经产生的副作用，不能只返回一句话失败。

所有产物引用都要支持稳定读取。文档，代码快照绑定版本哈希；远端业务记录绑定对象ID和查询条件。协调者日常只读取摘要，遇到分歧时再打开原始证据。这种方式兼顾上下文开销和可审计性。

消息本身也要区分类型：通知消息，变更指令，新的子任务。如果主协调者中途修改目标，这条变更指令要投递到正在运行的子任务，并且更新任务状态。不能只发一条自然语言通知，子智能体看不到状态变更，继续按旧目标执行。

通信成本随智能体数量快速上涨。\(n\) 个智能体两两互通消息，一轮通信链路是 \(n(n-1)\)。集中协调模式通信量可控，但协调节点会成为瓶颈。工业平台一般采用定向消息，只把消息发给依赖它的下游，不做全量广播。

摘要的取舍是工程上反复调参的点。摘要压缩过狠，丢失关键假设；完整传递全部轨迹，协调者上下文会爆炸。成熟平台的标准做法：结构化结论+简短自然语言说明，附带可跳转的产物引用。关键数值，版本，风险项单独抽成字段，不埋在自然语言段落里。

## 10.4 共享产物
多个智能体并行读取同一份材料通常安全，并发写入同一个对象是事故高发点。除了直接覆盖的显性冲突，还有更隐蔽的语义冲突：文本合并没有报错，但接口约定，业务逻辑已经互相不兼容。共享产物管理，既要管版本，也要管语义约束。

代码场景最常用方案：按目录，模块分配写权限，每个开发智能体在独立沙箱分支修改，变更提交之后再统一合并。接口变更必须先由架构角色统一发布约定，下游开发基于锁定的接口版本工作，不允许私自修改公共依赖。

文档，报告类场景，优先使用“多人产出，单点汇总”。各个调研智能体独立产出分片报告，由集成智能体维护最终主文档。不要让多个智能体同时编辑同一份最终文档，冲突和口径不一致很难治理。

合并事实的时候，优先对齐实体，时间，统计口径。两份结论数字不一致，大概率是读取了不同版本数据源，统计范围不一样。协调者不能直接投票，而是生成一条新的核查子任务，定向核验原始来源。

系统里要区分**建议**和**生效状态**。子智能体提出修改方案，只是建议；经过集成，校验之后，才会更新主版本。有副作用的外部操作（下单，发布，数据变更），统一由固定的执行角色发出，并且复用第9章 harness 的幂等ID，状态查询机制，防止重复执行。

合并完成之后，必须做全局验证。每个子模块在自己的隔离环境里测试通过，不代表合并之后整体可用。顶层验收要针对合并后的最终版本执行核验，并且保存验证记录。

> 工业实例：数据治理平台。
> 多个智能体并行盘点不同数据表的字段，血缘，质量规则。它们只读原始数据表，各自产出质量报告；统一由一个汇总智能体维护全局数据字典。如果某个智能体提出字段变更，先提交变更申请，经过评审智能体核验之后，才会正式更新元数据。所有变更都留版本记录，方便追溯是谁，在哪个子任务里提出的改动。

## 10.5 调度与资源
多智能体有两层预算：子任务独立预算，加上全局总预算。很容易出现每个子任务都没有超限，但是整体算力持续膨胀。调度器需要同时管控全局模型调用次数，工具调用配额，并发智能体数量，子任务递归深度，截止时间。

总开销不只是模型生成token，还包括所有子智能体的系统提示，工具返回，交接摘要，同一份基础指令会在多个智能体里重复加载。前缀缓存可以降低prefill开销，但无法省掉生成和工具执行成本。

执行耗时由关键依赖链决定。多条分支并行时，整体任务的速度由最慢的那条分支决定。平台会实现抢先交付策略：如果部分分支已经足够支撑核心目标，可以先整合交付，非关键分支继续后台执行或者直接裁掉。临近截止时间，资源优先分配给阻塞整条链路的关键节点。

取消操作需要沿任务树向下传播。顶层任务终止之后，正在运行的子任务，后台工具轮询，待提交的副作用操作，都需要按策略停止。这里有一个很容易踩坑的点：停止子智能体，不会撤销它已经执行完成的外部操作，调度器必须记录已经生效的变更。

Anthropic 公开的多智能体调研系统给出了一个参考量级：多智能体调研任务的token消耗大约是普通单轮对话的15倍。这个数值不是通用标准，但它提醒工程落地：多智能体是用算力换取并行能力，隔离性和校验能力，不是省钱方案。

选型判断标准：适合多智能体的场景，一般是长文档调研，模块化开发，多维度评审；适合单智能体的，是连续操作同一个界面，强依赖串行推理，子任务粒度极小的场景。

调优的标准实验方式：固定全局总预算，逐步增加并行智能体数量，同步缩小每个子任务的工作量，观测成功率，关键路径耗时，交接冲突量。一开始并行带来收益，到某个临界点之后，拆分过细，重复读取，汇总冲突会拉低整体效果，这个临界点就是当前任务的最优拆分粒度。

主协调者本身是典型瓶颈。大量子任务同时返回长篇报告，协调者上下文会被塞满。成熟平台的做法：子智能体只返回结构化发现，冲突清单，风险点，协调者只对分歧项打开详细证据，而不是读取全部报告。

子任务失败之后重新派发，不能直接拉起一个新智能体重复执行写入操作，容易产生竞争。写类任务，先暂停旧任务，隔离沙箱，再指派新负责人；只读调研任务，可以同时派出两个独立智能体，比对两份结论，用来交叉校验。

## 10.6 集成与辩论
同一任务交给多个独立智能体分别求解，再交叉对比结果，是另一种常见用法，目标是降低单条推理路径的疏漏。想要保证独立性，要让各个智能体先独立完成全部推理，之后再交换结果；如果一开始就互相阅读，很容易趋同，共享同一个错误假设。

Multiagent Debate 的思路，就是让多个智能体先独立输出答案和推导，之后多轮辩论，把争议收敛到具体事实点：某个条件有没有使用，数值来源是否可靠，推导和原始资料是否冲突。辩论的价值，不在于比拼话术，而在于把分歧转化为可核验的查询，测试，计算。平台会区分两种修改：只是改写措辞，或是调用工具拿到新证据修正结论。无法收敛的分歧，最后交给指定审核角色裁决。

在答案是离散选项的场景，可以使用多数投票。假设每个判断者独立正确概率为 \(p\)，三人投票多数正确的概率：
\[
p^3+3p^2(1-p)
\]
这个公式成立的前提是错误互相独立。但模型共享训练数据，检索同源文档，很容易出现群体性错误。工业项目里想要提升独立性，会给不同评审智能体分配不同检索源，不同验证工具，再看投票能不能稳定提升准确率。

开放类产出，很难直接投票，适合 MoA（Mixture-of-Agents）分层汇总。第一层多个智能体独立生成方案，第二层汇总模型读取全部候选，融合，修正，输出最终版本。它不需要复杂的任务调度，更偏向“多候选+分层精炼”，适合写作，方案生成这类开放任务。但候选越多，汇总阶段的上下文开销越高，层数和并发数量要做收益权衡。

还有一类专职评审智能体，不负责生成方案，只聚焦单一维度校验：接口兼容性，引用真实性，安全合规，测试覆盖率。生成者修改之后，再次提交给评审者复检。生成，辩论，汇总，定向评审可以自由组合。

做对照实验时，要固定全局算力预算，对比单智能体和多智能体的效果。分工类场景重点看并行提速，冲突管控；辩论评审类场景重点看错误检出率的提升。多智能体本身不是银弹，增加调用的每一个环节，都要对应明确的质量或者时效收益。

> 工业实例：代码评审平台。
> 多个评审智能体各司其职：一个查安全漏洞，一个查性能隐患，一个查编码规范，一个核查单元测试覆盖。它们独立读取同一份PR，各自输出问题清单，互不干扰。汇总智能体合并所有问题，去重，标注风险等级，再推送给开发。这套方案的好处是评审维度可以横向扩展，新增一个检查项，只需要新增一个评审代理，不用改动主流程。

## 10.7 多智能体与 Harness 的衔接

多智能体负责任务拆分，角色分配，消息流转与结果汇总，而 Harness（执行层框架）统一接管所有智能体外部动作的落地，状态持久化，幂等与校验。二者的边界可以简单概括：**智能体做决策，Harness 做可靠执行与观测**。没有这一层隔离，多个智能体各自直接调用工具，操作外部系统，极易出现重复提交，状态不一致，副作用无法追溯的问题。

每一个子智能体发出的工具调用，文件修改，接口请求，都不会直接触达外部资源，而是先提交给 Harness。Harness 会给每一条操作分配全局唯一的操作 ID，也就是第 9 章里提到的操作主键，用来实现幂等。同一个子任务重试，或者调度器重新派发任务时，重复的操作 ID 会被拦截，避免重复发单，重复写入数据库，重复合并代码这类危险副作用。

Harness 同时维护一套全局任务状态树，和多智能体的任务树一一对应。顶层任务，子任务，每一条执行动作都有独立状态：pending，running，success，failed，cancelled。调度器发送取消指令时，不是直接杀掉智能体进程，而是通过 Harness 向下传递终止信号：标记子任务为取消，停止派发新的工具轮次，同时记录已经完成，不可回滚的外部操作。智能体本身只是生成下一步动作的逻辑，它随时可以被重启，替换，真实世界的状态全部由 Harness 保管。

权限与沙箱隔离也在 Harness 层实现。在多智能体配置里，我们只声明每个角色的动作白名单，读写范围：调研智能体只能读仓库快照，只读文档；开发智能体只能操作指定分支目录；评审智能体没有任何写入权限。Harness 拦截越权动作，在调用外部接口之前做参数校验，限流，配额扣减。算力预算也在这里统一统计，它汇总所有智能体的 token 消耗，工具调用次数，对照全局预算阈值，达到上限之后停止分发新的子任务，而不是等到各个智能体分别超限之后再止损。

智能体和 Harness 之间的交互接口是标准化的。智能体输出结构化动作请求，Harness 返回标准化观测结果，附带版本快照，执行日志，异常码。这带来两个工程好处。第一，同一个工作者智能体，既可以在单智能体链路里跑，也可以直接放进多智能体调度池，不需要改动内部推理逻辑；第二，替换底层调度策略，更换模型，切换评审流程，都不需要修改执行层的校验逻辑。

子任务交接，失败重派也依赖这套统一状态。当一个工作者超时，崩溃或者产出不可信结果，调度器可以拉起新的同角色智能体接管这个子任务。新智能体不会从头读全部历史对话，而是从 Harness 读取该子任务的快照：已经完成的动作，已产出的产物引用，未解决的前置依赖，已经消耗的预算。对于只读调研任务，调度器还可以并行拉起第二个智能体独立跑一遍，两份观测结果回传给协调者做交叉比对；对于写入类任务，Harness 会先锁定资源，防止新旧两个智能体同时修改同一个对象，产生冲突。

最后，所有日志，产物，操作记录在 Harness 层归集，形成完整审计链路。协调者合并多方结论产生分歧时，不需要回溯各个智能体内部的对话上下文，只需要根据 task_id，operation_id 拉取对应的原始输入，工具返回，产物版本。这也是工业平台和简单 Demo 版多智能体最大的区别：Demo 的消息流只服务于当前对话，而 Harness 把决策和真实世界的副作用解耦，让多智能体系统具备可重试，可审计，可控回滚的工程属性。

> 
> 工程示例：代码重构多智能体平台
> 协调智能体拆分模块改造任务，下发给多个开发智能体。开发智能体生成修改文件，执行测试的请求，全部送入 Harness。Harness 分配沙箱分支，扣减子任务配额，给每一次 git 提交分配幂等 ID。如果某个开发智能体长时间无响应，调度器拉起新代理接管，新代理从 Harness 读取该模块已经提交的变更和测试报告。所有提交，测试结果，报错日志统一存储，评审智能体拿到的不是模型对话，而是 Harness 输出的标准化执行记录。
