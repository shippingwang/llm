#  8 章 Agent 下：工具交互，Skill

Agent 想好要查询内容或者修改文件之后，这个想法不能直接生效。模型输出的意图，和真实程序执行之间，还有一层转换流程：先标准化生成调用请求，再做校验，执行，最后把执行结果整理成模型可以读懂的观察，送入下一轮推理。

我们需要提前告诉模型每个工具能干什么，参数怎么填，返回数据长什么样，模型才能结合当前任务选出合适动作。遇到复杂任务，模型还可以写一段程序串联多个工具，或者直接调用预先写好的成熟流程。工具接口，沙箱执行环境，流程说明，共同决定 Agent 能不能稳定完成真实任务。

## 8.1 调用消息

每一个工具都包含名称，功能描述，参数结构。模型读到这些信息之后，结合上下文挑选工具，并且填充参数。执行器拿到调用请求，找到对应的程序运行，再把结果返回给模型。结果追加到上下文，模型再判断继续调用工具，还是直接输出最终答案。

举一个读取订单的接口声明示例：

```
{
"name": "get_order",
"description": "按订单标识读取当前状态，条目和可执行操作。",
"input_schema": {
"type": "object",
"properties": {
"order_id": {"type": "string"}
    },
"required": ["order_id"],
"additionalProperties": false
  }
}
```

描述用来告诉模型这个工具适合什么场景，JSON Schema 用来约束参数的结构和类型。模型需要从用户问题，历史观察里拿到真实的订单编号。Schema 只能限制参数格式，**没法保证填入的编号一定对应真实存在的订单**。

单次调用需要带上调用标识，返回结果也要绑定同一个标识：

```
{
"call_id": "call-17",
"name": "get_order",
"arguments": {"order_id": "ord-204"}
}
```

执行器返回的内容，可以包含执行状态，结构化数据，简短说明。call_id 的作用是绑定请求和返回结果，order_id 是业务对象编号，二者用途完全不同。读取同一个订单可以发起多次独立调用；调用超时重试的时候，还需要额外的业务标识，用来防止重复执行写操作。

模型输出工具请求之后，本轮生成就结束，交由后端程序负责执行。工具返回结果之后，才开启新一轮模型推理。工具调用只是一段请求文本，**不会在模型内部运行代码**，参数只是待执行的指令。这个边界非常关键：模型只负责表达意图，参数校验，业务操作，副作用控制全部交给程序。

如果同时调用多个工具，返回结果要分开记录状态。有可能其中一个查询成功，另一个查询失败，模型需要清楚哪些信息已经拿到。如果直接把所有结果揉成一段无来源的文字，很容易出现信息混淆，引用错误。工程上可以同时保留结构化原始返回和简短摘要，原始数据通过引用标识按需读取。

我们顺着一轮完整流程看清楚工具的价值：模型先读取 get_order 的说明，从上下文拿到订单 ID 发起调用；执行器返回订单正在处理，版本号为 6。模型就能知道任务还没有结束，后续修改操作必须带上版本 6 做校验。如果返回订单不存在，下一步就核对订单编号；如果返回服务暂时不可用，就要走重试或者降级分支。

后面每一轮决策，都只能依赖已经拿到的观察。模型不能靠工具描述去猜测订单里面有哪些字段，也不能把一次查询动作，当成已经完成修改。如果用户要求修改数据，模型只能先生成变更请求，执行器校验前置条件，版本号，确认安全之后再提交写入，最后把真实结果回传。最终结论全部基于执行返回，区分清楚计划，已执行动作，待办事项。

在训练的时候，工具轨迹的难点不在于参数拼写。真正决定多轮任务成败的，是模型能不能选对对象，怎么处理空结果，识别过期版本，根据返回结果调整后续动作。所以工具示范，评测用例，都要覆盖这些不同状态，才能检验模型会不会真正使用接口，而不只是格式写对。

## 8.2 接口设计

工具接口的粒度，直接决定 Agent 需要多少次决策。接口拆得太细，简单任务也要反复调用，拼接参数；接口做得太粗，一次动作附带大量副作用，很难校验和回滚。合适的接口边界，对应一个语义清晰，结果可以核验的工作单元。

读取，准备预览，提交写入，最好拆成独立操作。读取动作只返回当前真实数据；准备阶段生成变更内容，输出预览和对象版本；提交动作在版本没有过期的前提下，完成写入。这样模型可以先核对内容，程序也能在写入前做版本校验。是否需要人工确认，由权限和业务规则决定。

参数尽量使用稳定唯一标识，带上明确单位。日期标注时区，金额标注币种和单位，分页参数带上游标，文件修改带上基准版本。不要把多种信息塞进自由文本框，否则原本可以确定的解析逻辑，又重新交给模型去猜。

默认参数也会带来风险。默认直接覆盖文件，默认取当前时间，默认选中第一条记录，在信息不全的时候，很容易产生意料之外的修改。默认值只适合稳定不变的常规行为；对于会产生副作用的参数，要么要求显式传入，要么在准备阶段标记为待确认项。

错误返回要给出可解读的语义。参数类型错误，要指明出错字段；版本冲突，返回服务器最新版本；查询为空，带上本次筛选条件。模型拿到明确反馈，才能区分是改参数重试，换查询条件，还是直接终止任务。如果只返回笼统的 “error”，模型很容易无意义地反复重试。

返回内容的长度，要服务于下一步推理。搜索接口优先返回标题，片段和引用；读取大文件支持按范围读取；表格接口先返回字段结构，行数和少量预览。超大结果单独存储，返回句柄，避免一次性把全部数据塞进上下文。

大量统计，筛选计算，适合放在程序侧完成。模型只需要生成筛选逻辑，交给执行环境处理全量数据，最后返回聚合结果，减少上下文传输负担。但是脚本必须限制输入范围，超时时间，并且增加结果校验。我们需要同时权衡 token 开销，和计算逻辑的正确性。

模型学会 “什么时候调用工具”，也可以通过数据训练。Toolformer 先用少量示范样例生成候选调用，真实执行之后，看工具返回能不能提升后续文本预测效果，用这个标准筛选训练样本。完整的 Agent 任务，还需要让模型看到工具返回，以及后续的处理步骤，学会根据反馈继续推进。

## 8.3 程序式行动

单次函数调用只能表达一条独立操作，但很多任务需要循环，条件判断，中间变量计算。如果每一个小分支都单独调用模型，大量中间数据会反复占用上下文。对于规则固定的流程，可以让模型直接写出完整程序，交给执行器运行，再把结果返回模型。

PAL（Program-aided Language Models）是比较早的这类思路。模型读懂自然语言问题，把条件，数量关系翻译成代码，解释器负责数值运算。模型负责理清变量和约束，Python 运行时承担计算；但我们依然要核对代码，确认程序逻辑和原题要求一致。

更进一步，代码可以直接调用环境提供的工具函数，也就是 CodeAct。模型输出可执行 Python 代码，代码内部可以调用工具，执行结束之后，把输出或者报错交给模型。相比单次函数调用，代码可以在一轮动作里面组合多个工具，写判断，循环，保存中间变量。

假设执行环境已经提供查询，写入工具，模型可以生成下面这段代码，完成数据筛选统计：

```
rows = query_rows(table="orders", status="completed", limit=5000)
selected = [row for row in rows if row["currency"] == "CNY"]

result = {
"count": len(selected),
"amount_cents": sum(row["amount_cents"] for row in selected),
}
artifact = write_json("summary.json", result)
print({"summary": result, "artifact": artifact})
```

这里的工具函数，字段定义，由执行环境预先提供。模型选定数据范围，统计规则，程序完成批量处理，返回统计结果和文件引用。如果需要遍历全量数据，就要处理分页，或者直接调用后端聚合接口；示例里的 limit 只是本次读取上限。模型拿到结果之后，判断信息是否足够，再输出结论或者继续处理。

执行环境还可以在同一会话里保留变量。第一轮读取数据，第二轮清洗缺失值，第三轮生成报表，不需要每次把全部原始数据转成文本送入上下文。模型只读取预览和汇总信息，数据处理交给程序。程序输出分开保存结构化结果和运行日志，方便模型核对。

代码运行出错的时候，执行器返回异常类型，报错位置和简短上下文，模型基于报错修改代码。语法错误在运行前就能捕获；运行时异常，有可能一部分动作已经执行完成。带有写入操作的代码，重试前要先检查已经产生的文件和外部状态，防止重复执行。长流程代码可以拆成多个阶段，每阶段完成保存结果，方便从断点恢复。

面向软件工程的 SWE-agent，也采用这套接口思路。它配套文件检索，区间读取，编辑，运行测试的工具，让 Agent 持续定位和修改代码项目。编辑接口可以立刻返回语法报错，读取接口带上行号上下文，方便定位问题。

多种执行方式可以混合使用。稳定的业务操作封装成工具函数，批量数据处理交给代码，界面自动化依赖页面元素和截图。模型拿到结果再决定下一步，运行环境负责保存状态，提供可核验的反馈。

## 8.4 MCP

当 Agent 对接很多不同工具服务，每一个服务都有自己独立的调用格式，客户端就要写大量适配代码。MCP（Model Context Protocol），也就是模型上下文协议，给应用和工具服务定义统一标准，工具发现，资源读取，工具调用都遵循同一套结构。

MCP 里有三类角色：host 是承载 Agent 的主应用；client 是 host 内部和服务通信的组件；server 对外提供工具能力。模型本身不会直接发起网络请求；host 读取 server 暴露的能力描述，选择性传给模型，再把模型的调用请求转成协议消息发给服务端。

协议底层基于 JSON-RPC 2.0。连接初始化阶段，双方交换版本和支持能力。server 向外暴露三类能力：tools 代表可执行动作，resources 代表可以读取的静态资源，prompts 是可复用提示模板。三者都可以用来补充上下文，但用途不一样，需要区分。

一次标准接入流程是：建立连接，初始化握手，拉取可用工具列表，整理描述交给模型，转发模型调用，处理返回结果。当 server 的工具列表更新，host 需要刷新能力列表。如果工具很多，支持分页或者按需加载，避免一次性把全部工具描述塞进上下文。

标准化协议，解决不了业务语义冲突。两个服务都叫 search，检索的数据源可能完全不一样；两个 update 接口，覆盖逻辑也可能不同。工具名称，描述，入参 schema，返回语义，才决定模型能不能正确使用。协议只是减少适配成本，每个工具的业务逻辑依然要单独测试。

身份，权限控制，由连接和服务端负责。host 持有用户授权范围，server 再对每一次请求做权限校验。工具返回的文档，描述属于外部输入，应用本身要做好可信校验。协议里的只读，破坏性标记，只是辅助提示，不能替代真实访问控制。

MCP 的交付产物是一组可以复用的工具服务和连接，**不需要重新训练模型**。开销主要来自工具描述加载，网络交互，服务计算，结果传输。如果工具数量庞大，每次都把全部工具描述送入上下文，会显著增加 token 开销，所以按需检索，动态选择工具是工程里的常见方案。

## 8.5 Skill

工具定义单次操作怎么调用，复杂任务还需要知道多个工具怎么有序组合。Skill 把任务步骤，领域规则，模板，可复用程序打包在一起，Agent 识别到匹配任务之后，加载这套流程执行。

一种常用的 Agent Skill 目录结构，以 SKILL.md 作为入口文件，里面包含名称，适用场景，执行步骤；配套 scripts 脚本目录，reference 参考文档，静态资源目录。名称和简短描述用来快速匹配任务，正文写清楚执行步骤和检查标准，脚本承载确定性的重复处理逻辑，参考材料存放领域细节。

按需加载可以节省上下文。系统先读取简短元信息，判断这个 Skill 适不适合当前任务；匹配成功之后，再加载完整流程；执行到对应步骤时，再打开脚本，参考资料。这样不用任务一开始，就把所有 Skill 全部塞进上下文。

高质量的 Skill，写清楚执行前提和验收标准，而不是简单罗列步骤。输入来源，数据格式，什么时候需要向用户补充信息，脚本会生成哪些文件，完成之后怎么校验，都要写明白。稳定的计算逻辑，优先用经过验证的脚本实现，比让模型每次手写代码更稳定，结果更容易复现。

Skill 不会扩大 Agent 的权限。流程里写了读取某个目录，最终能不能读，依然由执行器的权限控制；脚本发起网络，写入文件，同样要遵守任务授权。我们需要记录 Skill 的来源和版本，防止同名 Skill 更新之后，行为发生变化而没有感知。

测试 Skill 的时候，可以固定模型和测试用例，做几组对照：不加载 Skill，只加载文字步骤，加载完整流程 + 脚本。对比任务成功率，调用次数，上下文长度，失败恢复能力，产物质量。如果收益几乎全部来自脚本，就要单独评估脚本的价值；如果模型经常判断错适用场景，就要修改 Skill 的入口描述。

## 8.6 执行与恢复

模型输出调用请求之后，执行器一般分三层校验：第一层校验结构，检查字段，类型，必填参数；第二层校验业务语义，核对对象，单位，版本，前置条件；第三层校验权限，确认操作在授权范围内。全部校验通过之后再执行，并且持久化执行状态。

只读查询遇到临时网络故障，一般可以直接重试；写操作要小心重复带来的副作用。请求已经到达服务，但是返回报文丢失，客户端单凭超时，无法判断操作是否成功。**幂等键**用来标识同一个逻辑操作；恢复的时候，先查询当前状态，再决定要不要重试。

幂等键要绑定业务含义。修改金额，目标对象，版本之后，不能继续沿用旧的幂等键；每次重试都生成新键，又失去去重的意义。参数摘要，业务操作 ID，调用 ID，三者要分开管理。

耗时很长的后台任务，可以返回作业句柄 job_id。执行器记录任务状态，截止时间，模型可以先去处理别的独立任务，之后再轮询进度。主动查询和完成通知都可能拿到结果，系统要保证最终的业务动作只生效一次。任务取消之后，后台作业也要同步终止或者按策略保留，避免资源持续占用。

代码执行是通用计算能力，可以批量处理数据，调用库，生成文件。执行沙箱要隔离目录，依赖，网络，资源上限，返回退出码，有限日志，产物引用。脚本运行成功，只代表语法没有报错，业务结果依然需要单独校验；测试脚本和业务代码最好分开维护。

界面自动化依靠页面元素或者屏幕坐标执行动作。页面布局会在两次操作之间发生变化，所以点击之前的观察，点击之后的状态确认都必不可少。元素选择器比固定坐标更稳定，截图可以补充结构化页面缺失的视觉信息。两种方式可以搭配，并且每次操作之后回读状态，确认动作是否生效。

执行器保存每一次调用记录，返回结果，产物版本之后，模型就可以基于确定状态继续推进。遇到网络中断，进程重启，程序先读取历史记录，再决定查询结果，重试操作，或者重新交给模型判断。

## 8.7 轨迹监督

模型能够生成合法的调用格式之后，还需要学会在不同状态下选择动作。一次查询返回空结果，继续沿用旧编号通常没有意义；工具返回了明确错误，模型则应根据错误修改参数或调整方案。要训练这些行为，我们需要保存完整交互，使模型同时看到先前动作造成了什么结果，以及接下来怎样继续。只收集成功任务的最终回答，能够监督交付文本，却没有保留中间决策的学习依据。

一条训练轨迹可以记成 \(\tau=(o_1,a_1,o_2,a_2,\ldots,o_K,a_K,o_{K+1})\)。其中 \(o_j\) 是第 \(j\) 次决策之前取得的观察，\(a_j\) 是模型生成的动作，\(K\) 是这条轨迹包含的决策次数。动作可以是一组工具调用，一段可执行代码，也可以是向用户提问或提交最终结果。观察则包含工具返回，用户补充和执行环境提供的信息。环境与模型轮流产生内容，所以一条轨迹的全部文本并不都由模型生成。

整理数据时，需要同时保存原始事件与模型每轮实际读取的输入。harness 可能截取文件片段，省略旧日志，或者把历史压缩成摘要，因此原始事件的完整拼接，与当时模型真正看到的上下文可能不同。若我们在训练时额外提供了后续证据，模型就会在比真实执行更容易的条件下学习。更稳妥的做法是保留每轮请求中的消息，工具定义和可用材料，再将目标动作与这份输入对应起来。

设这一轮的可见历史为 \(h_j\)，动作 \(a_j\) 由 \(L_j\) 个 token 构成，轨迹监督的基本损失为：

\[
\mathcal{L}_{\mathrm{agent\text{-}SFT}}
=
-\mathbb{E}_{\tau\sim D}
\sum_{j=1}^{K}
\sum_{t=1}^{L_j}
m_{j,t}
\log\pi_\theta(a_{j,t}\mid h_j,a_{j,<t})
\]

这里 \(m_{j,t}\) 标记当前配置要求学习的模型输出位置。工具名称，调用参数和最终回答，如果属于模型实际生成的内容，就可以进入监督目标。用户问题和工具返回作为输入提供，通常不作为策略需要复现的输出。实现时可以在完整序列中把这些位置的标签置为 -100，再处理好下一 token 对齐。掩码只去掉这些位置的直接监督损失，模型仍然需要读取观察，回答损失也会通过相关的上下文计算传播梯度。

在多轮记录中，这个区别尤其重要。工具可能返回很长的文件，日志或网页；如果把整条记录的每个 token 都作为目标，训练会花费大量权重去复述外部材料。我们真正希望模型学会的是如何利用这些材料决定下一步，因此需要按消息来源与实际生成边界制作标签。协议程序插入的角色标记和控制字段，也要根据真实模板处理，不能仅凭文本中出现了某个字符串就推断整段都属于模型动作。

轨迹可以由人工示范，强教师或搜索得到，但每个可执行动作最好经过真实环境运行。教师提出一个看似合理的调用之后，我们需要取得对应返回，再让它继续生成；如果工具结果由教师自行编写，后续动作便可能依赖实际环境中不存在的信息。代码任务可以恢复仓库状态并运行命令，数据任务可以使用可重置数据库，对话任务则需要确定用户模拟器的角色和信息提供规则。这样收集到的示范才包含可复现的因果过程。

成功轨迹也需要检查执行过程。一次任务最后通过测试，可能经历了多轮有意义的修复，也可能包含大量重复调用。前者能够教会模型根据错误恢复，后者则会增加没有必要的行为。因此，筛选时可以保留有效修正，删去已经确认冗余且不影响后续条件的重复步骤，但不能为了缩短记录而把必要观察一起删除。对于失败轨迹，可以保留失败上下文，再接经过验证的修正动作，使模型学习怎样从真实错误状态继续。

如果模型使用相同上下文时可以模仿示范，自由执行时却频繁进入未见状态，继续增加相似成功轨迹未必足够。我们可以让当前学生实际运行任务，收集它经常产生的状态，再由教师或验证器提供修正。这个安排与同策略蒸馏有共同的数据思想，不过工具任务还需要确认修正动作在当前环境中能够执行。教师看到了完整成功记录之后，也不能直接把其中的下一步复制到学生已经改变的状态中。

## 8.8 多轮强化学习

监督轨迹提供了可学习的行动方式，但它通常只覆盖有限路径。同一个任务可能存在多种正确操作顺序，模型也需要适应自己执行时产生的新观察。我们因此可以让当前策略在环境中自主运行，依据最终产物和过程约束获得奖励，再提高能够完成任务的行为概率。代码测试，数据库状态和结构化产物检查，都可以提供其中一部分可验证反馈。

一次完整采样从初始环境开始。模型读取 \(h_1\)，生成动作，执行器返回观察，harness 再组装下一轮输入，直到任务结束或达到预算。使用组内相对奖励时，我们对同一任务运行多条轨迹，每条都恢复约定的初始状态，避免前一个候选已经修改的文件或记录改变后一个候选的难度。工具与模拟用户如果包含随机性，也需要保存它们的配置与运行记录，才能解释不同候选之间的差别。

在条件环境转移不直接依赖模型参数的设定下，轨迹概率中的可训练部分来自模型动作。于是，结果奖励版本的策略梯度可以写成：

\[
\nabla_\theta J
=
\mathbb{E}_{\tau\sim\pi_\theta}
\left[
\big(R(\tau)-b\big)
\sum_{j=1}^{K}
\sum_{t=1}^{L_j}
\nabla_\theta
\log\pi_\theta(a_{j,t}\mid h_j,a_{j,<t})
\right]
\]

\(R(\tau)\) 是整条轨迹的奖励，\(b\) 是不依赖当前采样动作的基线。模型通过改变动作影响后续观察，这种影响已经体现在采样得到的轨迹和奖励中。计算策略梯度时，工具返回不作为模型采样的动作加入求和，也无需对数据库，浏览器或解释器反向传播。

实现多轮 GRPO 时，可以先根据同任务候选的最终奖励计算组内优势，再把一条轨迹的优势分配给其中的有效动作 token。每个位置都需要对应采样时的旧概率，训练时在同一可见历史上重算当前概率，再构造选定的裁剪目标。KL 也应在明确规定的模型动作位置统计。轨迹中混入多少工具文本，不应悄悄改变损失分母，所以归一化时需要区分模型动作长度与整份交互日志长度。

将最终奖励传给全部动作，在相应假设下具有策略梯度依据，但信号往往较粗。一条最终失败的轨迹，可能前面检索和计算都正确，只在提交时漏掉条件；另一条成功轨迹，也可能包含多次无效操作。使用单个结果奖励时，我们很难仅凭这一条样本区分各轮贡献，这就是多轮任务中的信用分配问题。它更多地影响学习方差与样本效率，不能简单把整条轨迹共享奖励视为计算错误。

如果环境能够提供中间检查，我们可以为完成子目标或造成明确错误的动作记录逐轮奖励。第 \(j\) 轮的回报可以从当前轮向后累计，再减去当前历史下的价值估计，形成相应优势。也可以在可恢复的状态上比较不同后续，观察某个动作是否提高了完成任务的机会。这些方法提供更细反馈，但需要额外采样或训练价值模型。中间奖励还会改变优化目标，因此应根据任务要求定义，避免模型只增加容易得分的中间动作，却迟迟没有交付结果。

工具调用具有不同于普通推理文本的分布。失败任务可能包含更多重试，也就包含更多工具调用 token。如果把相同负优势分配到全部位置，再按长度聚合，这些调用可能在更新中取得很强的负权重，模型之后反而更少使用必要工具。2026 年的 TACA 针对这类现象，分别研究工具调用的优势处理，调用与直接回答的结果比较，以及成功调用的监督重放。这个例子说明，检查多轮训练时，需要把调用行为，执行结果和最终成功率联系起来，才能判断模型减少某类动作究竟改善了效率，还是失去了必要能力。

训练记录还会经过模板转换和重新分词。harness 保存的一轮请求可能包含摘要，代码片段或多个消息段，训练器需要重建模型当时真正读取的 token 序列。若把每轮上下文重复拼接成一条长序列，却又按整条序列重复计算相同动作的损失，部分步骤就会被无意增加权重。整理轨迹时，应让每段实际生成的动作具有明确标识，确认它在哪个训练样本中计分，重复出现的历史只提供条件。

Agent Lightning v1.0 提供了把运行与学习分开的近期实践。harness 保留原有的环境交互过程，训练系统收集模型请求和返回，再整理为优化所需样本。这样可以继续利用已有工具和上下文管理，但接入训练之后，仍然需要处理重新分词，样本合并，优势计算与归一化。运行程序负责正确完成交互，训练器负责解释这些交互怎样形成学习目标，两者之间需要保存足够精确的数据约定。

## 8.9 训练环境

在交互训练里，环境本身决定模型能获得什么经验。我们需要为每个任务提供初始状态，用户目标，可用工具，结束条件和奖励检查器。初始状态应能够恢复，工具要提供与目标应用相近的成功与失败返回，检查器则需要独立读取最终产物。模型可以修改工作文件，但不能同时修改隐藏测试和最终评分程序，否则奖励就可能反映检查过程的变化。

训练任务也需要覆盖不同阶段的困难。模型起初可能连调用格式都不稳定，这时可以先学习短轨迹与单步反馈；随着基本操作可靠，再增加需要读取多个对象，处理错误和跨轮保存信息的任务。难度变化应根据实际成功率安排。若绝大多数候选全错，模型难以从当前结果中区分行为；若几乎全部成功，则可以减少重复采样，增加仍能提供学习信号的任务。

为了检查泛化，我们应按任务来源，仓库，文档或工具组合划分数据，而不能把同一任务改写后分别放进训练与测试。模型在训练中见过一个接口，也可以继续测试它在新状态下的使用；如果希望判断它能否适应新工具，还需要另外保留没有参与训练的接口说明和任务。两种设置观察不同能力，训练报告应说明测试中究竟改变了什么。

模拟用户和环境错误也会影响奖励。模拟器过早提供隐藏信息，会降低任务难度；服务偶发失败，则可能使合理动作被记为失败。我们可以固定用户角色和提供信息的条件，保存外部返回，并区分模型行为错误与设施故障。后者按照统一规则重跑，模型自身重复调用和错误恢复则应保留在轨迹中，连同耗时一起统计。

资源预算需要按整条任务计算。每道任务采样多条轨迹，每条轨迹又包含多轮请求，生成，环境执行和评审的开销会共同增加。长工具返回虽然不作为策略输出计损失，仍会增加输入处理和反向传播所需的计算。比较训练方案时，应报告模型生成量，实际请求数，环境运行时间和最终完成率，才能判断更细的反馈是否值得额外投入。

形成一个新版本后，可以同时检查单次任务成功率，重复运行稳定性，工具使用情况和完成成本。如果测试成绩上升，却只发生在训练时反复使用的仓库或初始状态中，就需要继续补充独立任务。训练希望获得的是在观察发生变化之后仍能正确决策的能力，因此验证也应让模型真正执行，而不能只让它复述一条已经保存的成功轨迹。
