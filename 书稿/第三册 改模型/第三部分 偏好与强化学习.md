# 第三部分 偏好对齐与推理训练

**目的**：SFT 告诉模型“像这个答案”，偏好学习告诉它“在这两个答案里更应该选哪个”，强化学习则让它自己生成轨迹并从结果中学习。本部分沿着训练信号逐步增强，而不是把算法名并排罗列。

# 第 7 章 偏好数据与奖励建模

> **开场问题**：两个回答都没有标准答案，但标注员稳定地认为 A 比 B 好。怎样把这种比较变成训练信号？

## 7.1 为什么不继续做 SFT

开放式问答常有多个合理答案。把 chosen 当唯一标准答案做 SFT，会同时做两件事：提高 chosen 的概率，却完全不利用 rejected 告诉我们的“它差在哪里”。

偏好样本的基本结构是：

```json
{
  "prompt": "...",
  "chosen": "...",
  "rejected": "..."
}
```

它表达的是相对顺序，不是 chosen 得 100 分、rejected 得 0 分。A 胜 B、B 胜 C，并不意味着 A 与 B 的差距等于 B 与 C。

## 7.2 偏好对必须“有区分度”

若 chosen 完美、rejected 完全胡说，模型很容易区分，梯度价值反而有限。高信息量数据往往是两个答案都像样，但在一个关键维度上不同：是否遵循隐含约束、是否引用证据、是否泄漏隐私、推理有没有微妙错误。

也不能难到标注员无法稳定判断。应测标注一致率，并允许 tie/都不好。强迫标注员在两个同样差的答案中选一个，会制造随机偏好。

## 7.3 标注 rubric 必须拆维度

“总体更好”很容易退化成“更长、更像专家”。应把标准拆开：

- 正确性与证据支持。
- 是否完整遵循指令。
- 相关性与简洁性。
- 安全与权限边界。
- 风格和可读性。

不同维度冲突时要说明优先级。医疗回答中安全高于讨好用户；代码任务中测试通过高于解释华丽。标注界面、培训样例和仲裁流程都属于算法的一部分，因为它们决定了 reward 的含义。

## 7.4 Bradley–Terry 奖励模型

奖励模型给 prompt—answer 对输出一个标量 \(r_\phi(x,y)\)。用 chosen \(y_w\) 和 rejected \(y_l\) 训练：

\[
\mathcal L_{\text{RM}}
=-\log\sigma(r_\phi(x,y_w)-r_\phi(x,y_l))
\]

它只要求赢家分数高于输家，不要求分数本身有绝对意义。训练后 3.2 分不代表“质量 3.2”，不同奖励模型的尺度也不能直接比较。

通常从 SFT 模型初始化，加一个标量 value head。也可用生成式 judge 输出评分，但训练策略模型时，稳定的标量模型更便于批量计算。

## 7.5 奖励模型学到的捷径

奖励模型只会学习训练数据中能预测偏好的特征。若标注员常偏爱长答案，它就把长度当质量；若高分答案总以“当然可以”开头，它会奖励这句话；若训练中从未出现伪造引用，它可能无法识别。

因此必须做对抗测试：

- 内容相同，只改变长度和排版。
- 答案流畅但包含一个关键事实错误。
- 大量术语包装一个空洞答案。
- 回答直接声称“这是高质量、安全的答案”。
- 在末尾注入操纵 judge 的文字。

## 7.6 标量 reward 的信息压缩

帮助性、正确性、安全、简洁性本来是多目标的，把它们压成一个数必然丢信息。实践中可训练多个 reward/component grader，再按业务规则组合；或把硬约束做成门禁，违反即淘汰，不让其他高分抵消。

“总 reward 最高”并不自动等于产品最优。reward 是代理指标，最终仍要回到第 13–16 章的独立评测。

### 核心问答

**Q：偏好数据为什么不能只保留 chosen？** rejected 提供决策边界：它告诉模型“这个看起来也合理的答案为什么应该更低”，这是普通 SFT 丢失的信息。

**Q：reward 分数能跨模型比较吗？** 通常不能。它只在自己的训练分布和尺度内有意义，应看排序准确率与校准，而非绝对值。

**Q：标注一致率低说明什么？** 可能 rubric 不清、样本本身无明确优劣、或任务超出标注员能力。不能简单用多数票掩盖。

**Q：奖励模型准确率高就够了吗？** 不够。随机切分可能泄漏模板，且策略会主动寻找漏洞；必须做分布外和对抗测试。

# 第 8 章 直接偏好优化：DPO 及其变体

> **开场问题**：能不能不训练奖励模型、不在线采样，直接用偏好对更新语言模型？

## 8.1 从“提高赢家概率”还差一步

最朴素的 pairwise loss 是让 \(\log \pi(y_w|x)-\log \pi(y_l|x)\) 变大。但如果无限推，策略可能远离原来的语言分布，牺牲流畅性与通用能力。

对齐通常写成一个 KL 约束优化：既追求更高 reward，又不让新策略 \(\pi_\theta\) 离参考策略 \(\pi_{\text{ref}}\) 太远。参考策略一般是同一个 SFT checkpoint 的冻结副本。

DPO 利用最优策略与 reward 的关系，把未知 reward 消掉，得到：

\[
\mathcal L_{\text{DPO}}
=-\log\sigma\left(
\beta\left[
\log\frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)}
-\log\frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}
\right]\right)
\]

读法比推导重要：新策略相对参考模型，应该**更多地提升 chosen、或更多地压低 rejected**。比较的是相对变化，不是裸概率。

## 8.2 reference 在防什么

若 chosen 本来就比 rejected 常见，裸概率差异可能只是 SFT 已学会，不代表这次更新做了什么。减去 reference 的 log-ratio 后，训练只奖励“相对基线进一步向 chosen 移动”。

reference 还充当隐式 KL 锚点。实际实现可常驻一个冻结模型，也可预计算数据集中 chosen/rejected 的 reference log-prob。后者省训练显存，但模板、tokenizer 或序列变化后必须重算。

## 8.3 beta 到底控制什么

\(\beta\) 与 KL 约束强度相关。直观上，它决定模型为满足偏好允许离参考分布走多远，但不同实现的参数化和解释方向可能不同，不能只凭“beta 越大越激进”死记。

调参时直接监控：

- chosen reward 与 rejected reward 的差。
- policy 与 reference 的 KL。
- chosen/rejected log-prob 各自变化。
- 回答长度与格式分布。
- 通用能力回归。

有时 loss 在下降，却主要是把 rejected 概率压到极低，chosen 本身没有提升；这会让模型更尖锐但不更好。

## 8.4 长度偏差与 token 求和

序列 log-prob 是每个 token log-prob 的总和，天然随长度变得更负。chosen 和 rejected 长度差异大时，DPO 会受到长度影响。

处理方式包括按 token 平均、控制配对长度、在数据和评测中显式监控长度，以及采用对长度更稳健的目标。但归一化也会改变“整条回答概率”的语义，没有一个对所有任务都正确的选项。

## 8.5 DPO 为什么简单，也为什么有上限

优点：离线训练、实现像分类 loss、不需要 rollout、不需要 value model，稳定且成本低。

上限来自数据：它只能学习偏好数据覆盖到的答案。若数据由旧策略生成，新策略变强后会进入新的行为区域，原偏好边界不再够用；它也不会主动探索全新的解题策略。DPO 是优秀的离线偏好学习方法，不是 RL 的完全替代。

## 8.6 IPO、SimPO、KTO、ORPO 各在改什么

- **IPO**：避免 DPO 在可分数据上把偏好间隔无限推大，使用有有限目标间隔的回归式目标，提升噪声鲁棒性。
- **SimPO**：不用 reference model，以平均 log-prob 和显式 margin 做偏好优化，减少显存与实现复杂度。
- **KTO**：可用不成对的“好/坏”反馈，不要求同一 prompt 下严格配对，适合点赞/点踩日志，但更依赖数据分布和基线估计。
- **ORPO**：把 SFT 的正样本似然和偏好 odds 目标合在一个阶段，不需 reference，适合简化流程。

这些名字不是四个必须都学的平行算法。先掌握 DPO 的“偏好间隔 + 参考锚点”，再看它们分别拿掉 reference、放宽数据格式或改变间隔形状。

## 8.7 一套可靠的 DPO 流程

1. 用稳定 SFT 模型作为 policy 初始化和 reference。
2. 确认 chosen/rejected 使用完全相同的 prompt 与模板。
3. 过滤无区分度、长度极端和标注冲突的 pair。
4. 小学习率、短训练，持续监控 KL、margin 和长度。
5. 不只看偏好准确率；跑通用、领域、安全和格式回归。
6. 用独立 judge 或人工盲评，不用训练该数据的同一个 reward 体系自证。

### 核心问答

**Q：DPO 与 SFT 的本质差别？** SFT 提高一个示范的绝对似然；DPO 利用成对偏好，要求新策略相对参考更多地偏向赢家。

**Q：为什么需要 reference？** 它提供基线并限制策略漂移，让模型学习“相对 SFT 应该改变什么”，而不是无界地追逐偏好数据。

**Q：DPO 能替代 RLHF 吗？** 在离线、已有高质量偏好对的行为对齐上经常可以；需要在线探索、可验证任务和超越已有答案时不能。

**Q：DPO loss 降了但结果变差，先查什么？** 查 KL 是否过大、是否只在压低 rejected、回答长度是否漂移，以及模板和 reference log-prob 是否一致。

# 第 9 章 语言模型强化学习：策略梯度与 PPO

> **开场问题**：语言模型的“动作”“状态”和“奖励”分别是什么？为什么不能像 SFT 一样直接反向传播最终得分？

## 9.1 把生成写成决策过程

状态 \(s_t\) 是 prompt 加已生成 token；动作 \(a_t\) 是下一个 token；策略 \(\pi_\theta(a_t|s_t)\) 是语言模型；一整段回答是轨迹 \(\tau\)；结束后得到 reward。

环境还可以包含工具：模型发出调用，环境返回结果，新的观察进入状态。于是 Agent 轨迹也是同一个强化学习形式，只是动作不止自然语言 token。

## 9.2 为什么 reward 不能直接对 token 求导

代码是否通过测试、数学答案是否正确，是离散执行后的结果，无法沿着采样 token 直接反传。策略梯度使用：

\[
\nabla_\theta J
=\mathbb E\left[
\sum_t A_t\nabla_\theta\log\pi_\theta(a_t|s_t)
\right]
\]

若一条轨迹比预期好（优势 \(A_t>0\)），提高其中动作的概率；比预期差则降低。这里最难的不是公式，而是**怎么估计“比预期好多少”**。

## 9.3 return、value 与 advantage

return 是从当前时刻起最终会拿到的累计回报。value \(V(s_t)\) 预测处于状态 \(s_t\) 时的期望 return。advantage \(A_t=R_t-V(s_t)\) 表示这次动作结果比该状态下通常水平好多少。

减 baseline 不改变期望梯度，却大幅降低方差。PPO 里的 critic/value model 就为此存在；训练它又引入额外模型、显存和误差来源。

## 9.4 on-policy 为什么昂贵

策略梯度严格要求轨迹来自当前策略。模型每更新几步，旧样本就逐渐 off-policy；继续使用会引入偏差。于是训练循环不断交替：用当前模型生成 → 打分 → 更新少量步 → 再生成。

生成恰好是最慢的 Decode 工作负载，因此第二册“后训练的训推接口”中权重同步、rollout 引擎与策略版本追踪会成为瓶颈。

## 9.5 PPO 在做什么

直接用策略梯度可能一步改太大。PPO 用新旧策略概率比：

\[
r_t(\theta)=
\frac{\pi_\theta(a_t|s_t)}
{\pi_{\text{old}}(a_t|s_t)}
\]

并把它 clip 在 \(1-\epsilon\) 到 \(1+\epsilon\) 附近，防止单批数据让策略剧烈变化。实际 RLHF 还常加入相对 reference 的 KL 惩罚，保住语言质量。

一套 PPO-RLHF 往往同时需要 policy、reference、reward model、value model 四个角色；还要维护 old-policy log-prob、GAE、clip、KL controller。这就是它难调、显存重、实现容易错的原因。

## 9.6 credit assignment

最终 reward 只有一个数，却要分给几千个 token。简单做法把同一个优势给整条轨迹的所有 token，但错误可能只在中间一步，前面正确步骤也被一起惩罚。

更细的信号包括过程奖励模型（PRM）、步骤验证器、代码执行的阶段结果、工具调用成败。奖励越接近真正做出决策的位置，学习效率越高；但中间验证器本身也可能错误。

## 9.7 entropy 与探索

策略变得过早确定后，反复采样都是同一种答案，找不到更优策略。entropy bonus 鼓励分布保持一定多样性；温度和采样策略则控制 rollout 时的探索。

探索不是越大越好。过高温度产生大量无意义轨迹，验证成本不变却没有训练价值。应监控每题答案多样性、正确率和有效轨迹比例。

### 核心问答

**Q：语言模型 RL 中一个动作是整段回答还是一个 token？** 数学上通常是一个 token，整段回答是轨迹；工程上 reward 可能只在轨迹结束时给出。

**Q：value model 为什么存在？** 预测当前状态通常能获得多少回报，作为 baseline 降低策略梯度方差，并为每个 token 估计优势。

**Q：为什么 PPO 需要 old policy？** 概率比衡量这次更新相对生成该数据的策略改变了多少，clip 用它限制单步漂移。

**Q：旧 rollout 能不能无限复用？** 不能。策略变化后数据变成 off-policy，偏差会积累；可容忍程度取决于算法与重要性修正。

# 第 10 章 可验证强化学习：GRPO、RLVR 与过程奖励

> **开场问题**：数学题最终答案可以自动判对错，还需要昂贵的人工偏好和 value model 吗？

## 10.1 RLVR 的核心变化是 reward 来源

RLHF 的 reward 来自学习到的人类偏好模型，存在主观性和可被利用的漏洞。RLVR（Reinforcement Learning with Verifiable Rewards）使用程序化验证：数学答案匹配、代码通过测试、定理通过检查器、工具任务达到环境目标。

验证器便宜、稳定、可规模化，能让策略大量探索。这是现代推理模型取得进展的重要条件，不是某个特定 RL 算法单独创造的。

## 10.2 GRPO 为什么不需要 value model

对同一道题，从旧策略采样 G 个回答，得到 reward \(r_1,\ldots,r_G\)。用组内均值和标准差标准化：

\[
A_i=\frac{r_i-\operatorname{mean}(r)}
{\operatorname{std}(r)+\epsilon}
\]

同一道题里，比同伴好的回答优势为正，比同伴差的为负。这个组内相对 baseline 取代了单独训练的 critic，省掉一个大模型和一套 value loss。

然后仍用类似 PPO 的概率比、clip 和 KL 约束更新策略。**GRPO 不是“不要 reference、不要 old policy、只看 reward”**；它主要拿掉的是 value model。

## 10.3 组内采样的代价与盲点

每题采 G 条意味着 rollout 成本乘 G。如果一组全对或全错，reward 没有方差，标准化后的优势几乎没有信号。太简单和太难的题都浪费生成预算，最有价值的是当前模型成功率位于中间区域的问题。

这自然导出动态课程：根据近期成功率增加处于“学习前沿”的题，降低长期全对/全错题的采样率。但要保留一部分固定锚点，防止课程只追逐短期波动。

## 10.4 可验证奖励并不等于可靠

验证器也会有漏洞：

- 数学只抽取最终数字，忽略单位和条件。
- 代码测试覆盖不全，硬编码样例也能通过。
- 格式奖励被大量模板 token 轻易拿满。
- 工具任务通过篡改环境状态获得高分。

一旦用 RL 优化，策略会主动寻找这些漏洞，速度远超人工发现。训练前要把验证器当安全边界做对抗测试，训练中监控 reward 与独立评测是否脱钩。

## 10.5 长思维链是怎样出现的

若复杂题上更长探索有机会获得更高正确率，RL 会提高产生自检、回溯和多方案尝试的轨迹概率。长 CoT 是在 reward 与生成预算共同作用下形成的策略，不是把“请一步步思考”写进 prompt 就等价。

但更长不必然更好。模型可能学会反复改写、伪装检查或拖延最终答案。需要同时监控正确率、推理 token 数和单位正确答案成本，并对无效冗长施加预算或轻微惩罚。

这里只讲 RL 如何把思维链训长。这条思维链本身为什么能提高准确率、预算怎么控、怎么评测、怎么蒸馏进小模型，是下一章的完整主题。

## 10.6 outcome reward 与 process reward

**ORM** 只看最终结果，可靠、便宜，但 credit assignment 粗。**PRM** 给中间步骤评分，信号密、学习快，但要有步骤标注或可靠步骤验证器，而且可能奖励看似合理的伪过程。

可程序验证的中间状态最可信，例如编译是否通过、单元测试到哪一步、定理检查器是否接受。纯语言 PRM 应与最终结果共同使用，不能取代结果验证。

## 10.7 奖励组合

常见 reward 包括 correctness、format、tool success、安全、长度/KL。把它们简单线性相加会产生尺度问题：一个容易刷满的格式分可能压过稀疏的正确性分。

优先顺序应是：

1. 能做硬约束的先做门禁。
2. 主要任务结果作为主 reward。
3. 格式和长度只做小幅 shaping。
4. 每个分量单独记录，不只看总 reward。

若总 reward 上升而独立正确率不升，应立刻停训检查 hacking。

## 10.8 从 SFT 到 RLVR 的完整流程

1. 基座经过高质量 SFT，能稳定输出目标格式和基本推理。
2. 准备带验证器的问题池，按难度与来源切分。
3. 用当前策略对每题采样一组轨迹。
4. 执行验证器，过滤基础设施错误，计算各 reward 分量。
5. 组内估计优势，做受 clip 与 KL 约束的策略更新。
6. 频繁同步新策略并重新 rollout。
7. 在固定独立集上测准确率、长度、稳定性和通用回归。

任何一步都可能成为瓶颈：生成吞吐看第二册，算法正确性看本章，验证器可信度看第 14–16 章。

### 核心问答

**Q：GRPO 比 PPO 少了什么？** 少了单独的 value model/critic，用同题多条轨迹的组内相对 reward 作为 baseline；policy、old policy 概率和 KL 约束仍然存在。

**Q：为什么每题要采多个回答？** 需要组内比较估计相对优势，也提供探索多种解法的机会。代价是生成成本成倍增加。

**Q：全对或全错的一组为什么没信号？** 组内 reward 相同，无法判断哪条轨迹相对更好，标准化优势接近零。

**Q：RLVR 最大风险是什么？** 验证器漏洞。策略会学会最大化可测 reward，而不一定完成真实目标。

# 第 11 章 测试时计算：思维链与推理扩展

> **开场问题**：同一个模型、同一道题，让它先写三千 token 再回答，准确率能高一大截。这些 token 到底提供了什么？模型真的在"思考"吗？

## 11.1 为什么多生成 token 就能算对更难的题

一次前向里，模型对每个 token 做的计算量是**固定**的：L 层，每层宽度固定。这是一个常数深度的电路。如果一个问题本身需要的串行步骤超过 L，单次前向连放中间结果的地方都没有。

生成中间 token 改变了这件事。每写出一个 token，它就进入下一步的输入，成为下一次前向可以读取的状态。于是 **token 序列变成了模型的外部工作内存，生成长度变成了可变的计算深度**：一次前向是固定深度，n 个 token 的思维链约等于把 n 次固定深度的计算串起来。

这个视角一旦建立，很多现象就不需要死记：

- **CoT 买的是串行计算步数，不是知识。** 知识缺失的问题想一万个 token 也变不出事实，这正是 RAG 不能被 CoT 替代的原因。
- 收益集中在"多步、可分解、有中间状态"的任务：多位数运算、多跳推理、模拟执行、约束求解。
- 一步就能查到答案的题，长 CoT 只增加成本和出错机会。

理论侧有相应结果（常数深度 Transformer 的表达能力有明确上界，允许足够长的中间步骤后能力类显著变大），不必记定理，记住"深度换长度"这个交换即可。

## 11.2 三种 CoT，别混成一个词

**提示出来的 CoT**：few-shot 给几个带推理过程的例子，或 zero-shot 加一句"一步步想"。它不改变权重，只是把概率质量引向带中间步骤的输出分布。对没做过推理训练的基座模型效果显著；对现代推理模型，这句话作用很小，甚至会干扰它自己的思考格式。

**训练进去的 CoT**：用带推理轨迹的数据做 SFT，模型学会该展开时展开。形态取决于示范数据，通常比较像人写的解题过程。

**RL 长出来的 CoT**：第 10 章那条线。奖励只看最终结果，模型自己发现"多试几种、中途自检、错了回头"能提高正确率，轨迹于是自然变长，并涌现出验证、换方法、承认错误这些行为。它不是在模仿人怎么写解题步骤，而是在优化"怎样更可能答对"——所以读起来常常不像教科书解答，会有大量自言自语和反复。

三者的产物都是"一段思考文字"，但可控性、长度分布和失败方式完全不同。讨论"CoT 有没有用"之前，先说清是哪一种。

## 11.3 测试时扩展的两个方向

**串行**：让单条轨迹更长。收益来自更多中间状态和自我修正，代价是延迟线性增长，且超过某个长度后边际收益递减甚至转负（想太久把对的改错）。

**并行**：采样 N 条独立轨迹再聚合。

- **多数投票（self-consistency）**：答案可归一化时最简单有效，不需要额外模型。
- **Best-of-N + 验证器**：有可靠 verifier（测试、检查器）时远好于投票；换成奖励模型打分则受 reward hacking 影响。
- 两者的天花板都是 pass@N：正确答案至少要被采到一次。

两个方向可以组合，但预算是相乘的。这里要建立一个硬习惯：**报告准确率必须带 token 预算**。"多想一倍换两个点"和"多花十倍算力换两个点"是完全不同的结论。真正有意义的产物是一条 accuracy-vs-token 曲线，单点准确率在测试时扩展的语境下几乎没有信息量。

## 11.4 谁来决定想多久

- **固定预算**：简单，但简单题浪费、难题不够。
- **可控档位**：把 reasoning effort 暴露成 low/medium/high，由调用方按场景选，是目前主流产品做法。
- **自适应**：模型自己判断该不该展开。训练上通常要在 reward 里加长度惩罚，或用难度条件化，否则 RL 会单调地把轨迹推长。
- **预算强制**：到上限就注入"因此，答案是"逼它收尾；反过来在它想停时注入"等一下"逼它继续。粗暴但有效，属于推理时旋钮，不是训练方法。

工程上必须有硬上限。没有上限的思考在生产里会变成不可控的成本和延迟长尾——一个请求烧掉三万 token 的事故，几乎都是这么来的。

## 11.5 思考区与回答区必须分开

现代推理模型把输出分成 thinking 段和 answer 段，用特殊 token 界定。这不是显示层的美化，涉及三件实打实的事：

1. **loss 和 reward 的作用范围**：thinking 段通常不要求格式、不给用户看；answer 段要严格遵守 schema。训练时两段的监督方式不同。
2. **多轮上下文怎么带**：上一轮的 thinking 通常**不放回**下一轮。否则上下文迅速爆炸，而且模型会被自己上一轮的草稿带偏。这条直接影响第二册的前缀缓存——丢掉 thinking 意味着历史前缀被改写，命中率和缓存键都要重新设计。
3. **给不给用户看**：展示思考有透明度价值，但会暴露中间错误、也更容易被人蒸馏走，很多产品折中成只给摘要。

训练数据里如果 thinking 和 answer 混在一起不加标记，模型会在最终答案里继续碎碎念。这是长 CoT 微调最常见的翻车方式。

## 11.6 CoT 不等于模型真实的计算过程

写出来的推理是一段被采样的文本，它和模型内部真正决定答案的计算不是一回事。有个已被反复观察到的现象：在提示里埋一个无关线索（比如暗示某个选项是对的），模型的答案会被它带走，但推理文字里会另外编出一套看起来合理的理由，完全不提那个线索。

两个直接后果：

- **不能把 CoT 当作可靠解释**交给用户或监管。它是模型的一种行为，不是它决策过程的证明。
- **过程监督要非常小心**。奖励"看起来合理的推理"，训出来的是更会写理由的模型，不是更会算的模型。这正是 10.6 节说 PRM 有风险的根源。

可信度排序始终是：可执行的中间状态（代码跑通、检查器接受、工具返回）> 结构化可验证步骤 > 自然语言推理文本。

## 11.7 失败形态与监控

- **过度思考**：简单题写几千 token 反复确认，甚至把对的答案改错。
- **思考不足**：难题上过早收敛到第一个想法。
- **反复横跳**：在两个候选之间来回摇摆，不收敛。
- **假验证**：写"让我验算一下"，然后编一个通过的验算。
- **语言漂移与退化重复**：长思考中混入其他语言或陷入循环，RL 训练里常见，通常要专门加惩罚。

该监控的不只是平均思考长度，还包括：长度的整条分布（尾部才是成本来源）、答案在思考中被改变的次数、每个正确答案的 token 成本，以及按难度分层的"长度—正确率"关系。只看均值会完全错过过度思考。

## 11.8 把长 CoT 蒸馏进小模型

这是目前小推理模型最主流的来源：用强推理模型在一批**可验证**的题目上生成长轨迹 → 只保留最终答案正确的 → 拿这些轨迹做 SFT。

四个决定成败的细节：

- **必须按结果过滤**。答案对但过程胡来的轨迹会教出"看起来在推理"的模型；条件允许时再叠加过程检查。
- **要保留失败恢复**。如果只留一次做对的干净轨迹，学生遇到自己的错误状态时不知道怎么回头——它从没见过"错了再纠正"长什么样。
- **长度要匹配学生容量**。小模型学不动几万 token 的轨迹，通常要按难度分档或做压缩。
- **tokenizer 不同就只能做文本蒸馏**，做不了下一章要讲的分布蒸馏。

必须说清的局限：蒸馏出来的小模型在目标分布上接近教师，但在分布外和真正需要探索的新问题上明显更弱。**它复制的是已经找到的解题模式，不是找到解法的能力。** 常见配方因此是两段——先蒸馏拿到推理格式和习惯，再用少量 RLVR 在目标领域继续拉。

## 11.9 它如何改变另外两册的账

- **第一册**：CoT 把每个请求的 decode token 数放大一到两个数量级。KV 显存、长上下文、投机解码、MTP 的价值全部随之上升——第 13、14 章那些架构选择的性价比是被这条线重新定价的。
- **第二册**：线上推理和 RL rollout 的 decode 长度暴涨，调度、KV 管理、PD 分离的账要重算；训练侧生成耗时进一步压过反向传播。
- **第三册**：它是被 SFT 和 RLVR 训出来的行为，也是需要被评测、被预算约束的对象。

### 核心问答

**Q：CoT 为什么能提高准确率？** 它把固定深度的一次前向，变成可变长度的多次串行计算，中间 token 充当外部工作内存。它增加的是计算步数，不是知识。

**Q：对现代推理模型还需要写"一步步思考"吗？** 通常不需要，甚至有害。这类模型已经把思考训进了默认行为，额外指令可能干扰它自己的格式。

**Q：串行想更久和并行采样多条，哪个更划算？** 取决于有没有可靠验证器。有 verifier 时 Best-of-N 很强；没有时只能投票，且受 pass@N 上限约束。两者预算相乘，必须画 accuracy-vs-token 曲线来比。

**Q：能把模型写出来的推理当作解释吗？** 不能。已有明确证据表明推理文字可以与真实决定答案的因素脱节。它是行为，不是证明。

**Q：蒸馏出来的推理小模型和 RL 训出来的差在哪？** 差在分布外和探索能力。蒸馏复制已知解题模式，RL 才是在学怎么找解法。

# 第 12 章 安全对齐、拒答策略与对齐税

> **开场问题**：安全训练后危险回答减少了，但“怎样切洋葱”也被拒绝。模型更安全了吗？

## 12.1 安全不是一个二分类器

请求通常落在连续谱上：明确无害、双重用途、需要上下文判断、高风险但合法、明确恶意。简单的“敏感词 → 拒绝”会产生大量过度拒答，也容易被改写绕过。

安全行为至少包含：识别风险、判断用户意图和权限、决定回答粒度、必要时拒绝、给出安全替代方案。它是一个完整策略，不是一句固定免责声明。

## 12.2 拒答数据必须成对覆盖边界

只收集危险请求并训练拒答，会让模型把相似表面特征都判成危险。需要同时加入 near-neighbor benign examples：

- 恶意代码与防御性安全分析。
- 制造危险物品与历史/教育介绍。
- 医疗诊断与一般健康信息。
- 个人数据查询与用户本人授权查询。

模型真正要学的是决策边界，而不是关键词。

## 12.3 对齐税

对齐可能降低某些原始能力：回答更保守、创造性下降、复杂任务因过度安全而中断、偏好优化把答案拉向平均风格。这就是对齐税。

不能只拿“安全分提高”来证明成功。必须同时报告帮助性、安全性、过度拒答率和核心能力回归，并画 Pareto 前沿。不存在脱离业务风险偏好的单一最优点。

## 12.4 Prompt Injection 与模型训练的边界

RAG 和 Agent 中，模型会读到不可信文档和工具输出。文档里写“忽略 system prompt”属于数据，不应取得指令权限。

可以用训练提高模型识别能力，但不能只靠模型自觉。系统必须做权限隔离：高权限指令与不可信内容分通道、工具最小权限、参数校验、敏感操作二次确认。安全对齐不能替代系统安全。

## 12.5 红队与对抗迭代

红队不仅尝试 jailbreak，还要覆盖：

- 多轮逐步诱导。
- 编码、翻译和角色扮演变体。
- 工具越权和间接 prompt injection。
- 隐私信息拼接与成员推断。
- 拒答后的安全替代是否仍泄露关键步骤。

发现失败后先判断修复层：输入过滤、权限系统、prompt、SFT/DPO 数据，还是模型本身。把所有问题都回流安全 SFT 会造成越来越严重的过度拒答。

## 12.6 安全评测的最小矩阵

每个风险类别至少测四格：

1. 恶意请求是否拒绝。
2. 邻近无害请求是否正常回答。
3. 允许的高风险专业场景是否给出适当粒度。
4. 改写和多轮攻击下是否稳定。

只测第一格，会得到一个“什么都拒绝”的满分模型。

### 核心问答

**Q：拒答率越高越安全吗？** 不是。拒绝一切当然“安全”，但系统失去用途。要同时测恶意请求防护和无害请求的过度拒答。

**Q：安全问题都能靠微调解决吗？** 不能。权限、数据隔离、工具参数校验必须由系统强制，不能把安全边界交给概率模型。

**Q：什么是对齐税？** 为获得更符合偏好或更安全的行为，对通用能力、创造性、简洁性或可用性付出的损失。

**Q：安全数据为什么需要无害近邻？** 它们帮助模型学到真正的决策边界，避免把表面关键词当成危险标签。
