# 第一部分 目标，数据与评测

**目的**：训练之前先回答三个问题：到底要改变哪种行为，什么样的样本能提供这种信号，怎样证明改变来自泛化而不是记住了测试题。

---

# 第 1 章 后训练地图

> **开场问题**：模型不会回答公司内部问题，究竟该做 RAG，继续预训练，SFT，还是 DPO？

## 1.1 先分清四个经常混在一起的目标

**知识**是模型是否知道某个事实；**能力**是能否完成推理，编程，抽取等过程；**行为**是它是否按指令，格式，语气和安全边界输出；**系统能力**是模型配合检索，工具和外部状态后能完成什么。

四者的解法不同：

- 缺少会变化的私有知识，优先 RAG；把每天变化的库存训进权重是错误方向。
- 不会稳定执行某类任务，先用高质量示范做 SFT。
- 已经会做，但答案风格，帮助性或安全边界不理想，用偏好优化。
- 结果可自动验证且需要探索更好的解题策略，才进入 RLVR。
- 单次回答做不到，必须调用外部系统或跨多步完成，用工具和 Agent。

“模型效果不好”不是可执行的诊断。必须先把问题归到上述一类，才知道训练信号该长什么样。

## 1.2 改上下文，改部分权重，改全部权重

最轻的办法是改上下文：system prompt，few-shot，检索内容，工具描述。优点是立刻生效，容易回滚，知识可更新；缺点是每次请求都占 token，复杂规则容易互相冲突，模型的底层能力没有改变。

LoRA 等 PEFT 方法只训练很小的增量权重。它适合稳定的任务格式，领域风格和中等规模数据；容易保存多个适配器，也容易做 A/B。它不是“效果较差的全量微调”，而是在低成本与可插拔之间做出的结构化选择。

全量更新适合需要深度改变能力分布，数据量足，预算高的场景。代价不仅是训练贵，更是旧能力更容易遗忘，评测范围必须更广。

一个实用原则：**从最轻，最容易验证和回滚的方法开始**。Prompt 能解决就不要上 SFT，RAG 能解决动态知识就不要继续预训练，SFT 能稳定行为就不要直接上 RL。

## 1.3 后训练不是“把答案塞进去”

模型训练仍然是在调整条件概率分布。SFT 提高示范答案中 token 的概率；DPO 拉大偏好答案和拒绝答案的相对概率；RL 根据整条轨迹的回报改变策略。

因此一条样本不是一条数据库记录。它同时影响相似上下文中的一片行为区域，可能带来迁移，也可能伤害无关能力。后训练的核心困难正是：**用有限样本改变目标区域，同时尽量不扰动其他区域。**

## 1.4 基座模型，指令模型和推理模型

基座模型只学续写互联网文本，不天然理解“system/user/assistant”这些角色；指令模型经过对话 SFT 与偏好对齐，学会把用户内容当任务；推理模型又经过带长推理轨迹的数据和 RLVR，学会分配更多生成计算解决可验证问题。

三者不能混用同一套训练假设。给基座模型直接做少量 DPO，模型可能连稳定的对话格式都没有；给已经高度对齐的 instruct 模型继续做窄领域 SFT，可能很快过拟合语气并遗忘通用指令遵循。

## 1.5 第三册与第二册在哪里接上

第三册决定：样本怎么构造，loss 怎么定义，reward 怎么算，旧轨迹能不能用。第二册决定：这些计算怎样分布到 GPU，rollout 如何高吞吐生成，权重如何同步。

例如 RLVR 中“每道题采样 16 个回答”是算法决策；这 16 个回答怎样连续批处理，KV 如何管理，是推理系统决策。二者必须协同，但不要混为一章。

### 核心问答

**Q：企业知识问答应该先微调还是先 RAG？** 若知识频繁更新，需要引用和可追溯，先 RAG。微调更适合教会回答方式，术语风格和稳定任务流程，不适合充当可更新数据库。

**Q：LoRA 能提升模型上限吗？** 能在目标分布上显著提升，但受基座能力约束。基座完全不会的复杂能力，仅靠很小规模 LoRA 很难凭空创造。

**Q：什么时候值得做 RL？** 任务有可靠奖励或验证器，SFT 已让模型具备基本行为，且需要通过探索发现比示范更好的策略时。

**Q：Agent 属于改模型吗？** 它通常不改权重，却改变模型所处的观察—行动循环，因此能改变系统行为上限。第三册讨论的是“改成你的”，不仅是“改参数”。

# 第 2 章 任务规格与基线

> **开场问题**：“让客服模型更专业，更准确”为什么无法直接变成训练项目？

## 2.1 先写输入输出契约

任务定义至少包含：

1. 输入由哪些字段组成，哪些字段可信，最长多长。
2. 输出是自然语言，JSON，标签还是工具调用。
3. 哪些信息必须出现，哪些绝不能出现。
4. 不确定，缺资料，权限不足时应该怎么做。
5. 延迟，成本和可解释性约束。

“专业”必须被拆成可观察行为，例如：引用给定文档，不编造政策，先给结论再解释，涉及退款必须调用订单工具，没有证据时明确说不知道。

## 2.2 成功标准必须包含反例

只列正向能力会制造一个永远能刷分的系统。每条行为规格都要同时写：

- 正例：什么情况下应该做。
- 反例：看起来相似但不该做的情况。
- 边界例：信息不足，输入矛盾，超出权限时怎么办。
- 对抗例：用户试图绕过 system 指令或诱导泄露时怎么办。

例如“主动调用搜索工具”不能只测该调用时是否调用，还要测常识问题是否乱调用，工具不可用时是否降级，检索结果冲突时是否承认不确定。

## 2.3 建立失败分类，而不是堆一袋错题

一个可用的分类法：

- **知识缺失**：没有相关事实或事实过时。
- **理解错误**：误解用户意图，指代或约束。
- **推理错误**：中间步骤错误，条件遗漏。
- **指令错误**：知道答案但没遵循格式，语气或优先级。
- **工具错误**：选错工具，参数错，忽略返回结果。
- **安全错误**：泄露，越权，危险指导或过度拒答。
- **系统错误**：截断，检索失败，解析器失败，超时。

分类的价值是决定修法。知识缺失去补检索或数据；格式错误做 SFT 或约束解码；工具参数错误补轨迹示范；系统超时不能拿训练数据修。

## 2.4 基线不是“原模型跑一下”

至少保留三条基线：

- **零改动基线**：原模型 + 最小 prompt。
- **强 Prompt/RAG 基线**：先证明不训练能到哪里。
- **可实现的上界**：人工答案，强教师模型或带正确工具结果的 oracle。

若强 Prompt 已达到上界的 98%，训练项目可能没有经济价值；若 oracle 也只有 70%，问题可能在数据或任务定义，不在模型。

## 2.5 训练集，开发集，测试集怎样切

不能随机把高度相似的样本打散。客服同一政策的不同改写，代码仓库中同一函数的多个版本，同一文档切出的片段，都应按来源分组后整体切分，否则测试集只是训练样本的近邻。

时间敏感任务应按时间切：过去数据训练，未来数据测试。用户个性化任务按用户切；代码任务按仓库切；多轮会话按完整会话切。切分单位必须对应你真正想泛化的单位。

## 2.6 指标要分层

**硬指标**适合自动判断：JSON 是否可解析，字段是否齐全，答案是否等于标准值，代码是否通过测试，工具调用是否成功。

**软指标**需要 rubric 或人工判断：帮助性，论证质量，语气，是否充分利用证据。

**系统指标**包括延迟，token 成本，调用次数和失败率。一个准确率提高 1%，但平均多调用五次工具的 Agent，未必更好。

最终不能只有一个总分。应保留能力切片和安全门禁：总分上涨不能掩盖某个高风险切片从 99% 跌到 90%。

### 核心问答

**Q：为什么不能先收数据再定义指标？** 因为数据会自然偏向“容易找到和标注的东西”，而不是业务真正重视的失败。指标先行才能决定该采什么。

**Q：随机切分有什么问题？** 相似样本会泄漏到测试集，得到的是近邻记忆能力，不是真实泛化能力。

**Q：一个综合分数为什么危险？** 权重可以掩盖硬性退化。安全，权限，结构化输出等必须设独立门槛，不允许被其他能力补偿。

**Q：什么时候应该停止训练项目？** 当强 Prompt/RAG 已接近上界，或上界本身很低且瓶颈在数据/流程时。

# 第 3 章 数据工程

> **开场问题**：十万条自动生成指令，为什么可能不如两千条认真整理的失败样本？

## 3.1 不同训练方法需要不同的数据单元

SFT 样本是“上下文 → 理想回答”；偏好样本是“同一上下文 → chosen 与 rejected”；奖励模型样本还可以是多答案排序或逐项评分；RLVR 只需要题目和可靠验证器，回答由当前策略在线生成；Agent 数据是一整条包含观察，思考，工具调用，工具结果和最终答案的轨迹。

把一种数据强行转成另一种会丢信息。例如只有最终正确答案的数学题可以做 SFT，但没有过程监督时无法告诉模型哪一步出了错；只有点赞/点踩日志做 DPO，往往混入答案质量之外的长度，语气和用户情绪。

## 3.2 质量不是“看起来像人写的”

一条训练样本至少检查：

- **正确**：事实，推理，代码和工具结果是否可验证。
- **相关**：是否对应目标分布，而不是泛泛的通用问答。
- **有区分度**：是否提供了基座当前不会的信号；模型本来就 99% 会的数据价值很低。
- **一致**：同类问题的规则，格式和安全边界是否互相矛盾。
- **可学习**：输入里是否包含得出目标答案所需的信息。

最后一条经常被忽略。输入缺少关键上下文，标注员凭内部知识写出正确答案，模型只能学会猜或背。

## 3.3 数据来源与各自偏差

人工专家数据质量高，贵，规模小，并且专家常省略他们认为显然的步骤。真实日志贴近分布，但包含隐私，旧系统行为和未被发现的错误。教师模型生成便宜，覆盖广，却会复制教师偏差和语言风格。规则合成可精确控制难度，但容易模板化。

好的数据集通常混合来源，并给每条样本记录 provenance：来自哪个日志，哪个模型版本，什么生成 prompt，经过哪些过滤，谁审核过。没有来源记录的数据，后续发现问题时无法撤回。

## 3.4 去重不是删除完全相同的字符串

至少有三层：

- 精确去重：哈希文本，去掉完全重复。
- 近似去重：MinHash，SimHash 或 embedding 相似度，识别改写和模板填充。
- 语义/来源去重：同一文档，同一题库家族，同一代码仓库即使文本不同，也可能构成泄漏。

训练集内部重复会改变样本权重，让高频模板支配模型风格；训练—测试重复会制造虚假能力。两种危害不同，都要处理。

## 3.5 数据配比就是隐式目标函数

训练时每种数据出现多少次，就等价于给这种行为多大权重。一个领域数据集里 60% 是摘要，模型最终最明显的提升大概率也是摘要，即使产品真正关心的是少量复杂问答。

不能只按“自然数量”混合，要按能力目标设计采样率。还要监控 token 占比而非样本占比：一条长推理轨迹可能等于几十条短问答。

常见策略是分阶段 curriculum：先用高质量通用指令稳定格式，再加入领域任务；难度从短，可验证任务逐步增加到长，多步任务。但 curriculum 不是必然更好，必须通过开发集验证。

## 3.6 难例挖掘比盲目扩量更有效

让当前模型跑真实或合成任务，把失败按第 1 章分类，再补针对性样本，这就是 error-driven data flywheel。

真正有价值的不只是“答错的题”，还包括：

- 模型置信很高但答错。
- 多次采样结果不一致。
- 基座答错而更强教师答对。
- 对一个无关表述变化极度敏感。
- 已知高风险边界的近邻样本。

这类样本提供的信息密度远高于随机生成十万条简单题。

## 3.7 数据污染，隐私与许可

训练前要做 PII 检测和脱敏，尤其是真实会话日志；需要保存用户同意和数据保留策略。版权与许可不能因为数据“在网上公开”就跳过。安全数据还要防止把危险内容连同详细执行步骤直接教给模型。

测试集必须像密钥一样隔离。不要把完整测试集交给生成训练数据的教师模型，不要让调参人员反复浏览测试答案，更不要把线上回归失败自动回流训练而不先检查它是否来自评测集。

## 3.8 数据版本要能重建

数据集不是一个最终 JSONL，而是一条可重放流水线：原始来源 → 清洗 → 去重 → 过滤 → 生成/增强 → 审核 → 切分 → 模板化。

每一步都要有版本，配置和统计报告。模型实验记录的是这条流水线的版本，而不是“data_v7_final_final.jsonl”。

### 核心问答

**Q：高质量小数据为什么可能胜过大数据？** 后训练目标是移动已有模型的行为分布，不是从零学语言。高区分度，规则一致的数据提供的有效梯度更强；大量简单重复样本只会放大风格和模板。

**Q：合成数据最大风险是什么？** 不只是事实错误，而是分布坍缩：模型反复学习同一种教师语言，解法和偏好，覆盖面越来越窄。

**Q：应该按样本数还是 token 数配比？** 训练成本和 loss 都发生在 token 上，所以至少要看 token 占比。长推理数据会在样本数看似很少时占据大部分梯度。

**Q：线上失败都应该回流训练吗？** 不。先分类：系统错误修系统，知识更新进 RAG，稳定行为缺陷才进入训练；还要排除隐私和评测集污染。

# 第 4 章 评测底盘

**目的**：评测不是训练完成后的汇报步骤，而是整个后训练项目的控制系统。本部分把“跑题库”升级为可复现的 harness，可信的 judge 和持续回归闭环。

---

## 大模型评测方法与指标体系

> **开场问题**：模型在公开榜单涨了 5 分，真实用户为什么没有感觉，甚至投诉更多？

## 4.1 先建能力矩阵

横轴是任务/能力：知识问答，抽取，代码，数学，工具调用，长上下文，安全等；纵轴是难度，语言，输入长度，用户类型，领域，风险等级。

每个格子明确：样本数，数据来源，指标，门槛和业务权重。公开 benchmark 只覆盖其中少数格子，主要作用是和外部模型建立共同坐标；内部评测才决定是否能上线。

## 4.2 生成配置是评测的一部分

temperature，top-p，max tokens，停止词，是否展示思考，对话模板都会改变结果。贪心解码测稳定能力，采样测分布和 pass@k；两者回答不同问题。

比较模型时必须固定配置，或者为每个模型使用其官方推荐模板并明确说明。把 instruct 模型套错 chat template 再比较，是常见但严重的不公平。

## 4.3 确定性任务与生成式任务

选择题，数值题，代码测试可以自动判分，但解析器必须稳健：模型输出“答案是 (C)”不能因为不等于字符串“C”就判错；同时不能用过宽正则从一段矛盾文本里捞出碰巧正确的字母。

开放回答没有唯一字符串，需要：

- 基于事实单元的匹配。
- rubric 分项评分。
- 成对比较。
- 人工专家评审。

指标越自动，规模越大；判断越细，成本和噪声越高。可靠方案通常分层：全量自动评测 + 小规模高质量人工复核。

## 4.4 pass@k 与采样预算

代码和数学常报告 pass@k：采样 k 次，至少一次正确的概率。它衡量模型是否“有能力偶尔找到答案”，不等于单次产品体验。

必须同时报告 pass@1，采样温度和总 token 预算。通过把 k 从 1 提到 100 获得高分，实际成本可能不可接受。对推理模型更应报告 accuracy-token Pareto：多想一倍是否真的值。

## 4.5 均值会隐藏什么

总体 80% 可能由简单题 95%，关键高风险题 40% 组成。必须做切片，并报告每个切片置信区间。

两个模型只差 0.5 分时，先问是否超过评测噪声。对同一批题的成对 bootstrap 比较比独立均值更有力；judge 评测还要考虑判官自身随机性。

## 4.6 离线和线上为什么会不一致

离线集固定，干净，通常是单轮；线上输入会漂移，信息不完整，多轮依赖，带恶意内容，还受检索与工具故障影响。

上线后要看任务成功，重试，用户改写，人工接管，投诉，token 成本和延迟，而不只是点赞率。点赞有强选择偏差：只有部分用户愿意点，且常受语气和速度影响。

### 核心问答

**Q：公开榜单还有价值吗？** 有，适合外部坐标和通用回归；不能替代贴近业务分布，带真实约束的内部评测。

**Q：为什么温度必须记录？** 它改变输出分布和 pass@k。不同温度下的单次准确率不可直接比较。

**Q：选择题为什么也会评错？** 模型输出格式多样，解析器过严会误杀，过宽会从矛盾文本中捞答案。解析协议必须单测。

**Q：线上点赞能当最终指标吗？** 不能单独用。它受用户选择，语气，速度和幸存者偏差影响，应与任务成功和人工抽检结合。

## 可复现评测系统：Evaluation Harness

> **开场问题**：同一个模型，同一个 benchmark，两个团队为什么能跑出相差 8 分的结果？

## 4.7 harness 是实验协议，不只是脚本

一项任务应被封装为：

1. 数据加载和版本。
2. prompt/chat template 构造。
3. 生成参数。
4. 输出解析。
5. 评分函数。
6. 聚合和置信区间。
7. 缓存，日志和可重放记录。

只有数据集名称相同远远不够。few-shot 示例，答案顺序，system prompt，是否要求 CoT 都能带来数分差异。

## 4.8 Task，Document，Request，Metric

一个清晰的 harness 把原始样本 Document 转成一个或多个 Request：生成文本，计算候选 log-likelihood，调用工具或运行 Agent 环境。模型产生 Response，再由 Metric 聚合。

分层的好处是同一任务可切换本地模型，API 模型和不同后端；评分逻辑不依赖执行方式。任务协议一旦和某个 SDK 写死，后续很难复现。

## 4.9 log-likelihood 与 generation

多选题可比较每个候选的条件 log-likelihood，不必真的生成；这种方法稳定，便宜，但长度不同的候选要考虑归一化。真实产品是生成答案，因此还应补 generation 评测，测试格式遵循和解释能力。

两种设置回答不同问题，不应拿 likelihood 结果冒充端到端生成效果。

## 4.10 缓存与可重放

模型调用昂贵，应按“模型制品哈希 + 模板版本 + 生成参数 + 输入”缓存原始响应。**缓存原始输出，不只缓存分数**，这样解析器或评分规则更新时不必重新推理。

每条结果要能追溯到完整请求和响应。只保留总分会让错误分析和 judge 复核无从进行。

## 4.11 并发，重试与 API 评测

外部 API 会限流，超时和返回瞬时错误。重试必须区分幂等错误与内容错误；不能因为解析失败就重新采样到一个能过解析的答案，这会暗中把 pass@1 变成 pass@k。

记录实际重试次数，模型版本和服务端可能变化的日期。闭源模型名称相同也可能滚动更新，结果无法永久复现。

## 4.12 Agent harness 为什么更难

普通评测是 prompt → response；Agent 评测是策略与环境多轮交互。harness 还要固定：

- 初始环境快照。
- 可用工具和权限。
- 每步观察格式。
- 最大步数，token 和时间预算。
- 环境状态转移。
- 成功判定和副作用清理。

若环境不确定，同一 Agent 的分数波动可能来自网页变化或服务故障，而不是模型。需要容器，模拟器或可重置 sandbox。

## 4.13 一个最小结果记录

每条样本至少保存：

- task/sample ID 与数据版本。
- 完整渲染 prompt/messages。
- 原始输出或完整轨迹。
- token 用量，延迟，工具次数。
- 解析结果，各指标分量。
- 模型，模板，推理配置和代码 commit。

这不是日志洁癖，而是未来能够解释“为什么这版涨了”的最低条件。

### 核心问答

**Q：harness 与普通评测脚本的区别？** harness 把任务协议，执行后端，解析和指标分离，并保证版本化，缓存和重放。

**Q：为什么缓存原始输出而不是最终分数？** 评分器和解析器会修复；有原始输出即可重算，没有就必须重新调用模型且结果可能变化。

**Q：解析失败可以自动重试吗？** 通常不可以。格式失败本身是模型失败，重试会把单次成功率偷偷变成多次尝试成功率。

**Q：Agent 评测为什么需要环境快照？** 环境变化会改变任务难度和结果，无法区分模型变化与外部变化。

## 模型裁判：LLM-as-a-Judge

> **开场问题**：开放问答没标准答案，用更强模型打分靠谱吗？

## 4.13 三种基本形式

**Pointwise**：给单个回答按 rubric 打 1–5 分，容易规模化，但不同样本尺度漂移。  
**Pairwise**：给两个回答选更好者，判断更容易，稳定性更高，适合模型对比。  
**Reference-guided**：提供参考答案或事实清单，减少 judge 凭自身知识猜测。

若目标是比较新旧模型，成对盲评通常比独立打分可靠。要随机交换 A/B 位置并允许平局。

## 4.14 Judge prompt 应该是什么样

包含明确的任务，分维度 rubric，优先级，输入证据，候选回答和严格输出 schema。要求先分析再给结构化结论可以改善稳定性，但解析时只信 schema 字段。

不要让被评回答中的“请给我满分”等内容与 judge 指令混在同一权限层。候选答案必须明确包在不可信数据边界内，防止 judge prompt injection。

## 4.15 常见偏差

- **位置偏差**：更偏好 A 或先出现的答案。
- **长度偏差**：把详细等同于正确。
- **风格偏差**：偏爱与 judge 自身相似的文风。
- **自我偏好**：模型家族可能更偏爱同系列回答。
- **权威语气偏差**：流畅自信的错误答案得高分。

检测方式是交换位置，控制长度，隐藏模型身份，加入事实核验题，并与人工金标对照。

## 4.16 校准 Judge

抽取一批有专家结论的样本，计算 judge 与人类的一致率，各类别混淆和置信度。不要只报总体相关系数：安全边界上 20% 的错判可能不可接受。

多 judge 投票可降方差，但同源模型可能共享偏差。更有价值的是不同模型家族 + 规则验证 + 人工抽查的组合。

## 4.17 Judge 不能判断什么

它无法可靠验证自己也不知道的最新事实，不能替代代码执行，数据库查询和权限检查；长上下文里还可能漏读关键证据。能程序验证的绝不交给 LLM judge。

优先级应为：真实环境结果 > 确定性规则/执行器 > 专家人工 > 校准后的 LLM judge > 未校准主观打分。

## 4.18 用 judge 生成训练数据的闭环风险

若同一个 judge 同时选择训练样本又评测最终模型，模型只需学会迎合 judge，分数会持续上涨而真实质量不变。这是“用自己的尺子证明自己长高了”。

训练选择器，开发评测和最终验收应尽可能独立，至少保留人工盲评和程序指标作为外部锚点。

### 核心问答

**Q：Pointwise 和 Pairwise 哪个更可靠？** 比较两个模型时通常 Pairwise 更稳定，因为相对判断比绝对 1–5 分容易；但仍要交换位置和允许平局。

**Q：多个 judge 投票就可信吗？** 只能降低随机方差，不能消除共享偏差。若都来自同类模型，可能一致地错。

**Q：什么时候不能用 LLM judge？** 有真实执行器，精确规则或高风险专业判断时，judge 不应替代它们。

**Q：为什么训练和评测不能用同一个 judge？** 模型会优化这个 judge 的偏好和漏洞，形成测量闭环，分数不再代表外部质量。

## 数据污染，能力回归与迭代闭环

> **开场问题**：模型在测试集上接近满分，怎样判断它是真会了，还是见过题？

## 4.19 污染有多个层次

- **精确污染**：训练中出现相同题目和答案。
- **近似污染**：改写，翻译，选项重排。
- **来源污染**：同一题库，代码仓库或文档的其他版本。
- **评测感知优化**：团队反复针对测试集修数据，即使样本没直接进训练，也已把测试集当开发集。

最后一种最普遍。测试集一旦被反复查看和用于决策，就不再是真正测试集，需要新的密封集。

## 4.20 怎么检测记忆而非泛化

做语义等价变换：改变量名，数字，实体，选项顺序，叙述风格，保持底层规则不变。若原题正确，变体大量失败，很可能依赖表面记忆。

代码评测按仓库切分并生成新测试；数学题参数化重采样；知识题使用发布日之后的事实。没有单一检测器能证明“绝无污染”，只能通过多种设计降低概率。

## 4.21 回归集要固定，探索集要流动

**回归集**保存历史上重要且已修复的失败，确保它们不再复发；**探索集**持续加入新分布和新攻击，发现未知问题。

回归集会逐渐被团队熟悉，不能承担泛化评测；探索集不稳定，不能用于精确比较历史版本。两者必须分开。

## 4.22 从失败到数据的闭环

1. 收集失败及完整上下文。
2. 确认能稳定复现。
3. 分类根因：模型，数据，prompt，检索，工具还是系统。
4. 选择最轻修法。
5. 构造正例，反例和边界近邻。
6. 放入训练/开发集；另留同类未见变体做测试。
7. 跑全量回归，确认没有挤坏别处。

“把失败答案改正确后直接加入训练”只完成了第 5 步的一小部分。

## 4.23 实验卡片与因果归因

一次实验只能有清晰的主要变量。若同时换数据，模板，学习率，基座和 judge，分数涨了也不知道为什么。

实验卡片记录：假设，变更，数据差异，训练配置，推理配置，结果，失败切片和结论。失败实验也必须保存，它们定义了已知无效区域，避免团队重复烧钱。

## 4.24 上线门禁

建议四层：

1. 确定性单测：模板，解析，工具 schema，停止条件。
2. 小型快速回归：每次提交运行。
3. 完整离线评测：候选权重或系统版本运行。
4. shadow/canary：真实流量中逐步验证。

高风险切片使用 hard gate，不允许总分补偿。任何自动 judge 的提升都不能绕过关键人工样本。

## 4.25 何时停止继续优化

当新增训练主要在测试噪声内波动，每个提升带来越来越大成本，或领域提升持续挤压关键通用能力时，应停止改权重，转向系统约束或接受边界。

成熟的模型开发不是把所有错误消灭，而是知道剩余错误是什么，概率多大，怎样被系统检测和兜底。

### 核心问答

**Q：去重能完全解决污染吗？** 不能。近似改写，同源数据和评测感知优化无法靠字符串去重彻底识别。

**Q：为什么已修复错题不能直接充当最终测试？** 团队已经围绕它做过决策，它现在是回归集。最终测试要用同类但未见的新变体。

**Q：一次实验为什么尽量只改一个主要变量？** 为了归因。不能解释提升来源的实验，无法稳定复现也无法指导下一步。

**Q：什么才算迭代闭环完成？** 不只是当前错题答对，还要同类未见变体提升，旧能力不退化，线上指标改善且成本可接受。
