# 第四部分 模型评测与迭代体系

**目的**：评测不是训练完成后的汇报步骤，而是整个后训练项目的控制系统。本部分把“跑题库”升级为可复现的 harness、可信的 judge 和持续回归闭环。

---

# 第 13 章 大模型评测方法与指标体系

> **开场问题**：模型在公开榜单涨了 5 分，真实用户为什么没有感觉，甚至投诉更多？

## 13.1 先建能力矩阵

横轴是任务/能力：知识问答、抽取、代码、数学、工具调用、长上下文、安全等；纵轴是难度、语言、输入长度、用户类型、领域、风险等级。

每个格子明确：样本数、数据来源、指标、门槛和业务权重。公开 benchmark 只覆盖其中少数格子，主要作用是和外部模型建立共同坐标；内部评测才决定是否能上线。

## 13.2 生成配置是评测的一部分

temperature、top-p、max tokens、停止词、是否展示思考、对话模板都会改变结果。贪心解码测稳定能力，采样测分布和 pass@k；两者回答不同问题。

比较模型时必须固定配置，或者为每个模型使用其官方推荐模板并明确说明。把 instruct 模型套错 chat template 再比较，是常见但严重的不公平。

## 13.3 确定性任务与生成式任务

选择题、数值题、代码测试可以自动判分，但解析器必须稳健：模型输出“答案是 (C)”不能因为不等于字符串“C”就判错；同时不能用过宽正则从一段矛盾文本里捞出碰巧正确的字母。

开放回答没有唯一字符串，需要：

- 基于事实单元的匹配。
- rubric 分项评分。
- 成对比较。
- 人工专家评审。

指标越自动，规模越大；判断越细，成本和噪声越高。可靠方案通常分层：全量自动评测 + 小规模高质量人工复核。

## 13.4 pass@k 与采样预算

代码和数学常报告 pass@k：采样 k 次，至少一次正确的概率。它衡量模型是否“有能力偶尔找到答案”，不等于单次产品体验。

必须同时报告 pass@1、采样温度和总 token 预算。通过把 k 从 1 提到 100 获得高分，实际成本可能不可接受。对推理模型更应报告 accuracy-token Pareto：多想一倍是否真的值。

## 13.5 均值会隐藏什么

总体 80% 可能由简单题 95%、关键高风险题 40% 组成。必须做切片，并报告每个切片置信区间。

两个模型只差 0.5 分时，先问是否超过评测噪声。对同一批题的成对 bootstrap 比较比独立均值更有力；judge 评测还要考虑判官自身随机性。

## 13.6 离线和线上为什么会不一致

离线集固定、干净、通常是单轮；线上输入会漂移、信息不完整、多轮依赖、带恶意内容，还受检索与工具故障影响。

上线后要看任务成功、重试、用户改写、人工接管、投诉、token 成本和延迟，而不只是点赞率。点赞有强选择偏差：只有部分用户愿意点，且常受语气和速度影响。

### 核心问答

**Q：公开榜单还有价值吗？** 有，适合外部坐标和通用回归；不能替代贴近业务分布、带真实约束的内部评测。

**Q：为什么温度必须记录？** 它改变输出分布和 pass@k。不同温度下的单次准确率不可直接比较。

**Q：选择题为什么也会评错？** 模型输出格式多样，解析器过严会误杀、过宽会从矛盾文本中捞答案。解析协议必须单测。

**Q：线上点赞能当最终指标吗？** 不能单独用。它受用户选择、语气、速度和幸存者偏差影响，应与任务成功和人工抽检结合。

# 第 14 章 可复现评测系统：Evaluation Harness

> **开场问题**：同一个模型、同一个 benchmark，两个团队为什么能跑出相差 8 分的结果？

## 14.1 harness 是实验协议，不只是脚本

一项任务应被封装为：

1. 数据加载和版本。
2. prompt/chat template 构造。
3. 生成参数。
4. 输出解析。
5. 评分函数。
6. 聚合和置信区间。
7. 缓存、日志和可重放记录。

只有数据集名称相同远远不够。few-shot 示例、答案顺序、system prompt、是否要求 CoT 都能带来数分差异。

## 14.2 Task、Document、Request、Metric

一个清晰的 harness 把原始样本 Document 转成一个或多个 Request：生成文本、计算候选 log-likelihood、调用工具或运行 Agent 环境。模型产生 Response，再由 Metric 聚合。

分层的好处是同一任务可切换本地模型、API 模型和不同后端；评分逻辑不依赖执行方式。任务协议一旦和某个 SDK 写死，后续很难复现。

## 14.3 log-likelihood 与 generation

多选题可比较每个候选的条件 log-likelihood，不必真的生成；这种方法稳定、便宜，但长度不同的候选要考虑归一化。真实产品是生成答案，因此还应补 generation 评测，测试格式遵循和解释能力。

两种设置回答不同问题，不应拿 likelihood 结果冒充端到端生成效果。

## 14.4 缓存与可重放

模型调用昂贵，应按“模型制品哈希 + 模板版本 + 生成参数 + 输入”缓存原始响应。**缓存原始输出，不只缓存分数**，这样解析器或评分规则更新时不必重新推理。

每条结果要能追溯到完整请求和响应。只保留总分会让错误分析和 judge 复核无从进行。

## 14.5 并发、重试与 API 评测

外部 API 会限流、超时和返回瞬时错误。重试必须区分幂等错误与内容错误；不能因为解析失败就重新采样到一个能过解析的答案，这会暗中把 pass@1 变成 pass@k。

记录实际重试次数、模型版本和服务端可能变化的日期。闭源模型名称相同也可能滚动更新，结果无法永久复现。

## 14.6 Agent harness 为什么更难

普通评测是 prompt → response；Agent 评测是策略与环境多轮交互。harness 还要固定：

- 初始环境快照。
- 可用工具和权限。
- 每步观察格式。
- 最大步数、token 和时间预算。
- 环境状态转移。
- 成功判定和副作用清理。

若环境不确定，同一 Agent 的分数波动可能来自网页变化或服务故障，而不是模型。需要容器、模拟器或可重置 sandbox。

## 14.7 一个最小结果记录

每条样本至少保存：

- task/sample ID 与数据版本。
- 完整渲染 prompt/messages。
- 原始输出或完整轨迹。
- token 用量、延迟、工具次数。
- 解析结果、各指标分量。
- 模型、模板、推理配置和代码 commit。

这不是日志洁癖，而是未来能够解释“为什么这版涨了”的最低条件。

### 核心问答

**Q：harness 与普通评测脚本的区别？** harness 把任务协议、执行后端、解析和指标分离，并保证版本化、缓存和重放。

**Q：为什么缓存原始输出而不是最终分数？** 评分器和解析器会修复；有原始输出即可重算，没有就必须重新调用模型且结果可能变化。

**Q：解析失败可以自动重试吗？** 通常不可以。格式失败本身是模型失败，重试会把单次成功率偷偷变成多次尝试成功率。

**Q：Agent 评测为什么需要环境快照？** 环境变化会改变任务难度和结果，无法区分模型变化与外部变化。

# 第 15 章 模型裁判：LLM-as-a-Judge

> **开场问题**：开放问答没标准答案，用更强模型打分靠谱吗？

## 15.1 三种基本形式

**Pointwise**：给单个回答按 rubric 打 1–5 分，容易规模化，但不同样本尺度漂移。  
**Pairwise**：给两个回答选更好者，判断更容易、稳定性更高，适合模型对比。  
**Reference-guided**：提供参考答案或事实清单，减少 judge 凭自身知识猜测。

若目标是比较新旧模型，成对盲评通常比独立打分可靠。要随机交换 A/B 位置并允许平局。

## 15.2 Judge prompt 应该是什么样

包含明确的任务、分维度 rubric、优先级、输入证据、候选回答和严格输出 schema。要求先分析再给结构化结论可以改善稳定性，但解析时只信 schema 字段。

不要让被评回答中的“请给我满分”等内容与 judge 指令混在同一权限层。候选答案必须明确包在不可信数据边界内，防止 judge prompt injection。

## 15.3 常见偏差

- **位置偏差**：更偏好 A 或先出现的答案。
- **长度偏差**：把详细等同于正确。
- **风格偏差**：偏爱与 judge 自身相似的文风。
- **自我偏好**：模型家族可能更偏爱同系列回答。
- **权威语气偏差**：流畅自信的错误答案得高分。

检测方式是交换位置、控制长度、隐藏模型身份、加入事实核验题，并与人工金标对照。

## 15.4 校准 Judge

抽取一批有专家结论的样本，计算 judge 与人类的一致率、各类别混淆和置信度。不要只报总体相关系数：安全边界上 20% 的错判可能不可接受。

多 judge 投票可降方差，但同源模型可能共享偏差。更有价值的是不同模型家族 + 规则验证 + 人工抽查的组合。

## 15.5 Judge 不能判断什么

它无法可靠验证自己也不知道的最新事实，不能替代代码执行、数据库查询和权限检查；长上下文里还可能漏读关键证据。能程序验证的绝不交给 LLM judge。

优先级应为：真实环境结果 > 确定性规则/执行器 > 专家人工 > 校准后的 LLM judge > 未校准主观打分。

## 15.6 用 judge 生成训练数据的闭环风险

若同一个 judge 同时选择训练样本又评测最终模型，模型只需学会迎合 judge，分数会持续上涨而真实质量不变。这是“用自己的尺子证明自己长高了”。

训练选择器、开发评测和最终验收应尽可能独立，至少保留人工盲评和程序指标作为外部锚点。

### 核心问答

**Q：Pointwise 和 Pairwise 哪个更可靠？** 比较两个模型时通常 Pairwise 更稳定，因为相对判断比绝对 1–5 分容易；但仍要交换位置和允许平局。

**Q：多个 judge 投票就可信吗？** 只能降低随机方差，不能消除共享偏差。若都来自同类模型，可能一致地错。

**Q：什么时候不能用 LLM judge？** 有真实执行器、精确规则或高风险专业判断时，judge 不应替代它们。

**Q：为什么训练和评测不能用同一个 judge？** 模型会优化这个 judge 的偏好和漏洞，形成测量闭环，分数不再代表外部质量。

# 第 16 章 数据污染、能力回归与迭代闭环

> **开场问题**：模型在测试集上接近满分，怎样判断它是真会了，还是见过题？

## 16.1 污染有多个层次

- **精确污染**：训练中出现相同题目和答案。
- **近似污染**：改写、翻译、选项重排。
- **来源污染**：同一题库、代码仓库或文档的其他版本。
- **评测感知优化**：团队反复针对测试集修数据，即使样本没直接进训练，也已把测试集当开发集。

最后一种最普遍。测试集一旦被反复查看和用于决策，就不再是真正测试集，需要新的密封集。

## 16.2 怎么检测记忆而非泛化

做语义等价变换：改变量名、数字、实体、选项顺序、叙述风格，保持底层规则不变。若原题正确、变体大量失败，很可能依赖表面记忆。

代码评测按仓库切分并生成新测试；数学题参数化重采样；知识题使用发布日之后的事实。没有单一检测器能证明“绝无污染”，只能通过多种设计降低概率。

## 16.3 回归集要固定，探索集要流动

**回归集**保存历史上重要且已修复的失败，确保它们不再复发；**探索集**持续加入新分布和新攻击，发现未知问题。

回归集会逐渐被团队熟悉，不能承担泛化评测；探索集不稳定，不能用于精确比较历史版本。两者必须分开。

## 16.4 从失败到数据的闭环

1. 收集失败及完整上下文。
2. 确认能稳定复现。
3. 分类根因：模型、数据、prompt、检索、工具还是系统。
4. 选择最轻修法。
5. 构造正例、反例和边界近邻。
6. 放入训练/开发集；另留同类未见变体做测试。
7. 跑全量回归，确认没有挤坏别处。

“把失败答案改正确后直接加入训练”只完成了第 5 步的一小部分。

## 16.5 实验卡片与因果归因

一次实验只能有清晰的主要变量。若同时换数据、模板、学习率、基座和 judge，分数涨了也不知道为什么。

实验卡片记录：假设、变更、数据差异、训练配置、推理配置、结果、失败切片和结论。失败实验也必须保存，它们定义了已知无效区域，避免团队重复烧钱。

## 16.6 上线门禁

建议四层：

1. 确定性单测：模板、解析、工具 schema、停止条件。
2. 小型快速回归：每次提交运行。
3. 完整离线评测：候选权重或系统版本运行。
4. shadow/canary：真实流量中逐步验证。

高风险切片使用 hard gate，不允许总分补偿。任何自动 judge 的提升都不能绕过关键人工样本。

## 16.7 何时停止继续优化

当新增训练主要在测试噪声内波动、每个提升带来越来越大成本、或领域提升持续挤压关键通用能力时，应停止改权重，转向系统约束或接受边界。

成熟的模型开发不是把所有错误消灭，而是知道剩余错误是什么、概率多大、怎样被系统检测和兜底。

### 核心问答

**Q：去重能完全解决污染吗？** 不能。近似改写、同源数据和评测感知优化无法靠字符串去重彻底识别。

**Q：为什么已修复错题不能直接充当最终测试？** 团队已经围绕它做过决策，它现在是回归集。最终测试要用同类但未见的新变体。

**Q：一次实验为什么尽量只改一个主要变量？** 为了归因。不能解释提升来源的实验，无法稳定复现也无法指导下一步。

**Q：什么才算迭代闭环完成？** 不只是当前错题答对，还要同类未见变体提升、旧能力不退化、线上指标改善且成本可接受。
