# 第五部分 检索增强与智能体系统

**目的**：很多产品问题根本不该靠训练解决。把指令，知识，工具和环境放进模型上下文，并用可靠的运行循环约束模型，常常更快，更可控。本部分从一次调用走到完整 Agent。

# 第 17 章 提示词与上下文工程

> **开场问题**：为什么同一句要求写进 system message 有效，放进检索文档里却会被忽略，甚至被当成不可信内容？

## 17.1 Context 不只是“一长段字符串”

现代聊天模型看到的是带角色和边界的消息序列。常见优先级是 system/developer > user > tool/data，但具体语义由后训练模板决定。

高权限消息定义目标，规则和可用工具；用户消息表达当前任务；检索文档和工具返回是**不可信数据**。若把它们全部拼成同一段文本，模型无法可靠区分“要遵守的指令”和“要分析的内容”，prompt injection 就由此产生。

## 17.2 一个可维护的 Prompt 结构

建议分成：

1. 角色与任务目标。
2. 必须遵守的硬约束。
3. 决策流程或边界条件。
4. 输出 schema。
5. 少量有区分度的示例。
6. 当前输入与外部证据。

把最关键的约束放在清晰，稳定的位置；避免十几条互相重叠的“不要”。Prompt 过长不仅贵，还会使规则竞争，模型更难判断优先级。

## 17.3 Few-shot 示例在做什么

示例不是给模型补知识，而是在上下文中定义任务，标签语义和输出风格。高价值示例应覆盖决策边界：一个正例，一个容易混淆的反例，一个信息不足的边界例。

随机堆十个普通例子常不如按当前输入检索两个相似示例。动态 few-shot 本质上是对“示范”的 RAG，检索目标应是决策结构相似，而不只是文本相似。

## 17.4 结构化输出

“请输出 JSON”只是自然语言愿望，不是协议保证。可靠性从弱到强：

- Prompt 要求 + 解析失败重试。
- JSON mode，保证语法合法但不保证 schema 正确。
- constrained decoding，根据 JSON Schema/CFG 限制下一 token。
- 工具调用协议，由模型输出结构化函数名和参数。

结构化约束能保证形状，不能保证语义。`amount: -999999` 依然是合法 JSON，必须在应用层做类型，范围，权限和业务校验。

## 17.5 长上下文怎样排布

模型对上下文不同位置的利用并不均匀，关键信息埋在中间可能被忽略。常见策略：核心指令置顶；当前问题和输出要求靠近末尾；长证据分块带标题；先压缩低价值历史；为证据编号，要求引用。

不要把“窗口支持 1M token”理解成“放进去都能同等利用”。第一册第 10 章讲的是模型侧能力，这里关注任务侧的信息预算。

## 17.6 Prompt 版本也是代码版本

每次修改都要有版本，变更原因，评测结果和回滚能力。禁止在线上控制台悄悄改一句话而不留记录。Prompt 与模型，模板，工具 schema 共同组成行为制品。

### 核心问答

**Q：Context Engineering 与 Prompt Engineering 的区别？** 前者不只写指令，还设计哪些证据，示例，历史和工具结果进入上下文，以及它们的权限和位置。

**Q：为什么检索文档不能拥有 system 权限？** 文档来自外部且可能被攻击者控制。它是待分析数据，不是可信指令。

**Q：JSON mode 能保证业务字段正确吗？** 不能。它最多保证语法，schema，范围，权限和语义仍需应用层验证。

**Q：什么时候 few-shot 比 SFT 合适？** 任务仍在变化，示例很少，需要快速试验或每个租户规则不同时；规则稳定且每次都重复占上下文，再考虑 SFT。

# 第 18 章 检索增强生成：从召回到可信回答

> **开场问题**：向量库已经召回了包含答案的文档，模型为什么仍然答错？

## 18.1 RAG 是一条链，不是一个向量数据库

完整链路：

**查询理解 → query 改写/分解 → 召回 → 过滤 → 重排 → 上下文组装 → 生成 → 引用校验**

最终错误要沿链路归因。文档没被召回是 retrieval failure；召回了但没进入上下文是 ranking/budget failure；上下文有证据却答错才是 generation failure。只看最终正确率无法决定该修哪一段。

## 18.2 文档切分决定检索单元

块太小，语义和上下文丢失；块太大，embedding 被多个主题稀释，召回后又浪费上下文。固定 512 token 是起点，不是答案。

更好的做法是尊重文档结构：标题，段落，表格，函数，类，页面。保存 parent-child 关系：小块用于精确检索，命中后带回更大的父块供模型理解。

每块必须带元数据：来源，时间，权限，文档版本，章节路径。没有元数据，后续无法过滤过期内容，做权限控制或生成可靠引用。

## 18.3 Dense，Sparse 与 Hybrid

Dense embedding 擅长语义相似和改写；BM25 等 sparse 检索擅长精确术语，编号，错误码和罕见实体。企业知识里两者都不可缺。

Hybrid retrieval 分别取候选，再用 RRF 或归一化分数组合。不能直接把两个系统的原始分数相加，因为尺度不同。

## 18.4 Query 改写与分解

多轮对话里的“它上一版有什么问题”不能直接拿去检索，要结合历史改写成独立查询。复杂问题还需分成多个子查询，分别召回后合并。

但改写会改变用户意图。应保留原查询并做多路召回，而不是完全替换；专有名词，数字，否定条件要明确要求保留。

## 18.5 Reranker 在做什么

embedding 检索通常从百万文档快速取 top-100，精度有限；cross-encoder reranker 同时阅读 query 和每个候选，重新排出 top-5/10。它慢但候选少，能显著提升精度。

召回关心 recall@k：正确证据有没有进候选；重排关心 nDCG/MRR：正确证据是否靠前。两阶段指标不能混成一个。

## 18.6 上下文组装

不能把 top-k 原样拼起来。要做：

- 去掉重复和近重复块。
- 保留来源和层级标题。
- 同一文档的相邻块适度合并。
- 多来源证据控制多样性，避免前 k 全来自一篇文档。
- 按 token 预算选择，而不是固定块数。
- 明确告诉模型只能基于证据作答，不足时说不知道。

还要处理证据冲突和时效性。通常优先权威，更新的来源，并把冲突暴露给模型，而不是静默选一个。

## 18.7 引用必须可验证

要求模型输出 `[1]` 不代表引用可靠。生成后要检查：

1. 引用 ID 是否存在。
2. 引用段落是否支持对应主张。
3. 关键主张是否都有引用。
4. 是否把来源里没有的信息“搭便车”挂在引用后。

可用 NLI/judge 做规模化初筛，高风险场景仍需规则或人工。

## 18.8 RAG 的端到端评测

至少分三层：

- Retrieval：recall@k，MRR/nDCG，权限过滤正确率。
- Context：证据覆盖率，冗余率，token 成本。
- Answer：正确性，faithfulness，引用精度/召回，拒答准确率。

还要构造“知识库里没有答案”的问题。若只测有答案样本，系统会学会无论如何都编一个。

## 18.9 RAG 与微调怎么配合

RAG 提供事实，SFT 教模型怎样使用事实：引用，处理冲突，证据不足时拒答。可以用 RAG 轨迹做 SFT，但训练时应随机加入检索噪声和空结果，否则模型只会在完美检索条件下工作。

不要用微调掩盖低召回，也不要指望 RAG 自动修复模型不具备的复杂推理能力。

### 核心问答

**Q：文档召回了，为什么仍答错？** 可能排名靠后没进入预算，被重复块挤掉，上下文组装丢了标题，或模型没有正确利用证据。要分层记录。

**Q：Dense 能完全替代 BM25 吗？** 不能。错误码，编号，罕见名字和精确术语通常 sparse 更强，混合检索更稳。

**Q：RAG 最容易被忽略的安全问题？** 权限过滤必须发生在召回层，不能把无权查看的文档先送给模型再要求它别说。

**Q：引用存在就说明 grounded 吗？** 不说明。必须检查引用内容是否真的支持该主张。

# 第 19 章 工具调用：协议，执行与安全边界

> **开场问题**：模型输出了格式完美的转账调用，为什么系统仍然绝不能直接执行？

## 19.1 Function Calling 的本质

给模型一组工具 schema：名称，用途，参数类型与描述。模型输出“选择哪个工具 + JSON 参数”，应用执行后把结果作为 tool message 放回上下文，模型再继续。

模型只是提出调用建议，不直接拥有能力。真正权限在执行器。这条边界决定了系统安全。

## 19.2 Schema 怎样写

工具应单一职责，命名可区分，参数尽量强类型。描述需要说明“何时用，何时不用”，而不只是功能。

坏设计：`run(action: string, payload: any)`，把所有决定都塞进自由文本。  
好设计：`get_order(order_id)`, `request_refund(order_id, reason, amount)`，各字段有枚举，范围和必填规则。

工具太多也会降低选择准确率并占上下文。可先按任务路由出一个小工具集，再交给模型选择。

## 19.3 参数生成之后必须验证

应用层检查：

- JSON Schema 和类型。
- 数值范围，枚举，日期。
- 当前用户是否有权限访问对象。
- 资源是否仍处于允许操作的状态。
- 敏感操作是否需要确认。

绝不能因为参数来自“受信模型”就跳过。模型可能误解，也可能被 prompt injection 操纵。

## 19.4 幂等性与副作用

网络超时后不知道转账是否成功，盲目重试可能执行两次。所有有副作用工具都应支持 idempotency key，并在重试前查询状态。

Agent 的“重试”不能简单等价于再次调用。读取类工具通常安全；写入，发送，删除，支付需要事务语义，确认和审计。

## 19.5 工具返回怎样放回上下文

返回应结构化，精简，标明错误类型。不要把 5 MB 原始日志全部塞回模型；先在执行器侧过滤，分页或摘要，但保留可追溯 ID。

工具输出是不可信数据。网页抓取结果即使包含“调用 delete_all 工具”，也不能改变权限。用清晰边界包裹，并在 system 层声明它只是观察。

## 19.6 工具错误分类

- **选择错误**：该调用时没调，或选错工具。
- **参数错误**：字段缺失，值错，引用了不存在对象。
- **执行错误**：外部服务超时或返回失败。
- **解释错误**：调用成功但误读结果。
- **循环错误**：重复调用同一个无效工具。

不同错误修法不同：选择和参数可通过示范/SFT；执行错误靠重试和系统；解释错误需改善返回 schema；循环错误需状态检测和步数限制。

## 19.7 工具调用数据

一条训练轨迹应包含：用户请求 → assistant tool call → tool result → assistant 最终回答。还要加入无需工具，工具失败，结果为空，多个工具有相似功能等反例。

只训练成功的完美轨迹，模型上线后遇到第一个 timeout 就不会处理。

### 核心问答

**Q：模型输出通过 JSON Schema，可以直接执行吗？** 不可以。Schema 只验证形状，还需权限，业务状态，范围和用户确认。

**Q：工具描述为什么要写“何时不用”？** 多个工具功能相近时，仅描述能力无法形成决策边界，模型会过度调用。

**Q：所有失败都能自动重试吗？** 不能。有副作用操作必须幂等并确认之前是否已成功。

**Q：工具结果算不算可信指令？** 不算。它是环境数据，可能包含恶意文本，只能作为观察。

# 第 20 章 智能体系统：规划，记忆与行动循环

> **开场问题**：一次工具调用和 Agent 的区别是什么？加一句“先制定计划”就算 Agent 吗？

## 20.1 Agent 是闭环

最小循环：

1. **Observe**：读取用户目标，环境状态和工具结果。
2. **Decide**：选择下一动作或结束。
3. **Act**：调用工具，写文件，执行代码等。
4. **Observe again**：环境变化后继续。

关键不是“会调用工具”，而是动作改变环境，新的观察又改变后续决策。固定工作流是预先写好步骤；Agent 由模型根据状态动态选步骤。能用确定工作流解决时，不要使用开放 Agent。

## 20.2 状态里应存什么

完整聊天历史会无限增长且充满噪声。应区分：

- 当前任务与不可变约束。
- 已完成步骤和关键结果。
- 待办/计划。
- 外部资源引用。
- 可丢弃的原始日志。

长任务中定期压缩状态，但摘要不能成为唯一真相；重要文件，测试结果和提交 ID 应保留结构化引用。记忆不是“把所有消息塞进向量库”。

## 20.3 计划的作用与局限

计划把长目标分解为可检查步骤，减少遗忘约束。但一次性生成十步计划通常会过时。更稳健的是滚动规划：先列高层里程碑，只详细决定下一两步，环境变化后更新。

计划必须连接验证：每一步完成条件是什么，由什么观察证明。没有验证的计划只是更长的自然语言。

## 20.4 终止条件

Agent 最危险的失败不是报错，而是永不结束：重复搜索，反复改同一文件，在两个方案间来回。

需要多层停止：

- 任务成功验证器通过。
- 明确不可恢复错误。
- 最大步数，token，时间和金钱预算。
- 检测到状态连续多轮无变化。
- 高风险操作前等待人工确认。

模型自己说“完成了”不是成功条件；必须由环境或独立检查器确认。

## 20.5 反思与重试

失败后让模型分析原因再试，确实有效，但必须提供新信息：错误日志，测试差异，工具状态。没有新观察的重复“反思”容易产生更长但同样错误的文字。

重试策略应按错误类型：瞬时网络错误可指数退避；参数错误回到模型修参数；权限错误立即停止；测试失败读取失败详情并局部修复。

## 20.6 单 Agent 还是多 Agent

多 Agent 可以并行搜索，让不同角色独立提出方案或交叉审查；代价是 token 成本，协调，共享状态和错误传播。

只有任务能自然分解，子任务接口清晰，并行收益大于协调成本时才值得。把同一个模糊任务扔给五个模型再让第六个总结，通常只是昂贵投票。

## 20.7 权限与 sandbox

Agent 运行代码和修改外部系统时应遵循最小权限：只挂载需要的目录，网络域名白名单，密钥按工具注入而不是写进 prompt，破坏性操作显式审批，完整审计日志。

把“请不要删除文件”写进 system prompt 不是安全边界。容器，文件权限和 API policy 才是。

## 20.8 成本是一等公民

Agent 成功率提高可能来自更多尝试。评测必须同时报告：

- 成功率。
- 平均/尾部步骤数。
- 输入输出 token。
- 工具调用次数和外部费用。
- wall-clock 延迟。
- 需要人工介入的比例。

一个 80% 成功，平均 50 步的 Agent 不一定优于 75% 成功，5 步的工作流。

### 核心问答

**Q：Workflow 和 Agent 的区别？** Workflow 的控制流由人预先确定；Agent 根据每步环境观察动态选择下一动作。前者更可靠，能用就优先用。

**Q：为什么“反思”有时没用？** 若没有新的外部信息，模型只是在同一上下文里重新组织猜测，无法突破事实缺口。

**Q：多 Agent 一定更强吗？** 不。任务不可分或共享状态复杂时，协调成本和错误传播会超过并行收益。

**Q：谁判断 Agent 完成？** 尽量由环境验证器，测试或明确状态判断，不能只信模型自报。

# 第 21 章 Agent Harness：运行时，状态与权限

> **开场问题**：同一个模型装进两个 Coding Agent，为什么一个能连续工作几个小时，另一个十分钟后就忘记目标，重复调用工具？差异往往不在模型，而在 Harness。

## 21.1 Harness 到底是什么

Agent 是第 20 章的“观察—决策—行动”闭环；**Agent Harness 是承载并约束这个闭环的运行外壳**。它至少负责：

- 把模型输出解析成动作并执行。
- 管理工具注册，选择，参数验证与权限。
- 保存任务状态，文件和中间产物。
- 在上下文变长时压缩，淘汰和重新注入信息。
- 处理错误，重试，暂停，恢复和人工审批。
- 调度子 Agent，并合并结果。
- 记录完整轨迹，成本和可观测信息。

模型只负责预测“下一步做什么”。长任务能否可靠完成，很大程度取决于 Harness 是否把正确的信息留在上下文，把危险动作挡在外面，把工具错误变成模型可理解的观察。

它不是一个新模型架构，也不只是几行 ReAct prompt。可以把它理解为 **Agent 的操作系统**：向上给模型稳定接口，向下管理工具，状态，资源与权限。

## 21.2 不要混淆三种 Harness

三个相似名字解决不同问题：

- **Agent Harness**：线上运行 Agent 的控制循环，本章主题。
- **Evaluation Harness**：第 14 章的实验协议，用同一套任务，解析和指标公平评测模型。
- **Environment Harness**：包裹训练/评测环境，动态调整任务，观察和反馈，但保留底层验证器。它属于第 22 章的前沿方向。

Evaluation Harness 可以启动 Agent Harness 去完成任务；Environment Harness 可以为 Agent 提供变化后的训练环境。三者可以组合，但不是同义词。

## 21.3 控制循环不能全交给模型

一个典型循环是：

1. 从持久状态恢复任务。
2. 根据当前阶段选择需要的工具定义。
3. 组装受预算约束的上下文。
4. 调用模型得到文本，工具调用或结束信号。
5. 校验动作与权限。
6. 执行并把结果转成结构化观察。
7. 更新状态，预算和轨迹。
8. 判断成功，失败，等待审批或继续。

步骤 2，3，5，7，8 必须有确定性代码参与。若连“是否已经成功”和“还有多少预算”都让模型用自然语言自行判断，系统会重复工作，越权或永不结束。

## 21.4 上下文管理是 Harness 的核心能力

长任务会产生大量工具输出，代码 diff，网页和子 Agent 报告，全部塞回上下文最终一定溢出。Harness 要区分：

- **始终保留**：用户目标，硬约束，权限和验收条件。
- **结构化状态**：待办，已完成项，文件路径，提交 ID，测试状态。
- **按需取回**：长文档，旧日志，网页内容。
- **可以丢弃**：重复输出，已被后续结果取代的中间尝试。

Compaction 不是把历史随便总结成一段话。摘要必须保存未完成承诺，失败原因和外部资源引用；事实性产物仍放在文件或数据库中，需要时重新读取。**上下文是工作内存，不是唯一存储。**

## 21.5 工具发现与按需加载

工具增到几百个后，把所有 schema 放进 prompt 会浪费 token，也降低选择准确率。现代 Harness 先让模型搜索工具目录，只把相关工具定义加载到当前上下文。

还可以让 Harness 直接用代码编排简单的数据流：并行调用多个搜索工具，过滤结果，做确定性聚合，只把精炼结果交回模型。这样既省上下文，也减少模型在机械搬运数据上出错。

原则是：**能由确定性程序完成的编排，不要消耗一次模型推理。**

## 21.6 持久任务，暂停与恢复

真正的 Agent 任务可能持续数小时或数天，会等待 CI，人工审批或外部事件。Harness 不能依赖一个常驻 Python 进程和内存中的消息数组。

每一步完成后保存：

- 当前状态和待办。
- 模型与 prompt 版本。
- 已用预算。
- 工具调用及幂等键。
- 环境快照或外部资源版本。
- 下一次恢复所需的最小上下文。

恢复时要避免重复执行已有副作用。持久化，幂等性和事件驱动状态机，比“再给模型一个更强 prompt”更能决定长任务可靠性。

## 21.7 子 Agent：上下文隔离比角色扮演更重要

子 Agent 的主要价值不是让多个模型扮演“研究员，评论家”，而是：

- 并行处理真正独立的子任务。
- 给每个子任务独立，干净的上下文。
- 防止主线程被大量搜索细节污染。
- 让不同子任务使用不同模型，工具和预算。

父 Agent 必须给出明确的输入，交付物和终止条件。子 Agent 返回的应是结论和证据引用，而不是完整思考历史。共享同一份可写状态时还要处理冲突，不能假设多个 Agent 自然会协调。

## 21.8 权限，审批与策略引擎

Harness 才是真正的执行边界。每个工具应声明：

- 读还是写。
- 可访问的资源范围。
- 是否有外部副作用。
- 是否可自动重试。
- 是否需要人工批准。

模型不能通过在参数里写“用户已经批准”绕过策略。审批结果应来自独立通道，并绑定具体动作摘要；动作发生变化后要重新审批。

## 21.9 可观测性：记录语义事件

除了模型延迟和 token，Harness 还应记录：

- 每轮选择了什么动作，为什么进入下一状态。
- 哪些上下文被加入，压缩或丢弃。
- 工具发现和选择结果。
- 重试原因和错误分类。
- 子 Agent 的派发，取消和合并。
- 权限拒绝和人工审批。

只有这些语义事件，才能判断失败源于模型，上下文，工具还是控制逻辑。

## 21.10 Agent 评测的单位是完整轨迹

保存每一步：

- 当时可见的消息和状态。
- 模型原始输出。
- 解析出的动作。
- 工具输入，输出，耗时和错误。
- 环境状态变化。
- token 和费用。
- 最终验证结果。

只有最终答案无法分析失败，也无法把成功轨迹回流训练。

## 21.11 环境必须可重置

编程 Agent 要固定仓库 commit，依赖和测试；浏览器 Agent 要固定网站快照或模拟后端；操作系统任务要在容器/虚拟机中恢复初始状态。

每次运行前重置，每次结束清理副作用。否则前一个 Agent 的修改会让后一个任务变简单或变难。

## 21.12 成功判定必须独立

编程任务以隐藏测试通过和改动范围为准，不以“Agent 说已修复”为准；客服任务看真实订单状态和政策遵循；研究任务检查引用和结论是否被来源支持。

公开测试可给 Agent 反馈，隐藏测试只用于最终验收，防止它针对测试投机。

## 21.13 消融：找出提升来自哪里

至少做：

- 同模型，换新旧 prompt。
- 同模型，换新旧工具。
- 同系统，换模型。
- 固定步数/预算后比较。
- 去掉记忆，规划，反思模块分别测试。

如果不固定预算，允许新系统多跑三倍步骤得到的成功率提升不能归因于“更聪明”。

## 21.14 轨迹怎样回流训练

失败轨迹先分类。工具 schema 错修工具；环境返回不清修接口；模型决策错才进入训练。

成功轨迹也不能原样全收：可能包含多余搜索，偶然试错，泄露测试信息。应压缩成高质量示范，保留关键决策和必要观察；也可以构造 chosen/rejected 轨迹对，训练模型偏好更短，更可靠的路径。

对可验证任务，可把最终环境结果作为 RLVR reward；步骤级工具成功可作为过程信号。但要防止 Agent 通过修改测试，绕过权限等方式 hacking 环境。

## 21.15 模型与 Harness 的共同进化

模型升级后，旧 prompt 的过度解释可能成为负担；模型工具调用更强后，手写纠错逻辑可能反而干扰。因此每次换基座都要重新做系统消融，不能永久继承所有 scaffold。

判断一项脚手架是否还需要：去掉它后质量是否下降，成本是否改善，失败类型是否变化。能由新模型稳定完成的逻辑应逐渐删掉，保持系统简单。

## 21.16 从离线任务到线上闭环

上线顺序：

1. 离线固定环境大量回放。
2. shadow 模式，只观察会怎么做，不真正执行副作用。
3. 低权限 canary，小流量执行。
4. 扩大权限与流量，同时保留人工接管。

线上收集的不只是成功/失败，还包括用户中断，人工修正，重试路径和成本。这些形成下一轮失败样本库。

### 核心问答

**Q：Agent 与 Agent Harness 一句话怎么区分？** Agent 是利用观察选择动作的策略；Harness 是让这个策略能够长期，安全，可恢复地运行的控制系统。

**Q：Harness 最重要的能力是什么？** 不是某个花哨规划算法，而是上下文管理，工具与权限，持久状态，错误恢复和完整轨迹。

**Q：Agent benchmark 为什么比普通问答难复现？** 结果依赖环境状态，工具版本，Harness，预算和多步随机性；任何一项变化都可能改变分数。

**Q：成功轨迹能直接拿去 SFT 吗？** 不应直接拿。成功可能靠大量无效试错或利用漏洞，需要清洗和压缩成可取的策略。

**Q：怎样证明提升来自模型而非更多预算？** 固定工具，prompt，步数，token 和时间预算做消融，只替换模型。

**Q：模型变强后旧 scaffold 怎么办？** 重新消融。没有持续贡献的规划，纠错和提示应删除，避免历史补丁永久堆积。

# 第 22 章 前沿方向：可验证环境与模型—环境协同进化

> **开场问题**：Agent Harness 之后，真正值得关注的新方向是什么？是再发明一个“多 Agent 框架”，还是改变模型学习和工作的环境？

本章只画技术地图，不把尚未稳定的论文结论写成行业定论。判断一条方向是否重要，看它是否改变了**能力来源**，而不是有没有一个新缩写。

## 22.1 第一条主线：Harness 正在成为 Agent 的运行时

早期 Agent 框架主要包装 ReAct 循环。2025–2026 年的变化是 Harness 开始承担完整运行时职责：

- 长任务的持久上下文与自动压缩。
- 沙箱中的文件，终端，浏览器和 GUI。
- 按需工具发现，而非把全部 schema 塞进 prompt。
- 并行子 Agent 与上下文隔离。
- 暂停，恢复，审批，预算和审计。

这使 Coding，Deep Research，Computer Use 看起来像三类产品，底层却逐渐共享同一套原语：**受控环境 + 工具 + 持久状态 + 子任务并行 + 可验证结束条件**。

真正的进展不是“模型能多调用几个函数”，而是系统能让一个概率策略连续工作数小时，并在进程重启，上下文压缩和工具失败后保持任务连续性。

## 22.2 MCP 与 A2A：协议层，不是智能本身

MCP 标准化 Agent 如何发现和调用工具，读取资源；A2A 标准化相互独立的 Agent 如何发现，委派，报告状态和交换产物。

它们解决生态互操作问题，类似 API/HTTP 对软件系统的价值，但**不会自动提高推理能力或成功率**。接入一百个 MCP server，可能只会让工具选择更困难，权限面更大。

判断协议是否有用要看：

- 是否减少重复适配代码。
- schema 与错误语义是否稳定。
- 身份，权限和审计能否贯穿调用链。
- 长任务状态和产物能否可靠传递。
- 工具/远端 Agent 是否来自可信来源。

所以应把 MCP/A2A 放在 Harness 的接口层学习，而不是当作新的模型算法。

## 22.3 Coding，Deep Research 与 Computer Use 正在汇合

Coding Agent 擅长终端，代码编辑和测试；Deep Research 擅长搜索，阅读，证据综合；Computer-Use Agent 通过截图，鼠标和键盘操作没有 API 的软件。

真实任务往往三者交替：研究一个产品 → 写脚本处理数据 → 在网页后台配置 → 截图验证结果。前沿系统因此从单一动作空间走向**混合计算机使用**，动态选择 API，代码，无障碍树还是视觉坐标。

动作优先级通常应该是：

1. 稳定结构化 API。
2. 脚本/终端。
3. 无障碍树或 DOM。
4. 最后才是截图坐标点击。

越往后通用性越强，可靠性越低。视觉点击很吸引人，但不应替代可验证的结构化接口。

## 22.4 可验证环境正在取代静态题库

静态问答数据只能给出输入和答案；Agent 需要一个可交互，可重置，能判断环境状态的世界。新的核心资产变成：

- 任务生成器：持续产生不同实例。
- 环境状态机：执行动作并返回观察。
- verifier：检查真实状态，而非只读最终文本。
- sandbox：隔离副作用并支持重置。
- trajectory recorder：保存每一步用于训练和审计。

软件仓库，终端，浏览器，桌面应用，游戏和模拟器都可以成为训练环境。只要“解题难，验证容易”，就能提供可扩展 RL 信号。

这比再收集一个固定 benchmark 更重要：模型很快会吃完静态题库，但可程序生成的环境可以不断采样新实例。

## 22.5 从结果奖励走向可验证过程奖励

第 10 章的 RLVR 常只在轨迹结束给一个分数。长 Agent 轨迹可能前 20 步正确，最后一步失败；也可能过程漏洞百出却偶然成功。稀疏结果奖励无法精确分配信用。

前沿方向是让环境为中间动作提供**可验证过程奖励**：

- 代码每次修改后编译和局部测试是否改善。
- 搜索是否找到包含关键证据的来源。
- GUI 操作后目标控件状态是否正确。
- 约束求解中当前部分解是否仍可满足。

重点是“可验证”，不是让另一个 LLM 主观评价“这一步看起来不错”。过程 verifier 越可靠，长轨迹训练越稳定；错误 verifier 也会把模型更快带偏。

## 22.6 自适应课程：环境跟着能力边界移动

GRPO 已暴露一个问题：一组全对或全错都没有相对优势。静态题库随着模型增强，会出现大量过易题和仍完全不会的过难题。

新方向让环境根据当前策略动态调难度，把任务维持在有学习信号的区域：

- 改变约束数量，工具噪声和时间预算。
- 针对近期失败类型生成变体。
- 保留固定锚点，防止课程只追逐短期弱点。
- 用新 rollout 验证新任务确实可解，可验且不重复。

这相当于把第 2 章的“难例挖掘”升级成在线环境课程。

## 22.7 RL 与 on-policy distillation 正在融合

纯 RL 有真实目标，但奖励稀疏，方差大；离线蒸馏信号密，却只在教师数据分布上学习，遇到自己生成的错误状态不会恢复。

新的混合路线是在**当前策略自己生成的轨迹上**同时使用：

- verifier 的 outcome/process reward，直接优化任务成功。
- 更强教师或带特权信息的自身给出的 token 级分布，提供密集纠错。

成功轨迹可继续做策略强化，失败轨迹不必全部丢掉，可以让教师针对模型真实到达的错误状态示范如何恢复。这比只蒸馏一批静态完美答案更贴近部署分布。

目前具体目标函数仍快速演化，不必追每个名称；应掌握“on-policy 状态 + 稠密教师信号 + 可验证 reward”这个稳定组合。

## 22.8 环境也开始被模型生成和改造

再往前一步，模型不只在环境中学习，还生成任务，验证器和环境包装器：

- 根据失败轨迹生成更针对性的任务。
- 为已有环境增加噪声，约束和恢复场景。
- 编写可执行 verifier，再用对抗样本验证它。
- 随策略增强持续提高难度。

这形成模型—环境共同进化。但风险也最大：模型若同时出题，写 verifier，解题，很容易留下只有自己知道的捷径，形成闭环自证。

可靠原则是 **solve–verify asymmetry**：求解应明显难于验证；底层 verifier 尽量保持独立，确定和可审计；新环境必须经过新 rollout，对抗攻击和人工抽查后才能进入训练。

## 22.9 Reward Hacking 正在从事故变成专门评测

过去发现 Agent 修改测试，读取答案，利用环境漏洞，往往当作个案修补。新的做法是主动在环境里植入可检测的“蜜罐漏洞”，测模型是否会利用：

- 修改验证脚本而非完成任务。
- 读取隐藏答案或测试。
- 绕过权限直接改状态。
- 欺骗 judge 或伪造工具结果。

这让 reward hacking 从主观阅读轨迹，变成可规模化，确定性检测。任何要用 Agent RL 的团队，都应该把“能否攻破 verifier”作为独立能力来测试。

## 22.10 长期记忆从向量检索走向状态学习

第一代 Agent memory 常把所有历史 embedding 后检索。前沿系统开始区分：

- 情节记忆：过去发生了什么。
- 语义记忆：从多次经历总结出的稳定事实。
- 程序记忆：某类任务的可靠操作流程。
- 工作状态：当前任务进行到哪里。

真正困难的是**写入策略**：什么值得记，何时合并，何时遗忘，错误记忆怎样撤销。未来训练信号会从“回答是否正确”扩展到“是否写入了有助于未来任务且不泄露隐私的记忆”。

## 22.11 Embodied AI 与 World Model 是更远的一层

Computer Use 仍在数字世界，动作可回滚，复制环境容易。机器人和具身 Agent 进入物理世界后，数据昂贵，动作有风险，环境不可完全重置。

World Model 试图学习“动作之后世界会怎样变化”，让 Agent 在内部模拟多步结果再行动。这与第一册的语言模型结构不同，也超出第三册的工程主线，但应知道它是 Agent 从软件环境走向物理环境的关键接口。

短期内最可落地的仍是：在数字环境中用可执行 verifier 训练，再把部分规划能力迁移到具身任务，而不是直接让模型在真实世界自由试错。

## 22.12 怎样判断一个“最新技术”是否值得追

用五个问题过滤：

1. 它增加了新的训练信号，还是只换了框架名字？
2. 它解决的是模型能力，Harness 可靠性，还是协议互通？
3. 结果能被独立 verifier 重现吗？
4. 比强基线多用了多少 rollout，工具和测试时算力？
5. 在新任务，新环境和固定预算下仍有提升吗？

MCP/A2A 是重要协议，但不是能力算法；多 Agent 是并行组织方式，不天然提高质量；某个新的 policy loss 若只在一个数学榜单赢 0.5 分，不应立即变成正文主干。**正文保留稳定机制，前沿章保留方向与判据。**

- [RLVE](https://lst627.github.io/publications/2026-4-30-rlve) / [EnvHarness](https://arxiv.org/abs/2608.19880)：自适应可验证环境与针对模型弱点的环境包装。
- [Verifiable Process Rewards](https://arxiv.org/abs/2605.10325)：用程序 oracle 提供步骤级奖励。
- [EvoEnv](https://arxiv.org/abs/2605.14392) / [SEAL](https://arxiv.org/abs/2605.24426)：环境生成及策略—环境共同进化。
- [OpenComputer](https://arxiv.org/abs/2605.19769) / [RecreationWorld](https://arxiv.org/abs/2609.22000)：把 GUI，代码与软件状态验证合并为可审计环境。

这些工作仍在快速演化。书中应保留论文日期与链接，下一版复核结论，而不要把当前缩写写成永久标准。

### 核心问答

**Q：Harness 是不是 2026 年最重要的新算法？** 不是算法，而是 Agent 运行时。它的重要性来自把上下文，工具，状态，权限和恢复变成可工程化系统。

**Q：MCP 和 A2A 哪个会取代哪个？** 不会。MCP 连接 Agent 与工具/资源，A2A 连接相互独立的 Agent；二者解决不同接口问题。

**Q：Agent 训练为什么越来越强调环境？** 长任务没有固定标准答案，真正结果存在于环境状态里。可重置，可验证的环境同时提供数据，reward 和评测。

**Q：比 GRPO 更新的方向是什么？** 重点不只是再换一个 policy loss，而是可验证过程奖励，自适应课程，on-policy 蒸馏，以及策略与环境共同进化。

**Q：模型自己生成训练环境可靠吗？** 默认不可靠。只有 verifier 独立，求解明显难于验证，并经过对抗检查和新 rollout 验证时才可用。

# 尾声 方法选择：从 Prompt 到 Agentic RL

面对一个新问题，按下面顺序决策：

1. **任务定义清楚吗？** 没有就回第 1 章。
2. **问题是知识，行为，推理还是系统流程？** 先分类。
3. **Prompt/few-shot 能解决吗？** 能就停在第 17 章。
4. **需要外部或动态知识吗？** 用第 18 章 检索增强生成：从召回到可信回答。
5. **需要操作外部世界吗？** 用第 19 章工具；步骤动态才升级到第 20 章 智能体系统：规划，记忆与行动循环。
6. **行为稳定且重复，上下文成本高吗？** 用 SFT 或 LoRA 固化。
7. **已经会答，但需要明确偏好边界吗？** 用 DPO。
8. **结果可验证且需要探索更优策略吗？** 才用 RLVR。

## 三道综合设计题

### 题一：企业知识助手

知识每天更新，按部门授权，答案必须引用来源。合理主线是 RAG + 权限过滤 + 引用验证；SFT 只教证据使用和拒答，不把文档事实硬塞进参数。

### 题二：代码修复模型

已有基座会写代码，但不擅长公司仓库。先建按仓库切分的 harness 和容器环境；用真实修复轨迹 SFT/LoRA 学工具协议；以隐藏测试做 verifier，再考虑 RLVR 优化多步修复策略。

### 题三：高风险客服 Agent

订单查询，退款和支付有不同权限。用确定工作流承载主流程，模型负责意图与参数；所有写操作幂等，校验，二次确认。只有确实无法预写控制流的部分才交给 Agent。

## 最终判断标准

真正掌握“改模型”不是会说出 LoRA，DPO，GRPO 和 Agent，而是面对失败时能回答：

- 这是哪一层的问题？
- 最小修法是什么？
- 训练信号具体长什么样？
- 它可能损伤什么？
- 用什么独立评测证明修好了？
- 失败后怎样回滚和继续迭代？

能逐项回答，三册的“做模型—跑模型—改模型”才真正闭环。
