# 第 12 章 数据与评测

前面各章改变了模型或它的使用方式。SFT 教模型学习示范，蒸馏提供教师目标，偏好优化调整回答概率，Agent 则把检索，工具与多轮决策接入执行过程。每一种方法都可能让训练指标变好，但最后需要回答的仍是：它能否在没见过的任务上，更可靠地满足要求？

假设新模型的偏好损失下降，用户却觉得回答更啰嗦；多 Agent 搜索到更多网页，却把关键日期混淆；工具调用的 JSON 全部合法，订单仍取消错了。这些情况都说明训练信号，局部指标和最终任务之间存在差距。本章从数据的构造与划分开始，再把评测推进到真实执行结果。

## 12.1 任务与数据

### 先明确检查对象

“更聪明”“更像人”难以直接评分。可以先把需求拆成可观察行为：预算不超限，缺失信息时不猜，引用能支持结论，实际文件字段完整，未经授权不提交操作。

不同任务需要不同单位。SFT 样本是一段对话和监督标签；偏好样本是同一问题下的比较对；强化学习样本是带奖励与采样版本的轨迹；Agent 任务还要包含初始环境，用户约束和最终检查器。

如果把这些记录都压成 prompt 和 response 两列，就会丢掉权限，工具状态，来源和过程信息。数据格式应保留训练和检查真正需要的字段，再按具体训练器导出对应视图。

### 来源与版本

每条数据最好能追溯到原始来源，采集或生成时间，模板，标注者或教师版本，处理脚本和过滤规则。合成数据还要保存采样参数，验证器与筛选原因。

记录这些信息不仅为了复现。某批教师误解了“总预算”，可以按来源找到受影响样本；某个工具模板升级后，旧调用样本可以统一迁移或淘汰。没有来源，错误只能在混合数据中重新寻找。

用户数据还需要按权限和保留策略处理。去掉姓名后，订单号，地址组合或原始文档片段仍可能识别个人。训练，日志和评测副本应使用适当脱敏与访问控制，删除流程也要覆盖索引与缓存。

## 12.2 清洗与划分

### 去重

完全相同的文本可以哈希去重，近重复则需要相似度，规范化或语义判断。同一问题换几个字，答案完全相同，可能仍是同一信息。代码里只改变量名，文档里只换页眉，也不能视为独立样本。

过度去重也会误伤。预算题有相同模板，但数字和约束不同，仍可能是有价值的任务变化。去重规则要结合目标：用于防泄漏时宁可按同源题族分组；用于控制训练重复权重时，还需保留真正不同的边界情况。

### 分组划分

最简单的随机按行切分，容易让同一用户，文档，代码仓库或题目变体同时进入训练和测试。应先确定不能跨集合的信息组，再按组分配。

例如一份公司手册分成一百块，不能先切块后随机把九十块训练，十块测试，再声称测试的是未见文档。可以按完整文档划分；评估同文档检索能力时，又可以设计另一套明确允许读取整份文档的协议。

代码任务可按仓库或问题来源分组；业务对话可以按用户，时间或业务实体分组。时间切分有助于检查新规则与新问题，但也会引入真实分布变化，报告要说明这种难度来自哪里。

### 开发集与最终测试

训练集更新参数，开发集选择提示，超参数，技能和工具配置，最终测试检查锁定版本。只改提示也属于系统调优，不能因为没更新权重就反复在测试集上选最优配置。

某个测试失败被收入训练，之后同一题可以成为回归用例，但不能继续充当未见泛化证据。应分别保留已知问题回归集与未参与迭代的新测试集。

教师生成数据，示例库和检索库也要参加泄漏检查。测试问题如果通过 few-shot 检索被原样放进上下文，模型实际上看到了答案。RAG 评测可以允许检索知识来源，但要避免把问答标注文件也当作普通知识文档检索。

## 12.3 模型输出指标

### 损失与困惑度

验证交叉熵衡量模型给目标 token 的平均概率，困惑度为其指数。它可以检查语言建模是否退化，也能比较相同分词器和数据上的拟合变化。

不同 tokenizer 的每 token 交叉熵不一定可直接横比。后训练还可能改变回答风格和长度，使标准答案似然变化与任务成功率不同。模型能生成另一种正确回答，却对唯一参考措辞概率较低，验证 loss 就未必反映实际质量。

### 分类与提取

分类除了准确率，还应看每类 precision，recall，混淆矩阵和样本量。假设90%的请求都是“不取消”，全部预测不取消也能得90%准确率，却完全不会处理真正取消的用户。

字段提取应检查字段级准确率，完整记录正确率，缺失值处理和无依据补全。日期格式正确但时区错了，JSON 合法但预算对象错了，都应在语义检查里体现。

对生成文本，exact match 比较简单，但受同义表达影响。可以先做明确的规范化，例如数值单位，空白和大小写；规范化不能宽到把不同答案合并。金额，正负号和关键实体通常需要保留。

### 推理与 pass@k

每题采样一次并检查成功，可以报告对应采样协议下的 pass@1。采样 \(k\) 次只要一次成功，衡量的是候选集里包含正确答案的机会。它不代表系统已经知道该选哪一份。

从每题 \(n\) 次样本中观察到 \(c\) 次成功，在通常的采样与可交换假设下，\(n\ge k\) 时可用

\[
\widehat{\mathrm{pass@}k}
=
1-\frac{\binom{n-c}{k}}{\binom nk}
\]

估计随机选 \(k\) 个候选至少一个成功的概率。若错误样本数少于 \(k\)，分子按零处理。实现上可以用乘积计算，避免巨大组合数。

上线若只有一个选择器，应另报“生成 \(k\) 份后实际选出的成功率”。验证器有漏检时，这个指标可能远低于 pass@k。还要记录总生成 token，测试次数与时间，才能比较预算利用。

### 开放式生成

摘要，规划和写作没有唯一答案。可以把评分拆为事实，约束，覆盖，表达和依据，逐项给判断标准。比如“行程轻松”可具体检查每日主要地点数，交通耗时和休息区间，但仍需保留人工对整体体验的判断。

不能把“段落整齐”“引用多”“回答长”直接当作质量。它们可能与质量相关，也可能正是模型为了得分而堆出来的表面特征。

## 12.4 模型评审与人工

### 评审协议

使用模型评审时，给它原始任务，候选输出，必要证据与明确评分规则。隐藏作者身份，随机交换 A，B 顺序，检查位置偏好；对复杂任务要求指出具体违例，便于核查评分依据。

评审模型自身也会受风格，长度和措辞影响。可以用带已知错误的对照样本测它是否识别，抽样让人工复核；升级评审模型后，要重做校准，不能把前后分数当作同一标尺。

成对胜率还依赖对手。新模型对旧模型胜率高，不能直接与另一组完全不同对手的胜率横比。固定基线，提示和评审配置，才能解释变化。

### 人工分歧

复杂偏好存在合理分歧。可以记录一致率和具体维度，而不把多数票自动当作唯一真理。若某类样本标注者意见长期分裂，可能是评分标准不明确，或者任务本身应当允许多个选择。

人工评测还要控制顺序，身份和疲劳。一次给评审者过长的任务，容易漏看隐藏约束。可以分批，随机排列，设置质量检查题，并保留“无法判断”。

## 12.5 Agent 的最终状态

### 初始环境

Agent 评测需要固定任务开始时的数据库，文件，账号权限和工具版本。取消订单任务的订单是否可取消，查询页面是否已经更新，都可能改变成败。

使用数据库快照或容器镜像能提高可复现性，但还要固定依赖服务和时间。网页可能动态变化，可以使用可重放响应，也可以明确采用实时环境并保存观察。两者评估的性质不同。

模拟用户也应固定角色与可提供信息。若模拟器把隐藏答案主动说出，或者随模型措辞改变底线，结果会混入模拟器行为。交互基准如 τ-bench 将工具，业务规则与用户交互纳入任务，提醒我们单次文本分数不足以描述真实执行。[τ-bench](https://arxiv.org/abs/2406.12045)

### 检查产物

任务成功应尽可能检查环境状态。用户要求更新日历，就读取对应记录，核对日期，内容和数量；用户要求修改代码，就检查变更和测试；用户要求生成文件，就验证文件存在，可解析，字段完整。

助手最后说“成功”，不应直接得满分；也不能因为它的措辞不符合参考答案，就忽略实际已经正确完成的操作。文本与执行状态分别评估。

还要检查额外副作用。正确创建一条日历记录，同时误删另一条，不能算完整成功。检查器可以明确允许变更集合，比较前后状态差异。

### 轨迹检查

最终状态正确，有时仍包含不可接受行为。例如未经允许提交过操作，之后又撤销；反复访问不相关信息；把未授权用户的数据带进报告。这些问题需要查看执行轨迹和权限事件。

轨迹也帮助诊断。工具名选错，参数错，实体错，解析错误，忽略观察，计划不一致和提前结束，是不同错误类型。修复时应对应工具描述，数据，模型或 harness，避免只用一个失败标签掩盖全部原因。

### 稳定性

同一个任务重复运行 \(k\) 次全部成功，可以用 pass^k 一类稳定性指标表达，与“至少成功一次”的 pass@k 含义相反。一个系统十次能成功一次，与十次都成功，适用场景差别很大。

如果单次成功率为 \(p\)，且各次独立，全部成功概率为 \(p^k\)。实际错误会相关，环境也可能波动，所以应按重复任务记录直接计算，并保留每个任务的稳定性差异。

## 12.6 成本与统计

### 同预算

比较 CoT，自一致性，多 Agent，TTT 时，生成 token，并行资源和训练更新都可能不同。可以分别做固定成本下质量比较，以及达到固定质量所需成本比较。

报告至少区分总计算与墙钟时间。四个工作者并行可能缩短等待，却消耗更多总 token。服务还需看首字延迟，完整任务时长，P50 与尾部延迟，峰值显存，工具费用和失败重试成本。

成功任务平均耗时会隐藏失败后长时间重试。可以同时报告全部任务成本，以及每个成功任务对应的总成本；任务超时计入失败，并保存已经消耗的资源。

### 波动

假设测试100题，版本 A 做对80题，B 做对82题。两题差异可能来自采样波动，也可能是题目难度覆盖不足。只展示82%高于80%，不足以判断稳定收益。

独立二元样本下，成功率估计的标准误可以粗略写成

\[
\mathrm{SE}\approx\sqrt{\frac{\hat p(1-\hat p)}{n}}
\]

取 \(\hat p=0.8,n=100\)，标准误约为4个百分点。这只是近似；小样本或接近0，1时应使用更合适的区间方法。

比较两个系统时，尽量在相同任务上做成对比较。保留每题结果，按任务重采样计算 bootstrap 差值区间；同一任务多次 rollout 应成组重采样，避免把强相关的生成当作独立题目。数据按用户或仓库相关时，还要考虑更高层的分组。

### 分层结果

总体平均可能掩盖某类任务退化。可以按语言，长度，难度，是否需工具，是否含缺失信息与是否涉及状态修改分层。

一个模型在简单提取提升5分，在取消订单退化10分，总分可能仍上升。是否接受版本，要看业务优先级和硬约束，总体平均之外，还需要检查这些重要任务的变化。评分权重应提前确定，避免看到结果后临时调整。

## 12.7 评测系统

### 配置与记录

每次运行保存模型及适配器版本，tokenizer，模板，提示，示例选择，工具定义，技能，harness，数据和评分器版本。温度，top-p，生成长度，seed，超时，并行度和重试也应记录。

seed 不能保证所有服务与硬件完全确定，外部 API，异步时序和浮点实现仍会产生差异。记录的目的是把可控条件固定，并定位剩余波动。

静态任务可以借助 lm-evaluation-harness 等框架统一模板和聚合，执行任务则需要相应环境与检查器。框架支持某个任务，不代表默认配置就与论文或业务要求完全一致，仍应查看实际输入和答案提取方式。[lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)

### 一份任务定义

~~~yaml
task_id: itinerary_014
task_version: 3
initial_state: fixtures/itinerary_014.json
instruction: 根据给定约束生成三天行程草稿，不进行预订。
budget:
  model_calls: 20
  wall_time_seconds: 180
checks:
  - all_days_present
  - budget_within_limit
  - required_rest_intervals
  - citations_support_time_sensitive_claims
  - no_booking_operation
~~~

这里的检查名称需要对应具体实现。预算计算是否包含住宿，休息区间最短多久，引用哪些结论必须核对，都要写清。检查器应由可信执行环境运行，不能让被评测 Agent 修改评分文件后继续拿成绩。

失败可以返回结构化报告：哪项未通过，对应证据，实际状态与期望状态。报告供开发者迭代，但对最终测试不能无限开放重试与人工修复，否则评估的已经变成另一个协议。

### 消融

一次同时换模型，提示，技能，检索器和工具返回格式，结果变好也难判断原因。可以先固定其他部分，逐项修改；存在交互的组件，再开展组合实验。

消融并不要求遍历所有组合，而应围绕主要判断设计。例如多 Agent 的收益是否来自并行独立上下文，就比较单 Agent 同预算；TTT 是否来自参数更新，就比较相同额外采样但不更新的版本；新检索是否更好，就固定生成器检查证据召回。

## 12.8 回到数据迭代

评测失败是新的数据来源。先定位错误类型，再决定进入哪条改进路径。格式问题可能适合补示例或 SFT；事实缺失可能需要更新知识库；接口含义模糊可能应修改工具；奖励漏洞需要修验证器和反馈；状态丢失则可能属于 harness。

不能把所有失败都自动生成为一份正确答案再微调。工具实际无法执行时，训练模型更肯定地回答“已完成”只会掩盖问题。应以证据确认期望行为，并保留失败条件。

形成新训练数据后，要去重，检查来源和划分，运行小规模验证，再评估完整任务。已修复样本作为回归检查继续保留，未见测试继续承担泛化判断。这样每轮改变都有可以追查的依据，也能知道能力提升究竟发生在哪些任务上。

## 核心问答

**Q1：训练 loss 一直降，还需要做生成评测吗？**

需要。损失衡量对监督目标的拟合，生成还受到采样，输入分布，工具和环境影响。

**Q2：pass@10 高，线上一次回答就会好吗？**

候选集中有正确答案，不等于系统能选中。应另测选择器与真实交付成功率，并统计十次采样成本。

**Q3：同一个基准反复调提示算泄漏吗？**

即使不更新权重，测试表现也参与了系统选择。它应被视为开发集，最终结果需要独立未参与调优的数据。

**Q4：Agent 最后输出正确答案，为什么仍可能失败？**

执行结果，额外副作用，权限和产物也属于任务。文字正确不能代替真实状态检查。

**Q5：模型评审能替代全部人工吗？**

它能扩大评测规模，但需要校准与抽查。复杂主观标准和高影响错误，往往仍需人工判断。

**Q6：业务数据很少，怎样开始评测？**

先选有代表性的真实任务，明确每题检查规则，保留完整失败记录。规模小就如实报告不确定性，随着业务逐步补齐分层覆盖。
