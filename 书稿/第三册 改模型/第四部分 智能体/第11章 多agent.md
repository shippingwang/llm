# 第 11 章 多智能体

一个智能体可以连续执行多个步骤，也可以把部分工作交给其他智能体。每个工作者有自己的上下文，工具和执行状态，围绕局部任务完成多轮决策，再把结果交回。多个这样的过程共同服务于一个目标，就形成了多智能体系统。

我们可以让多个工作者同时调查不同方向，也可以安排它们依次处理需求，设计与实现，或者分别给出判断后再讨论。分工改变了每个模型能够看到的材料，也增加了任务分配，消息传递和结果整合。协作方式要与任务依赖一起设计，才能让这些独立调用完成同一个目标。

## 11.1 分工条件

多智能体最容易受益的情况，是任务包含相对独立的分支。不同资料来源可以分别调查，不同模块可以在接口明确后独立实现。每个工作者在自己的范围里取得足够证据，协调者再按共同标准合并。

依赖很强时，分工收益会下降。后一步必须等待前一步确定参数，多个工作者又频繁修改同一对象，沟通与等待可能成为主要成本。因此，拆分前应先表示任务依赖，再看哪些部分真的能够并行，而不能简单按角色名称增加模型。

设原任务中串行部分占比为 \(f\)，其余部分可由 \(n\) 个工作者理想均分，则加速上限为

\[
S(n)
=
\frac1{f+(1-f)/n}
\]

若 \(f=0.2\)，四个工作者的理想加速为 2.5 倍。这个估算尚未计入分配，汇总，限流与冲突。工作者增加后，串行协调比例还可能上升，实际耗时应按完整任务测量。

除了时间，多上下文还提供信息容量。一个工作者可以读取较多原始资料，在本地筛选与压缩，再把相关结果交给主智能体。这样避免主上下文接收全部搜索历史。不过，压缩也可能遗漏条件，工作者必须保留证据引用和未确定项，让协调者能够继续核查。

分工边界需要能够判断完成。“研究这个系统”范围过大，“列出指定模块中三个数据流入口，对应调用链与未确认依赖”则更清楚。目标，输入，允许动作和结果要求越明确，越容易减少重复探索与漏项。

一个局部任务还应具有足够工作量。若工作只是一条固定查询，直接并行调用工具就能完成，增加一个完整智能体可能带来额外输入与决策开销。只有局部过程确实需要根据结果继续判断时，独立上下文的价值才更明显。

## 11.2 协作结构

最容易组织的结构，是让一个主智能体持有总目标，其他工作者只处理分配给自己的部分。主智能体先判断哪些任务可以独立完成，再给出输入，约束和结果要求。工作者可以连续使用工具取得信息，完成后返回结论与证据。主智能体随后检查各部分是否一致，决定继续补查还是整合交付。

这种安排使工作者能够在自己的上下文里处理较多材料，但它也要求主智能体把必要条件传清楚。主智能体可以不读取全部搜索历史，却需要知道结论从哪里得到，还有哪些问题没有解决。如果某个工作者只能在共享文件里留下一句话，后续往往很难判断它已经核实了什么，因此局部结果应当带有可以继续打开的证据和产物。

另一些任务更适合交接。当前智能体识别出需要另一个领域或工具集合处理时，可以生成一份交接记录，由新的智能体继续负责这段工作。系统同时移交任务状态，相关材料和下一步要求，并明确结束后是否返回原协调者。这样可以减少每位工作者都读取全局历史的开销，同时使当前负责人有清楚边界。

在早期 AutoGen 的研究中，开发者可以把模型，工具与人工参与者组织成能够互相发消息的对象，再定义对话如何继续。例如，一个模型提出实现方案，另一个执行者运行代码，把结果或异常发回来，再由模型修改。角色可以使用模型，也可以由确定性程序承担，因此系统首先要定义谁收到什么消息，以及收到后调用哪个处理过程。

多人讨论时，还需要选择下一位发言者。可以固定轮换，按任务状态选择，也可以让管理者根据最近消息指派。不同方式改变了通信路径：固定顺序容易复现，动态选择更容易根据异常调整。运行程序还要识别完成条件，避免模型不断互相回应，却没有产生新证据或产物。

CAMEL 的研究则通过任务和角色提示，让两个智能体围绕同一个目标合作，一个提出要求，另一个据此完成工作。角色说明有助于保持职责，但我们仍然需要在消息里保存具体任务，执行反馈与结果。后续任务如果要求实际操作工具，还要把这些消息与真实执行连接起来，才能判断协作是否完成了目标。

当交付物之间有稳定依赖时，我们可以进一步固定阶段顺序。MetaGPT 的研究者把软件开发中的标准操作流程写入角色与提示，让需求，设计，实现和检查按产物衔接。这里，上一阶段提交的需求文档，接口约定或代码，成为下一阶段的输入，接收方据此继续工作。每个阶段要读什么，交出什么，都有较明确的要求。

这种流程适合依赖可以提前说明的任务。发生需求变更时，我们可以找到受影响的设计与实现，再让对应阶段重新处理。若任务在执行中不断发现新方向，则可以保留主智能体动态分派，在局部使用固定流程。实际系统可以同时采用几种协作方式，关键是让控制权，输入与产物的流向清楚。

## 11.3 任务与消息

子任务请求可以作为结构化对象传递：

~~~json
{
  "task_id": "subtask-03",
  "parent_id": "task-042",
  "goal": "核查导出模块的日期处理与相关测试",
  "input_refs": ["requirements-v3", "repository-snapshot-18"],
  "scope": ["src/export", "tests/export"],
  "allowed_actions": ["read", "run_tests", "write_own_report"],
  "output_ref": "findings/date-check-v1",
  "limits": {"model_calls": 8, "tool_calls": 20}
}
~~~

这里给出了目标，输入版本，工作范围与交付位置。任务还可以包含依赖，截止时间和失败处理。工作者读取明确版本后，结果也应注明基于哪一版材料，避免协调者把旧分析当成最新状态。

结果最好分为结论，证据，产物和未决事项。状态可以是 completed，partial，failed 或 waiting。partial 允许交回已完成部分，让协调者判断是继续派发还是缩小范围；failed 需要说明失败发生在哪一步以及已经产生哪些副作用。

产物引用应能被稳定读取。共享文件时附带版本或内容摘要，远端记录时附带对象 ID 和查询条件。主智能体收到结果后，可以只读取摘要，也可以按具体问题继续打开原文。引用让结果压缩具有可回查性。

消息还需要表达期望动作。一条补充信息可能只是通知，也可能要求正在运行的工作者改变方向；若工作者已经结束，则需要重新调度才能继续。把消息投递与任务生命周期分开管理，可以避免主智能体以为修改已执行，而工作者只保存了通知。

通信量可以从消息次数和接收者数量估算。若所有 \(n\) 个工作者彼此交换消息，一轮通信关系可达到 \(n(n-1)\) 个有向对；集中协调通常更容易控制总量，但主节点会承担汇总负担。实际系统可以按依赖定向沟通，减少无关材料传播。

摘要长度也影响质量。压缩得太狠，证据条件丢失；发送完整轨迹，又会使协调者上下文迅速增长。可采用简短结论加结构化字段，再附详细产物引用的方式。重要数值，版本和未决问题应显式保存，避免只依赖自然语言概述。

## 11.4 共享产物

多个工作者同时读材料通常比较简单，同时写同一对象则需要协调。一个修改覆盖另一个修改，是最直观的问题；更隐蔽的是文本合并没有冲突，接口语义却已经不兼容。共享产物的管理必须同时处理版本和含义。

编码任务可以按模块或文件分配所有权，在隔离工作目录中提交变更，再通过集成步骤合并。接口改动应先形成共同约定，下游基于指定版本工作。工作者修改超出范围时，可以提交建议或请求协调，避免悄悄改变其他分支的前提。

研究与写作任务也有类似问题。若多个工作者都直接写最终报告，后写者容易覆盖新证据。让工作者分别提交结果，由一个集成者维护最终产物，通常更容易追踪来源。最终文件仍需要检查完整性与口径，不能仅把各段摘要拼接。

合并事实时，先核对实体，时间和计量方式。两份数字不同，可能来自不同版本或统计范围。协调者可以把分歧转成一个具体核查任务，指定要验证的对象与来源，避免再次发起宽泛研究。

共享状态还应区分建议与生效结果。工作者提出修改，只有集成后才改变主版本；工作者建议执行外部操作，也不能由其他工作者各自重复提交。将真正提交集中到指定执行者，并使用第 10 章的操作 ID 与恢复机制，可以减少重复副作用。

集成完成后要重新验证。局部测试通过，只说明各分支在自己的条件下可用；合并后共同依赖，配置和接口可能改变。主任务的完成检查应针对最终版本执行，并保存验证结果与对应产物，才能使交付与实际状态一致。

## 11.5 调度与资源

多智能体需要子任务预算，也需要全局预算。若主智能体不断追加工作者，每个子任务都没有超限，总成本仍可能持续增长。调度器应同时限制总模型调用，工具量，活跃任务数，递归深度与截止时间。

总 token 包括主智能体输入输出，所有工作者输入输出，以及结果交接后再次被读取的内容。共享系统指令也可能在各工作者中重复处理。缓存能够减少部分 prefill，不能消除全部生成和工具执行成本。

实际时间则由关键依赖链决定。多个分支同时运行，主任务可能要等待最慢分支；若部分结果已经足以完成核心目标，可以先整合，再判断是否继续等待。截止时间附近，优先资源应给阻塞后续工作的关键节点。

取消需要沿任务树传播。主任务结束时，运行中的子任务，后台工具与待提交动作都要按规则处理。工作者超时重试前，也要查看是否已经写产物或执行过动作。换一个新工作者，不会使旧执行留下的副作用消失。

公开的 Anthropic 多智能体研究系统使用主智能体协调并行研究工作者，在其内部研究评测中取得相对单智能体更好的表现。它同时报告这类系统消耗较多 token，其样本中多智能体约为普通聊天的 15 倍。这个数字对应特定系统与任务分布，不能当作所有多智能体方案的固定倍率。

实际选型应以任务价值与预算为条件。广泛调查，长材料分析和接口清楚的模块工作，较容易利用并行上下文；频繁共享状态，连续操作同一个界面的任务，协调可能更困难。框架可以提供消息与调度能力，但不会自动生成合理分工。

还可以按任务粒度做资源实验。固定总预算，逐步增加工作者数量，同时缩小每个工作者的子任务，记录成功率，关键路径时间与交接量。最初可能因为并行获益，随后则因任务太小，共享输入重复和汇总负担增加而变差。转折点反映当前任务的可拆分程度，比预设一个通用工作者数量更有参考价值。

主智能体自身也会成为资源瓶颈。所有结果同时到达时，它需要在有限上下文里完成比较；若每份报告都很长，就会把节省的搜索时间花在读取与整理上。可以让工作者先提交结构化发现与冲突项，主智能体只对关键分歧打开详细证据。这个选择过程仍要保留覆盖检查，避免短摘要掩盖遗漏。

失败重派可以利用已有检查点，但接手者应先确认产物与当前环境一致。原工作者尚未结束时，直接再派一个执行同样写入，容易形成竞争。调度器可以先停止或隔离旧任务，再指定新的写入负责人；对于只读调查，则可以保留两个独立结果进行比较。不同副作用决定不同恢复安排。

## 11.6 集成与辩论

多个智能体除了分工，也可以独立处理同一个问题，再比较各自的答案。这样做主要增加候选与判断路径，适合检查单次生成是否遗漏了条件。为了保留独立性，我们可以先让各方分别作答，再共享结果；如果从第一轮就互相阅读，它们可能很快采用同一个思路。

Multiagent Debate 的研究者让多个模型实例先提出各自的答案与理由，再在后续回合看到其他回答，并据此修改自己的判断。我们可以把争议缩小到具体步骤：某个条件有没有使用，某个数字来自哪里，或哪个推导与已知事实冲突。若能调用计算器，测试程序或原始资料，讨论就可以继续取得证据，而不只是在不同措辞之间选择。

每一轮之后，系统要保存各方修改了什么，以及是否出现新依据。某位智能体被另一份流畅解释说服，可能只是改变了措辞；若它运行检查后发现了原答案的错误，才有具体证据支持修订。讨论可以在预算内继续，也可以把未解决的分歧交给指定审核者，最后由它回看题目和证据作出选择。

答案可归一化时，还可以使用多数票。假设三位判断者各自以概率 \(p\) 正确，并且错误独立，多数正确的概率为

\[
p^3+3p^2(1-p)
\]

第一项对应三位都正确，第二项对应恰好两位正确。独立假设成立且 \(p>0.5\) 时，多数票有机会改善结果。实际模型可能共享训练数据与检索来源，因此共同错误也容易出现。我们可以通过不同资料，不同求解路径或程序验证增加判断的独立性，再观察投票是否带来实际收益。

如果输出比较开放，无法直接归并成几个答案，可以让一个模型阅读多份候选，再生成综合结果。Mixture-of-Agents，MoA，研究了分层安排：一层中的多个模型分别生成回答，下一层把上一层的回答作为辅助输入，继续改进，最后取得汇总输出。这里增加的是多份生成内容及其后续整合，基本结构可以围绕同一个问题运行，不必让每个模型都维护长期工具任务。

汇总模型需要重新检查候选里的事实和条件。多份回答可能各自覆盖不同部分，也可能重复同一错误；合并时要根据任务选取有用内容，处理冲突和重复，再组织结果。候选越多，读取和整合成本也会增加，因此层数与每层模型数量应围绕实际质量收益设置。

审核者还可以采用另一种职责：它不重新写答案，只检查实际产物的某个维度，比如接口兼容，引用依据或测试覆盖，然后返回可复核的问题。生成者据此修改，检查者再验证相应变化。这样，独立生成，互相讨论，集中汇总和定向审核，分别适用于不同阶段，也可以组合使用。

比较这些安排时，我们可以给单智能体相近的总计算预算，再观察质量，完成时间和沟通量。对于分工，重点看独立任务是否真的同时推进；对于辩论与集成，则要看新增判断是否帮助修正错误。这样，增加模型调用的原因就能与它产生的具体作用对应起来。
