# 第 10 章 harness

一个智能体连续工作时，模型会提出动作，工具会返回结果，文件和外部状态也会不断改变。模型调用之间，必须有程序保存这些变化，决定什么时候继续，等待或结束，并在网络与进程异常后恢复任务。围绕模型承担这些工作的运行系统，通常称为 agent harness。

最初可以用一个循环连接模型与工具，随着任务变长，这个循环会逐渐包含状态管理，上下文构造，调度，权限，预算与验证。它决定每次调用看见什么，也决定模型输出怎样影响环境。因此，我们给同一个模型提供不同的上下文，工具与恢复方式，也可能得到不同的任务表现。运行程序需要把每次判断与已经发生的动作连接起来，让模型在下一轮获得足够准确的工作状态。

## 10.1 任务状态

对话消息保存了交流内容，却不足以描述正在执行的任务。工具可能已经开始运行但尚未返回，文件可能已经生成而没有被模型重新读取，用户也可能修改了原要求。运行系统需要额外保存这些可确定的事实。

一个基础任务记录可以包含：

~~~json
{
  "task_id": "task-042",
  "status": "running",
  "revision": 8,
  "goal_ref": "requirements-v3",
  "message_cursor": 27,
  "pending_calls": ["call-17"],
  "artifact_refs": ["report-v2"],
  "remaining_model_calls": 12
}
~~~

task_id 标识整个任务，revision 表示记录版本，message_cursor 指向已经应用的消息或事件。pending_calls 保存尚未完成的请求，产物引用则连接实际文件或对象。模型可以读取其中影响决策的部分，调度器使用完整记录管理执行。

任务状态可以区分 ready，running，waiting，completed，failed 和 cancelled。waiting 可能等待工具，也可能等待必要用户输入，两者应有不同原因与恢复条件。完成意味着交付条件已经满足；失败意味着本次执行无法按要求继续。保留这些差别，界面和后续调度才能正确解释结果。

除了当前状态，还可以保存追加式事件。事件记录模型请求，模型返回，工具准备，工具完成，产物创建与用户修改，包含时间，调用标识和结果引用。当前状态由这些事件逐步更新，既方便恢复，也方便诊断。

事件应用需要去重。服务可能重复通知完成，网络重连也可能重新发送已确认消息。若事件具有稳定 ID，状态记录保存已处理位置或标识，就可以避免把一次结果应用两次。多个进程更新任务时，还需要版本检查或锁，防止彼此覆盖。

产物最好使用版本或内容摘要。只有路径时，文件后续被修改，旧事件仍指向同一地址，却已经无法表示当时的结果。保存不可变快照或内容哈希，可以让检查与交接对应具体版本。对需要修改的工作文件，则另行记录当前工作副本与已提交版本的关系。

## 10.2 决策循环

harness 每一轮先应用已经到达的事件，再判断当前是否具备继续决策的条件。若关键工具仍在运行，可以等待；若存在独立工作，也可以继续。随后构造上下文，调用模型，解析它返回的是工具请求，必要提问还是最终交付。

核心过程可以用伪代码表示：

~~~python
def run_task(task):
    while not task.is_terminal():
        apply_ready_events(task)
        enforce_budget(task)
        if task.is_terminal():
            break

        if task.requires_external_event():
            persist_wait_state(task)
            return

        context = build_context(task)
        decision = model_call(context, task.generation_limit())
        persist_decision(task, decision)

        if decision.kind == "tool_calls":
            for call in decision.calls:
                prepared = validate_and_prepare(task, call)
                persist_prepared_call(task, prepared)
                dispatch_or_recover(prepared)

        elif decision.kind == "need_input":
            persist_question(task, decision.question)
            task.wait_for_input()

        elif decision.kind == "final":
            check = verify_artifacts(task, decision)
            if check.accepted:
                task.complete(check)
            else:
                add_verification_feedback(task, check)

        persist_task(task)
~~~

这里的函数表达职责，实际服务还要处理中断，流式返回和异常。预算检查发生在持续执行的边界，完成验证失败后也不能无上限重复；系统可以根据剩余预算继续修正，或者保存未完成原因。

模型输出本身需要解析。正常结束，达到输出上限和连接中断，会产生不同完整性。半段参数对象可以保留作诊断，但不能直接提交执行。若接口支持结构化返回，可以减少解析失败，仍需检查参数语义和任务约束。

完成验证尽量使用产物事实。生成报告可以检查文件存在，必要章节和来源字段；代码任务可以检查变更范围与规定测试；外部操作可以查询实际对象状态。开放式质量仍可能需要模型或人工评价，但“存在”和“写得好”应分别验证。

用户的新消息也进入事件序列。它可能补充条件，纠正目标或取消任务。运行程序先记录并更新版本，再在合适边界让模型读取。已经发生的外部操作不会因为新要求而自动消失，所以后续处理需要同时考虑新目标与实际状态。

## 10.3 上下文管理

任务日志可以很长，每轮模型输入只应包含当前判断需要的内容。稳定指令与工具描述，当前目标与约束，进度，近期交互和必要证据，通常具有较高优先级。旧的原始材料可以保留引用，后续按需重新读取。

可以把输入预算写成

\[
C
=
C_{\mathrm{rules}}
+C_{\mathrm{tools}}
+C_{\mathrm{state}}
+C_{\mathrm{recent}}
+C_{\mathrm{evidence}}
+C_{\mathrm{output}}
\]

各项共同受到上下文窗口限制。输出预算也要提前预留，否则系统可能读入大量材料后，几乎没有空间生成完整动作。工具目录与长返回往往占据较大部分，因此按需发现和结果摘要会直接影响可执行轮数。

压缩不能简单按时间删除。用户最初给出的限制可能贯穿全程，刚返回的一大段无关日志却可以立即缩短。选择时应看当前依赖，约束和证据价值。模型若不断重新读取相同材料，也可能说明任务状态没有保留已经取得的结论。

接近窗口上限时，可以生成交接记录，保存目标，约束，已验证进度，关键证据，当前产物，未决问题和下一步。精确字段由程序补入，模型整理需要解释的关系。接手后先读取记录，再检查相关文件与状态，恢复下一轮工作。

交接记录应允许纠错。摘要中的结论最好指向证据，暂定推测与已完成动作分开。否则，一次摘要把“计划运行测试”写成“测试已通过”，后续会在错误事实基础上继续。原始日志与产物版本使这种错误能够被发现和修正。

Anthropic 的长运行 harness 实践采用初始化与后续执行分工：先建立环境和功能清单，后续会话逐项推进，留下进度记录与可检查产物。其经验说明，上下文切换后的接手可以依靠外部状态组织。摘要，工作文件和验证记录共同承担连续性，单次聊天窗口不必保存所有细节。

前缀缓存可以降低重复处理稳定输入的成本，但缓存属于计算优化。模型版本，token 序列或配置变化后，缓存可能失效；服务重启也可能丢失驻留状态。因此，任务应能依靠持久记录重新构造输入，并按用户与权限范围隔离可共享内容。

## 10.4 调度与并发

模型一轮可以提出多个调用。若它们读取独立对象，可以并行；若后一个需要前一个的结果，则要等待。调用依赖可以用图表示，调度器只启动前置条件已满足的节点，并根据工具配额和资源限制控制并发数。

并行减少的是独立工作的等待时间，总工作量仍然存在。多个请求若共享同一后端限额，同时发起可能触发限流；多个文件写入若修改同一区域，也可能冲突。因此，依赖除了数据，还包括共享资源，对象版本和副作用。

工具结果按 call_id 归入对应请求。结果到达之后，可以立即触发决策，也可以等待一组相关调用收齐。前者更及时，后者减少模型反复读取不完整结果的次数。具体策略取决于后续工作是否能利用部分结果。

后台任务应有持久句柄。工具先返回 running 与 job_id，调度器记录进度查询，截止时间和取消方式，模型可以继续其他工作。作业完成后，以事件形式恢复决策。服务重启时，可以用句柄查询真实状态，而不必盲目重新启动。

如果任务中的调用关系已经能够表示成图，运行程序还可以根据依赖主动调度，减少模型逐次选择工具的次数。LLMCompiler 的研究者把这部分工作分为函数调用规划，任务分派与执行：规划器给出调用和依赖，分派器等待所需输入就绪，再把可运行任务交给执行器。模型主要处理计划与需要重新判断的结果，程序负责已经明确的依赖关系。

例如，三个独立查询可以先同时开始，某个分析只依赖其中两个，就可以在这两个结果返回后立即执行，不必等待第三个查询结束。后续还依赖第三个结果的汇总节点继续等待。调度器因此需要分别保存 pending，running 和 completed 等状态，以及每个节点依赖哪些结果；结果到达时，只检查受它影响的后续节点，就能够继续推进。

我们还可以让规划器逐步输出任务，分派器取得完整且合法的节点后就开始准备执行。这使计划生成与工具运行有机会重叠，但未准备好的参数和依赖仍需要等待。出现空结果或调用失败时，调度器可以先保存异常，继续独立分支，再将受影响部分交回模型重新规划。这样，程序完成确定的调度，模型处理需要新判断的情况。

错误需要按原因处理。网络暂时失败可以程序重试，参数错误通常需要模型修正，权限拒绝需要停止相应动作，环境缺失则可能要调整任务安排。重试策略应设置次数，间隔与总时间上限，避免多个失败调用同时密集重发。

异步任务还会遇到过期结果。用户修改目标之后，原查询可能仍会返回；结果可以保留为记录，但是否继续用于当前版本，需要重新判断。调度器可以给调用绑定任务版本和输入摘要，帮助识别它针对的是哪一版要求。

## 10.5 中断与恢复

最困难的恢复场景发生在外部动作与本地记录之间。服务已经写入数据，但 harness 尚未保存成功结果就崩溃。恢复后只知道请求发出过，却不知道是否执行完成，直接重发可能产生重复副作用。

一种常见安排是在发送前持久化准备记录，保存稳定操作 ID，参数摘要和预期前置条件；发送后再保存结果。恢复时先根据操作 ID 查询外部状态，或使用相同幂等键重试。能否可靠恢复，取决于服务是否支持去重，查询和版本条件。

本地事务不能把任意外部服务一并纳入原子提交。对不支持幂等与状态查询的操作，系统可能只能保存“结果未知”，再通过其他证据核实。这个不确定状态比直接宣告失败或成功更符合事实，也便于后续决定是否需要人工处理。

文件工作可以利用版本控制，快照与原子替换建立恢复边界。外部邮件，付款和发布则具有不同撤销条件，需要分别设计补偿动作。补偿也可能失败，因而应保存其状态，而不能把“已发起取消”立即当成“已撤销”。

暂停，取消与进程失败也有不同语义。暂停停止后续调度并保留恢复点；取消还要处理后台子任务和待提交操作；进程失败则需要在重启后重建状态。正在进行的操作能否中断，取决于工具实际能力。界面应据此展示等待，正在取消或已停止。

权限与准备结果可以绑定。若操作预览之后对象版本，参数或权限发生变化，旧的提交条件可能已经失效。提交前再次检查对应标识和范围，可以避免把旧授权或旧预览用于不同操作。已明确授权的范围可以持续使用，运行程序不必每轮重复询问。

以一个有幂等支持的外部写入为例，可以沿五个边界观察恢复：准备记录尚未保存时，不应已经发出请求；准备已保存但尚未发送时，可以按原操作 ID 继续；请求已发出而结果未知时，先查询或以同一幂等键重试；成功结果已保存但任务状态未更新时，重新应用结果事件；任务状态已更新后，重复通知只需要去重。每个边界对应不同动作，恢复程序无需依靠模型猜测发生了什么。

如果在提交前还需要检查对象版本，就把预期版本与操作一起保存。服务返回版本冲突后，任务转入重新读取与准备阶段，模型基于新状态判断原变更是否仍合适。更新后的参数形成新操作，旧记录继续保留。这样可以同时解释操作意图，失败原因和后续修正。

这类故障路径适合在开发阶段主动注入。分别在发送前，服务处理后，结果保存前后终止进程，再恢复同一任务，检查外部对象是否重复变化，任务是否错误结束，以及运行中的作业是否仍可找到。正常路径跑通之后，这些测试决定系统能否承受长任务中的真实中断。

## 10.6 预算与观测

我们可以从任务开始到结束记录实际耗时，再分别统计模型请求，工具执行，网络与排队等待。多个调用并行时，执行区间可能重叠，因此各项耗时相加后，可能高于用户实际等待的时间。计算费用则要累计输入与输出 token，工具服务和后台计算等用量，并设置总截止时间，调用次数及重试上限，控制完整任务的资源使用。

可以为每轮记录

\[
C_{\mathrm{task}}
=
\sum_j
\left(
C_{\mathrm{input},j}
+C_{\mathrm{output},j}
+C_{\mathrm{tool},j}
+C_{\mathrm{other},j}
\right)
\]

并另外记录缓存命中，等待时间与执行时间。价格可以随服务变化，原始 token，设备时间和工具调用量则有助于跨版本比较。预算接近上限时，可以缩小剩余探索范围，优先完成关键依赖，保留尚未核实的部分。

轨迹记录应能回答三个问题：模型看见了什么，它决定了什么，环境实际发生了什么。模型输入版本，工具参数，错误类别，产物版本和验证结果共同形成诊断依据。敏感内容可以按访问范围保存，展示层使用必要片段与引用。

常见低效可以从轨迹定位。重复搜索可能来自状态遗忘，反复读取长文件可能来自检索接口不足，修改后没有验证可能来自完成规则不清。针对这些模式改善上下文，工具或检查机制，通常比在提示里增加一句“认真完成”更具体。

harness 自身也需要测试。可以模拟重复通知，调用超时，进程重启和用户中途修改，检查状态是否保持一致。模型能力评测则在可重置任务中运行同一套系统，再由独立检查器评价结果。模型，工具和运行程序的版本都应固定，才能分析哪一部分带来了变化。

对持续运行的任务，我们可以先根据轨迹找到具体失败，再调整相关组件：查询反复发生时检查结果是否进入状态，交接后遗漏约束时检查摘要，恢复后重复写入时检查操作记录。每次修改针对一个可观察问题，再运行相同任务验证，运行系统就能逐步积累更可靠的处理方式。

## 10.7 DeepSeek Harness

我们可以用 DeepSeek 公开的 DeepSeek Harness 看这些设计怎样组成一个运行系统。这个项目使用 dsh 作为命令入口，以 Cordis 管理插件，将模型连接，工具，会话，存储和界面分别组合。阅读它的实现时，可以先沿一次请求看控制流程，再看哪些功能由插件接入。这样，我们既能理解一次任务怎样执行，也能找到改变某种行为时应该修改的组件。

启动时，程序按 profile 加载一组配置。公开实现中的 web，headless 和 sdk 等运行方式，共用由 dsh-base 提供的基础组件，再增加各自需要的界面或调用入口。我们可以使用下面的命令查看 web 方式实际装配的插件，检查模型适配器，工具和持久化服务是否已经启用：

~~~sh
dsh --profile web --dump-config
~~~

profile 决定本次启动使用哪些组件，插件则把能力注册到运行环境。比如，文件工具注册读取和编辑，模型适配器负责把内部请求交给相应模型服务，持久化插件负责保存会话。负责运行循环的代码通过这些服务工作，所以我们调整存储方式或增加工具时，可以修改相应组合。主要组件可以按职责理解：

| 组件 | 负责的工作 |
|---|---|
| core/session | 追加会话事件，并从事件生成模型需要的消息历史 |
| core/system-prompt | 汇总当前指令，运行上下文和可见工具说明 |
| core/agent-loop | 接收输入，组织模型请求，并决定是否继续下一步 |
| llm | 提供请求与流式返回的公共类型，由适配器连接模型 |
| core/tools | 管理工具定义，由选定执行器完成调度与结果记录 |
| session-persistence | 将会话事件写入存储，并提供读取与恢复接口 |

这些组件使用同一份 Session 连接。用户输入，模型输出，工具调用和工具返回都追加为事件，后续模型请求再从事件记录生成消息。我们因而可以同时保留完整执行记录，以及当前需要送给模型的内容。界面也能够根据这些记录显示进度，重新打开会话时继续呈现已有结果。

下面沿一个文件修改任务看具体过程：用户要求检查导出程序对空数据的处理，修改实现，并运行已有测试。文件与测试名取决于实际项目，这里重点观察请求怎样经过各个组件。输入进入当前 Agent 的待处理队列，循环准备开始时创建 turn；在这个 turn 内，每次模型请求及其随后执行的工具组成一个 step。一次用户任务可能经过多个 step，工具返回之后，程序会根据剩余输入与结果继续决定是否请求模型。

在第一个 step，system-prompt 组件取得当前指令和工具说明，循环再从 Session 生成历史，并交给模型适配器。模型可能先请求搜索相关文件，或者调用 read 查看已知路径。read 接受 file_path，以及可选的 offset 和 limit，返回带行号的内容。模型获得的是文件工具提供的结果，循环把这份结果追加到 Session 后，后续请求就能使用刚读到的代码。

为了看清事件与调用的关系，可以把一段过程简化为下面的顺序。这里省略了系统指令变更和请求元数据，只保留任务推进所需的主要事件：

~~~text
turn/start
  step/start
    user/message       用户要求
    assistant/message  模型请求读取文件
    tool/call          记录 read 请求
    tool/result        保存读取结果
  step/end

  step/start
    assistant/message  模型根据源码请求 edit
    tool/call          记录修改请求
    tool/result        保存实际修改结果
  step/end

  后续 step：运行测试，读取反馈，必要时继续修改

  step/start
    assistant/message  模型说明修改与验证结果
  step/end
turn/end
~~~

事件中的 callId 将请求与结果对应起来。模型一次返回多个工具请求时，执行器会为每个请求保留这项关联，避免并发返回后混淆对象。默认循环读取模型输出中的工具调用，将整批交给工具执行器，待这一批处理完成，再决定下一次请求。普通工具返回后，模型通常还要继续解释结果或完成后续工作；如果工具明确返回了结束当前 turn 的信号，循环则按该状态处理。

执行器还会判断哪些调用可以并行。公开文件工具将 read 标记为可并发，write 和 edit 则按独占操作处理。因而，同一步中的多个独立读取可以重叠执行，写入前后则需要保留相应执行顺序。执行结束后，结果仍按模型调用顺序记录。我们可以在批量读取时减少等待，又让下一次请求得到稳定对应的调用与结果。

模型读完代码之后，可以用 edit 对指定文字进行替换，也可以用已启用的补丁工具完成多处修改。文件操作由工具与文件系统服务共同执行，结果里保存是否成功及相应变更信息。模型随后可以调用 shell 运行项目中已有的检查，读取退出状态和必要日志，再决定修改是否完成。如果测试失败，它就能根据具体反馈继续处理，而不必凭自己刚才写出的修改推断测试结果。

这里还有一个可以通过组合调整的细节。如果我们要求模型修改已有文件之前先成功读取，并且写入时检查读取版本是否仍有效，可以启用 fs-observation-policy。该插件在文件操作前检查观察记录，文件已经变化时，返回 FS_STALE_VERSION 等错误，要求重新读取。所查看的基础配置默认关闭了这项策略，因此部署时需要按目标显式启用。启用之后，这个条件由执行过程检查，模型可以根据错误重新取得内容，再提交更新后的修改。

任务执行时，用户也可能补充要求。运行循环通过 inbox 接收这些输入，并区分下一步进入的消息与后续 turn 的排队消息。这样，我们可以在一个检查步骤结束后把补充条件交给模型，让它据此调整后续修改。已经完成的工具结果继续保留在 Session 中，新要求与旧事实都能在下一次判断中使用。

长任务还需要处理上下文增长。DeepSeek Harness 将这部分工作放在 compaction 组件中，由 token 计量判断请求是否接近所用模型的容量。压缩时可以先处理过大的工具返回，再选择适当的历史范围生成摘要，同时保留近期内容。选择范围时要保持工具调用与结果的配对，使后续请求仍能解释每项观察来自哪个动作。

压缩过程也写入事件，记录开始，摘要与结束，再通过新的记录改变后续消息的生成方式。旧事件继续保留，新的请求则可以使用缩短后的历史。对于文件修改任务，我们可以让当前上下文保留最新代码与测试失败位置，把较早的搜索过程整理成摘要；需要核查时，再回到原始记录或重新读取文件。这种安排同时支持继续推理和执行追溯。

事件记录还要及时写入存储。公开实现提供 JSONL 持久化后端，并另外使用 session-checkpoint-policy 安排写入时机。Session 先组织事件，存储服务接收追加，检查点再通过 flush 等待必要记录可靠写入。对外部存储而言，追加被接受和已经能够承受进程崩溃之间，可能还有缓冲与写入过程，因此程序需要在重要执行边界等待确认。

这项检查点策略连接了三个位置：模型请求发出之前，顶层工具真正执行之前，以及前一步的响应与工具结果进入下一步之前。假如工具即将修改文件，程序先保存对应调用；写入确认失败时，就停止这一执行。这样，后续恢复至少能够知道程序已经准备执行哪个动作，以及哪些结果已经有记录。

如果进程在工具执行期间崩溃，恢复逻辑会读取已保存的事件，补齐尚未结束的 step 与 turn，并处理没有结果的调用。已经记录开始但缺少结果的工具，使用 TOOL_OUTCOME_UNKNOWN 标记；尚未记录执行开始的请求，则按未开始处理。接下来的模型能够看到这一区别，再判断是重新读取，核对文件状态，还是重新尝试。

对于刚才的文件修改任务，如果 edit 已经改变文件，但结果尚未保存就中断，恢复后就应重新查看相关内容和变更，再决定是否继续修改或运行测试。即使程序已经保存了调用意图，也仍需要通过文件实际状态核对执行结果。相同处理也适用于外部操作：服务是否已经完成写入，需要由对象查询或幂等机制进一步确认。

插件组合还使这些行为能够分别调整。我们可以保留同一套循环和工具，替换模型适配器；也可以保留模型，改变上下文压缩或持久化策略，再比较同一组任务的表现。扩展插件通过 Agent 接口和运行事件参与过程，例如在请求前准备上下文，在工具前检查条件，在结果后记录统计。这些注册随各自作用范围管理，卸载时也需要清理，避免旧行为继续影响后续调用。

这个案例里，模型负责根据代码和反馈选择下一动作，运行程序则负责组装请求，执行工具，保存事件与恢复状态。沿着一次文件修改追踪这些职责，就能把前面的状态，循环，上下文和检查点连接起来。排查任务失败时，我们也可以回到相应位置，判断是模型选错动作，工具没有完成，还是运行系统没有把已有结果正确交给下一次请求。
