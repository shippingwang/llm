# 第 9 章 Agent 核心 下：工具交互，Skill

智能体决定查询一个对象或修改一份文件之后，还需要把这个决定交给程序。模型输出，接口参数和真实执行之间存在一段明确的转换过程：先生成请求，再验证与执行，最后把结果组织成模型能够继续使用的观察。

我们需要给模型说明工具的用途，参数和返回形式，让它能够根据当前任务选出合适操作。对于比较复杂的工作，还可以让模型生成程序组合多个操作，或者读取一套已有流程，按规定步骤使用工具。接口，执行环境和流程说明共同影响模型怎样完成实际任务。

## 9.1 调用消息

一个工具通常有名称，功能描述和参数结构。模型在当前任务下读取这些信息，选择工具并生成参数。执行器解析请求，找到相应程序，运行后返回结果。结果进入后续上下文，模型据此决定是否继续调用或交付答案。

例如，一个读取订单的接口可以声明：

~~~json
{
  "name": "get_order",
  "description": "按订单标识读取当前状态，条目和可执行操作。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string"}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
~~~

描述说明工具的适用范围，schema 说明参数的结构约束。模型还需要从问题，查询结果或已有状态中取得真实 order_id。schema 可以限制它生成字符串，却不能保证这个字符串对应正确订单。

一次具体请求应有调用标识，返回也应关联同一个标识：

~~~json
{
  "call_id": "call-17",
  "name": "get_order",
  "arguments": {"order_id": "ord-204"}
}
~~~

执行器返回的内容可以包含状态，结构化结果和必要说明。call_id 用于关联请求与结果，order_id 则标识业务对象，两者作用不同。多次读取同一订单，会有不同调用；一次调用超时重试，也可能需要另外的业务操作标识来判断是否重复执行。

模型发出工具请求后，当前生成轮次通常结束，由运行程序接手执行。工具结果再进入新一轮输入。函数名看起来像代码，并不表示它已经在模型内部运行；工具请求中的参数也只是待执行内容。这个边界使模型能够表达复杂意图，同时让确定性校验与业务操作由程序负责。

多工具返回还需要保留各自状态。某个读取成功，另一个查询失败，模型应当知道哪些信息已经取得。把所有结果拼成没有来源的一段文字，会增加错误引用和混淆对象的机会。结构化返回可以与简短摘要并存，原始内容则按引用保存。

把一次任务沿消息展开，可以更清楚地看见工具能力的来源。模型先读取 get_order 的描述，再根据已有上下文填入订单 ID。执行器返回订单仍在处理中，当前版本为 6，模型据此知道尚未完成，也知道后续修改应针对版本 6。如果返回不存在，下一步就应核对标识或取得补充信息；如果返回服务暂时不可用，则属于另一种恢复分支。

之后的每一步都使用已经取得的观察。模型不能仅根据工具描述猜测订单里有哪些条目，也不能把一次查询解释成已经修改。如果用户要求的工作确实包含修改，模型可以先构造变更，执行器核对对象和前置条件，再将真实结果交回。最终回答从执行返回组织，使“准备了什么”“执行了什么”和“仍待处理什么”各有依据。

对训练而言，这段轨迹中的困难通常不只在参数拼写。对象是否选对，空结果怎样处理，旧版本何时失效，以及工具返回怎样改变后续行动，才决定多轮任务的成功。工具示例与评测也应覆盖这些状态变化，才能检验模型是否真正会使用接口。

## 9.2 接口设计

接口粒度决定模型要做多少次决策。工具过细，完成一个普通任务需要多轮读取和参数拼接；工具过粗，一个动作又可能包含许多难以检查的副作用。适合的边界通常对应一个语义清楚，结果可验证的工作单元。

读取，准备和提交可以分成不同操作。读取返回当前事实；准备计算待执行变更，并给出预览与版本；提交在条件仍然有效时完成写入。这样模型可以先核对对象和结果，程序也能在真正写入时检查版本与操作范围。具体是否需要用户确认，应由已有授权和应用规则决定。

参数应尽量使用稳定标识与明确单位。日期说明时区，金额说明币种与单位，分页说明游标含义，文件修改说明基准版本。把多个含义塞进一个自由文本字段，虽然容易接入，却把本可确定的解析问题再次交给模型。

默认值也会改变动作。默认覆盖旧文件，默认使用当前日期或默认选择第一条记录，都可能在信息不足时产生意外结果。默认值适合表达确实稳定的常规行为；对影响对象或副作用的参数，可以要求明确给出，或者在准备阶段返回待确定项。

错误返回应有可用语义。参数类型错误可以指出字段与期望类型，版本冲突可以返回当前版本，空结果可以提供已执行的筛选条件。模型看到具体反馈后，才能区分改参数，重新查询和停止等待。只返回一个笼统 error，通常会引出猜测式重试。

返回长度需要服务于下一步。搜索接口可以先给标题，片段和内容引用，文件接口可以按范围读取，表格接口可以返回 schema，行数和有限预览。大结果存储后，通过句柄继续查询，避免每轮都把全部内容送入模型。

有些任务适合把计算留在程序里。模型生成筛选或统计代码，让执行环境处理大量记录，再返回聚合结果，可以减少上下文传输。但程序需要明确输入范围，执行时间和结果检查；模型生成的脚本同样要经过执行器管理。减少 token 与保证计算含义正确，需要共同考虑。

模型什么时候调用工具，也可以通过数据学习。Toolformer 的研究者先用少量示范生成候选调用，再实际执行，观察加入工具结果后能否改善后续文本预测，用这个条件筛选训练样本。这样，我们可以从已有文本构造“在什么位置使用什么工具”的示范。对于完整任务，还需要让模型看到实际返回和后续处理，使它学会根据结果继续行动。

## 9.3 程序式行动

模型通过函数调用可以表达一次明确操作，但有些任务还包含循环，条件判断和中间计算。如果我们把每个小动作都拆成一次模型请求，就需要反复把中间结果放进上下文。对于规则已经清楚的部分，可以让模型先写出程序，再由执行器完成计算，把结果交回来。

PAL，Program-aided Language Models，较早研究了这种分工。模型读取自然语言问题，把条件和关系转成程序，解释器再计算结果。比如，模型负责确定哪些变量参与计算，怎样表达公式，Python 则负责数值运算和数据处理。这样，我们可以把计算交给已有运行时，并通过程序检查中间量。程序是否正确表达了题意，仍然要从变量，约束与输出之间的关系核对。

进一步处理多步工具任务时，我们可以让程序直接调用环境提供的函数。CodeAct 的研究者使用可执行 Python 代码表示动作，执行后把输出或错误交回模型，模型再据此修改代码或生成下一步动作。相比只生成一个固定函数请求，模型能够在同一个动作里组合多个调用，使用条件和循环，并保存中间变量。

假设执行环境已经提供查询和写入结果的函数，模型可以生成下面的程序，对已核对的数据进行筛选与统计：

~~~python
rows = query_rows(table="orders", status="completed", limit=5000)
selected = [row for row in rows if row["currency"] == "CNY"]

result = {
    "count": len(selected),
    "amount_cents": sum(row["amount_cents"] for row in selected),
}
artifact = write_json("summary.json", result)
print({"summary": result, "artifact": artifact})
~~~

这里，工具函数和字段约定由执行环境提供。模型先选择要读取的数据和计算规则，程序再完成批量处理，返回统计值与产物引用。若需要在所有记录上统计，就应继续处理分页，或者直接使用后端聚合接口；示例中的 limit 只覆盖本次返回范围。模型取得这些结果后，可以决定是否已经满足要求，再生成解释或继续操作。

执行器还可以保留同一会话中的变量。第一轮读取数据，第二轮检查缺失值，第三轮生成结果，就不必每次把全部记录重新编码成文本。模型只需读取必要预览与汇总，再让程序处理数据。程序输出也可以按结构化结果和日志分别保存，使模型看到的内容与实际产物对应。

程序出错时，执行器返回异常类型，位置和必要上下文，模型据此修正。语法错误通常发生在执行之前，运行错误则可能发生在一部分动作已经完成之后。对于包含写入的程序，重新运行之前要先检查已产生的文件或外部操作，避免把成功部分再次执行。我们可以把长程序分成可恢复阶段，每完成一段就保存结果，再继续下一段。

面向代码任务的 SWE-agent 还研究了另一种接口设计。研究者为模型组织文件搜索，带范围的读取，编辑与执行反馈，使它能够持续定位和修改项目。这里既要考虑动作能表达什么，也要考虑执行后返回什么信息。一个编辑接口若能立即指出语法问题，模型就能在继续修改之前修正；一个读取接口若带行号和上下文，就更容易把错误定位到实际文件。

这些做法可以共同使用。稳定且语义明确的业务操作适合保留为函数接口，批量数据处理适合交给程序，界面任务则根据元素和截图执行。模型在每轮取得结果后再判断下一步，运行环境负责保存执行状态，并提供可以继续检查的反馈。

## 9.4 MCP

当智能体接入多个工具服务，每个服务都自定义描述，调用和返回格式，客户端就要维护大量适配代码。Model Context Protocol，MCP，为应用与工具服务之间提供统一协议，使工具发现，资源访问和调用能够按共同结构组织。

MCP 中，host 是承载智能体的应用，client 是 host 内与服务通信的连接组件，server 提供能力。模型通常不会自己建立网络连接；host 读取 server 提供的描述，选择性地交给模型，再把模型的请求转换为协议调用。

协议使用 JSON-RPC 2.0 表达消息，并通过初始化交换版本与能力。server 可以提供 tools，resources 和 prompts：工具表达可执行功能，资源提供可读取内容，提示模板提供可复用消息。它们可以共同帮助应用取得上下文，但用途和调用方式需要区分。

一次典型接入包括连接，初始化，发现工具，映射描述，执行调用和处理返回。server 的工具列表变化时，host 还需要刷新可见能力。若采用分页发现或按需加载，也要让模型有办法找到尚未进入当前上下文的工具。

通信协议不会自动解决业务语义。两个服务都提供 search，可能搜索不同数据；参数相同的两个 update，也可能有不同覆盖行为。因此，工具名称，描述，输入 schema 和返回语义依然决定模型能否正确使用。标准化减少接入差异，接口质量仍需要逐个验证。

身份和权限还应由连接与服务实现处理。host 可以持有用户授权的访问范围，server 再对实际请求校验。返回的文档与工具说明属于外部输入，是否可信需要由应用确定。协议中的只读，破坏性等注解有助于表达意图，但不能直接替代真实访问控制。

MCP 的部署产物是一组可复用连接与工具服务，未必需要重新训练模型。成本主要来自发现与描述输入，网络交互，服务计算和结果传输。工具数量很多时，逐轮注入完整目录会明显增加上下文，因而按需发现与选择也成为运行系统的一部分。

## 9.5 Skill

工具说明某个操作怎样调用，较长任务还需要知道如何组织多个操作。Skill 将任务步骤，领域约定，模板与可复用程序打包，让智能体在适用时读取并执行这套流程。

一种公开的 Agent Skills 结构以 SKILL.md 为入口，包含名称，描述和正文，并可以附带 scripts，references，assets 等目录。名称与描述帮助系统识别适用任务，正文说明步骤和检查，脚本负责可重复的确定性处理，参考材料提供较详细的领域信息。

按需加载使这些材料不必从任务开始就全部进入上下文。系统先读取简短元信息，确定任务相关后再读取主体，执行到某一步时继续打开具体脚本或参考。这样把“能找到流程”和“当前必须阅读全部材料”分开，降低常驻输入。

一个好的 Skill 应表达操作条件和结果，而不只是给出一份泛化清单。输入材料在哪里，采用哪个格式，什么时候需要补信息，脚本会生成哪些文件，完成后用什么检查，都应能够支持具体执行。对于稳定计算，直接使用经过验证的程序通常比让模型每次重写更容易复现。

Skill 的存在不会扩大工具权限。正文可以要求读取一个目录，但执行器仍按当前访问范围处理；脚本涉及网络，写入或外部操作时，也要遵守任务已有授权。应用需要知道技能来源和版本，避免同名更新改变原有行为而没有被发现。

验证 Skill 时，可以固定任务集合与模型，比较未加载流程，只提供正文和提供完整程序包的差异。观察最终成功率，也记录调用次数，输入长度，失败恢复和产物质量。若收益主要来自某个脚本，就应明确这个程序的贡献；若模型仍频繁误判适用条件，则应改进入口描述与选择策略。

## 9.6 执行与恢复

模型产生调用之后，执行器通常分三步处理。首先校验结构，确认字段，类型和必要参数；其次校验语义，确认对象，单位，版本和前置条件；最后检查当前操作是否在授权范围内。通过后再执行，并把实际状态持久化。

只读查询通常可以在临时网络错误后重试，写操作则要考虑重复副作用。请求已经到达服务，结果却在返回途中丢失，客户端无法仅凭超时判断是否成功。稳定的幂等键让同一逻辑操作能够被识别；状态查询让恢复程序先核对结果，再决定是否重发。

幂等键应绑定操作含义。改变金额，目标对象或版本之后，继续使用原键可能得到错误复用；每次网络重试都生成新键，又会失去去重作用。参数摘要，业务操作 ID 与调用 ID 因此需要各自管理。

长任务可以返回作业句柄。执行器记录 job_id，状态与截止时间，模型先继续其他独立工作，再读取进度。完成通知和主动查询可能同时得到结果，运行系统要确保只应用一次。任务取消后，后台作业也需要按约定结束或保留，避免模型停止输出后资源仍然长期占用。

代码执行提供通用计算能力，可以批量处理数据，调用库和生成产物。执行环境应控制目录，依赖，网络和资源，返回退出码，有限日志与产物引用。语法执行成功只说明程序运行完毕，业务结果还需要检查；测试脚本与被测程序最好保留独立来源。

界面操作则通过页面元素或屏幕位置表达动作。页面可能在两次操作之间变化，所以点击前的观察与点击后的确认都重要。元素标识通常比固定坐标更容易跨布局复用，截图则能提供结构化页面没有表达的视觉信息。两种方式可以组合，并通过状态回读确认操作是否真正生效。

执行器保存调用，返回与产物版本之后，模型便能根据确定的任务状态继续工作。网络中断或进程恢复时，程序也可以先核对这些记录，再决定查询结果，重试操作还是重新请求模型判断。
