# 第8章 Agent 核心 上：感知，规划与记忆

模型回答一个问题时，通常先读取输入，再生成一段文本。可是，许多任务在开始时还没有准备好全部材料。我们可能需要先查资料，运行程序，或者打开页面，才能知道接下来该做什么。如果让模型把整个过程一次写完，它只能根据已有信息推测后续情况；如果允许它执行一步，读取真实结果，再决定下一步，求解过程就能随着环境变化继续推进。

我们把围绕目标持续作出判断，并通过工具与环境交互的系统称为智能体，Agent。它可以使用现成的语言模型，配合检索，执行程序和记忆完成工作。具体怎样安排这些组件，会形成不同方法：可以逐步决定动作，也可以先写计划；失败后可以总结经验再试，也可以同时保留几个候选方向继续搜索。

## 8.1 任务与观察

开始执行之前，我们首先要明确模型能够看见什么。用户通常给出目标和限制，环境则通过工具提供观察。比如，模型要修改一个导出功能，可能先拿到问题描述，再搜索代码，读取相关函数和测试结果。每次读取都只覆盖环境的一部分，当前上下文里没有出现的信息，仍然需要通过后续动作获取。

设用户要求为 \(x\)，第 \(t\) 次观察为 \(o_t\)，模型之前执行的动作为 \(a_1,\ldots,a_{t-1}\)，那么当前可见历史可以写成

\[
h_t=(x,o_1,a_1,o_2,\ldots,a_{t-1},o_t)
\]

模型根据这些内容选择下一动作：

\[
a_t\sim\pi_\theta(\cdot\mid h_t)
\]

这里的动作可以是检索，读文件，执行代码，也可以是向用户补充提问或交付答案。工具执行之后，环境返回 \(o_{t+1}\)，我们把它加入历史，再调用模型。这个循环把语言生成与实际执行连接起来，使模型能够根据刚取得的材料改变后续安排。

不同任务需要不同形式的观察。处理网页时，可以给模型页面正文，可访问性树或截图；处理代码时，可以提供目录，符号和带行号的内容；处理数据表时，可以先提供字段，数据类型和少量记录。我们选择哪种形式，取决于下一步判断需要哪些信息。结构化页面容易定位按钮，截图能补充布局与视觉细节，长日志则可以先提取错误位置，再按需查看上下文。

观察还应保留对应对象和版本。同一个函数可能在搜索后被修改，页面也可能在两次点击之间刷新。把来源，时间和版本一起保存，模型才能解释新旧结果为什么不同。它提出动作之后，也要继续读取返回状态：请求被接受，作业运行中，以及结果已经生成，分别对应不同进度。下一次判断以这些实际反馈为条件，整个任务才会沿着已经发生的事情继续。

## 8.2 ReAct

假如模型已经知道有哪些工具，最直接的办法是让它每次决定一个动作，执行后再继续。可是，如果我们只让它连续输出调用，它可能很快偏离原目标，或者没有解释当前信息还缺在哪里。因此，可以让模型在行动前先整理已有发现，说明还需要取得什么信息，再选择能够补充这些信息的工具。

ReAct 的研究者把这个过程组织为 reasoning 与 acting 的交替，名字也来自这两个词。原始形式通常写成 Thought，Action，Observation：模型先生成当前推理与行动意图，再发出请求；程序执行请求，把返回值作为观察交给模型；模型根据观察继续判断。这里，Thought 和 Action 由模型生成，Observation 来自环境。下一次推理可以直接使用刚取得的证据，而不必提前猜测工具会返回什么。

我们可以用一段简化轨迹理解这个安排。任务是找出某个配置项在哪里生效，工具包括搜索文件和读取指定行：

~~~text
判断：先找到配置项的定义与引用位置。
动作：搜索配置项名称。
观察：找到定义文件，以及两处读取位置。

判断：其中一处属于测试，先查看实际运行代码中的读取方式。
动作：读取对应函数及其上下文。
观察：函数只在初始化时读取配置，并把值保存到实例字段。

判断：还需要确认后续请求是否重新读取这个字段。
动作：搜索实例字段的使用位置。
观察：请求处理直接使用已保存的值。
~~~

在这条轨迹中，第二步的选择依赖第一次搜索得到的位置，第三步又依赖读取函数后取得的新名称。我们在任务开始时未必知道全部符号，因此很适合逐步行动。模型每轮还会说明当前判断，使它能够把新观察与原问题联系起来，最后解释为什么修改配置可能需要重新初始化。

原始 ReAct 在多跳问答，事实验证和交互任务中研究了这种方式。实现时，我们可以通过提示示例让已有模型采用这种过程，也可以让支持工具调用的模型使用结构化消息表达动作。用于执行的参数和供用户阅读的说明可以分开保存，运行程序只把完整合法的请求交给工具。这样，模型可以保留必要分析，工具执行仍由程序管理。

ReAct 的灵活性来自每轮重新观察，但连续调用也会增加开销。若每执行一步都要重新提交任务说明，历史和长工具结果，模型会反复处理相同材料。对于已经能够提前确定的几个独立查询，逐个等待并再次决策，可能花掉很多时间。于是，我们需要进一步判断：哪些步骤必须等观察之后才能决定，哪些可以先安排好，再交给执行器连续完成。

## 8.3 计划与执行

当任务包含几个明确阶段时，我们可以先让模型给出整体计划，再逐项执行。这样做能够减少遗漏，也让系统更容易判断还剩哪些工作。Plan-and-Solve 的提示方法就先要求模型把问题拆成子问题，再按计划求解。它主要研究推理过程中的任务分解；把相似安排用于工具系统时，还需要由程序真正执行各个步骤，并把结果带回模型。

在 Plan-and-Execute 这样的运行方式中，可以分别安排规划和执行。规划阶段给出子目标，依赖和完成条件，执行阶段只处理当前子目标。完成一段工作之后，规划器读取结果，决定原计划是否继续有效。规划器和执行器可以使用同一个模型的不同调用，也可以采用不同模型；实际需要分开的是职责和输入信息。

计划的粒度应当足以指导执行，同时留出根据新发现选择具体动作的空间。“完成实现”很难用来判断进度，而在尚未读代码时就列出全部编辑命令，又会过早依赖猜测。更合适的阶段可以是确认数据格式，定位转换逻辑，修改实现，再用规定输入检查结果。每个阶段都有可观察产物，内部动作则由执行时取得的信息决定。

如果后续操作形式已经明确，只是参数尚未取得，我们还可以先用变量表示这些结果。ReWOO，Reasoning WithOut Observation，的研究者据此把流程分成 Planner，Worker 和 Solver。这里强调先在规划阶段确定操作与依赖，实际证据再由工具执行取得。规划器先写出步骤及证据引用，执行器调用工具填入实际结果，最后求解器根据计划和证据组织答案。规划期间可以不知道证据的具体内容，但要知道后续怎样使用它。

下面使用自定义工具说明这种引用方式。任务是比较两家公司同一财年的收入，目标年份已经确定：

~~~text
#E1 = 查找年报(公司="甲公司", 年份=目标年份)
#E2 = 查找年报(公司="乙公司", 年份=目标年份)
#E3 = 提取收入(年报=#E1)
#E4 = 提取收入(年报=#E2)

求解：核对 #E3 和 #E4 的单位与统计范围，再完成比较。
~~~

执行器先取得两份年报，再将返回内容或引用代入后续请求。模型无需在第一次查询返回后，重新阅读全部历史来决定“接下来提取收入”。这里的 #E1 等是结果占位符，执行之后才具有实际值，所示工具和语法只是对这种数据依赖的表达。

这种安排适合操作关系较明确的任务。若找到的年报类型不同，提取工具返回了多个收入项目，或者目标文档根本不存在，系统就需要把异常交回模型，补充选择或修改计划。我们可以保留一部分预先规划的流程，只在出现需要判断的结果时重新调用模型。这样，逐步决策与计划式执行可以共同使用，具体取舍由信息依赖决定。

计划还会因用户要求或环境变化而失效。重新规划时，可以先确认哪些结果仍可复用，再修改受影响的后续步骤。已经完成的读取和验证保留为事实，尚未执行的动作则可以替换。这样，模型能够修正安排，也能继续利用已经取得的证据。

## 8.4 反思与搜索

模型完成一次尝试之后，还可以根据反馈继续修改。最简单的做法是先生成结果，再让它按任务要求检查，写出具体问题，最后结合这些意见生成新版本。Self-Refine 的研究者用同一个语言模型完成生成，反馈和修订，在一次任务内反复改善输出。整个过程可以只靠多次推理完成，参数保持不变。

要让修订有明确方向，反馈最好对应可以检查的内容。模型可以指出缺少了哪个条件，哪一步计算不一致，或哪段文字没有回答问题；如果有程序返回的错误位置，也可以一起提供。下一轮读取原结果和反馈，再修改相应部分。我们还需要保留原版本，因为修改可能解决一个问题，却引入另一个问题。判断是否继续，可以依据要求是否满足，外部检查结果，以及是否还出现有实质内容的新反馈。

如果一次执行已经失败，需要从头或从某个检查点重新尝试，我们还可以把失败原因写入经验记忆。Reflexion 的研究者把行动者，评价者和反思模块连在一起：行动者完成一轮尝试，评价者根据结果给出反馈，反思模块把轨迹和反馈整理成文字经验，再在后续尝试时提供给行动者。下一次便能看到上一次哪里没有成功，以及建议改变什么。

这里需要保存的是有条件的经验。例如，某次检索失败，是因为只搜索了字段的展示名称，后来才发现代码使用了另一个内部名称。反思可以记录这个遗漏，并建议下一轮先查映射关系。这样的内容能够影响具体行动，比“下一次更仔细”提供了更多信息。论文所说的 verbal reinforcement，主要通过文字反馈和记忆改变后续决策，基本流程不要求做策略梯度更新。

反思仍然需要依据。如果评价器只说任务失败，模型可能错误归因；如果测试日志已经给出了失败位置，反思就有更具体的材料。因此，实际系统可以把执行反馈作为已知事实，再让模型提出解释和修改建议。建议经过下一次执行验证后，才逐渐成为可靠经验。

逐次修改只保留当前版本，搜索则允许同时保存几个方向。LATS，Language Agent Tree Search，将语言模型的推理与动作组织为搜索树，并结合蒙特卡洛树搜索分配尝试次数。一个节点保存当前历史和相关环境状态，子节点代表从这里采取的不同后续。模型负责提出候选，搜索程序则决定先探索哪一条，取得结果后再更新节点统计。

一种常见的选择方式是 UCT：

\[
U(s,a)
=
Q(s,a)
+
c\sqrt{\frac{\log N(s)}{N(s,a)}}
\]

\(Q(s,a)\) 记录从状态 \(s\) 选择动作 \(a\) 后，已经观察到的平均回报；\(N(s)\) 是父节点访问次数，\(N(s,a)\) 是这个分支的访问次数。第一项倾向于继续尝试已有较好结果的方向，第二项给尝试较少的方向额外机会，\(c\) 控制探索的权重。尚未访问的节点要单独处理，通常优先给它一次尝试，再进入这个公式。

选到待扩展节点之后，程序让模型提出几个候选动作，执行或模拟后取得观察，再用评价模型和环境反馈估计哪些候选更值得继续。走到终局后，把实际结果沿路径回传，更新访问次数与回报。这里更新的是搜索树的统计，语言模型参数可以保持固定。LATS 还会记录失败轨迹与反思，在后续生成和评价时使用这些内容。因此，搜索保存的不只有文字分支，还包括每条分支尝试过多少次，以及得到什么结果。

对于纯文本推理，回到某个节点可以恢复对应前缀。涉及文件，浏览器或其他环境时，则要恢复相应状态，才能公平比较后续动作。代码任务可以使用独立工作目录或快照，模拟环境可以重置；真实外部写入则需要按其实际撤销能力处理。先确定可以怎样恢复，搜索树上的分支才有清楚含义。

## 8.5 检索

行动过程中，模型经常需要补充尚未掌握的事实。我们可以把文档放进知识库，检索与当前问题有关的片段，再交给模型处理。这就是检索增强生成，RAG，在运行时的基本使用方式。智能体还可以根据已取得的内容继续检索：第一次找到实体名称，第二次查它的属性，遇到冲突时再核对版本与原始来源。

建立知识库时，我们先解析正文，表格与标题，保留来源和位置，再把长文档划成可检索片段。如果片段太短，限制条件容易被拆散；如果太长，送入模型时又会夹带许多无关材料。因此，可以尽量沿章节，段落或代码符号切分，并在命中后提供相邻内容的读取方式。这样，检索先找到位置，进一步阅读再补齐语境。

向量检索用编码器分别表示查询和片段，再根据相似度选择候选。它适合寻找措辞不同但含义接近的材料，关键词检索则更容易保留版本号，接口名和标识符等精确信息。我们可以同时运行两路召回，再做排序融合。比如，倒数排名融合写为

\[
\operatorname{RRF}(d)
=
\sum_j\frac1{k+\operatorname{rank}_j(d)}
\]

其中，\(j\) 表示检索器，\(\operatorname{rank}_j(d)\) 是文档在该路的名次，\(k\) 是平滑常数。某个片段在多路结果中都靠前，就更容易进入后续候选。接下来还可以用重排模型同时读取问题和片段，进一步判断相关性，再把选中的内容放进生成上下文。

智能体取得检索结果后，要判断当前信息是否足以继续。例如，接口说明已经解释了参数，却没有说明失败返回，那么下一次可以定位实现或相关测试。我们把“调用方式已确认，错误处理待确认”保存成工作状态，下一轮就能围绕缺口继续查。每次查询都对应尚未解决的问题，材料也就能够逐步积累为完成任务所需的证据。

资料之间发生冲突时，可以先检查对象，时间与版本。新版本的实现和旧文档可能同时被召回，模型需要说明当前结论采用了哪一个条件。重要结论应保留原文位置，后续写作或验证时能够重新读取。为了减少输入，我们可以把片段提炼成事实摘要，同时保留引用，使压缩之后仍有办法核对上下文。

知识库的主要开销来自解析，嵌入，索引和在线检索。假设保存 100 万个片段，每个向量为 1024 维，使用 16 位存储，仅向量本体约为 2 GB，还要另计索引和原文。在线任务则取决于召回数量，重排次数和送给生成模型的长度。智能体可以先看有限结果，再按需继续读取，避免每次把所有候选都送入长上下文。

## 8.6 记忆

一次任务执行得越久，模型需要保留的信息就越多。当前上下文适合放目标，关键约束，近期动作和必要证据，旧日志和大段工具结果则可以保存在外部，后续按引用读取。跨会话时，我们还可以保存稳定偏好，任务经验和已确认事实，再根据新任务检索回来。

MemGPT 的研究者采用分层存储，让模型通过相应操作在当前上下文与外部记忆之间调入，调出信息。外部存储保存较多历史，当前窗口只保留本轮需要处理的部分。实现时，可以给记忆条目分配标识，提供搜索和读取工具，让模型先找到相关记录，再选择需要进入上下文的内容。

Generative Agents 则在交互模拟中保存观察记录，并在检索时结合相关性，近期程度与重要性选择内容，再从积累的事件中生成较高层的反思。这给出了两种不同的存储单位：一类保存具体发生过什么，另一类概括这些记录可能说明什么。后续规划既可以读取原始事件，也可以利用经验，但概括应保留依据，才能在出现新信息时重新判断。

对实际任务，我们可以进一步区分工作记忆，事件记录与长期知识。工作记忆回答当前正在做什么，哪些步骤已经完成；事件记录保存动作，返回和产物；长期知识则保存经过确认且仍有复用价值的内容。它们可以使用同一套存储设施，却有不同写入和更新方式。用户修改当前要求时，我们更新工作状态；外部事实过期时，则应修改知识记录与对应索引。

写入记忆也需要一个筛选过程。我们先判断新信息属于哪类，再检查是否与已有记录重复，冲突或替代。一次模型提出的假设，可以先留在任务工作区；取得执行或原始资料支持后，再标记为已确认。失败尝试也值得保存，但要附带失败条件和反馈，下一次检索到时才能知道这是一条被排除的路径。

上下文不足时，可以生成交接记录，保留目标，限制，已完成且有证据的动作，当前产物和未决事项。程序掌握的路径，版本与调用状态可以直接写入，模型负责解释这些信息之间的关系。后续会话先读记录，再查看关键产物，就能从一个较明确的状态继续，而不必重新推测先前做过什么。

记忆最终要通过后续行动发挥作用。某条经验没有帮助到任务，可能因为没有被写入，没有被找回，或者找回之后没有被正确使用。因此，检查时可以沿这几个阶段回看，再决定调整写入方式，检索条件还是当前上下文。这样，长期保存的内容才能逐步成为后续决策可使用的材料。
