# 第五部分 评测、服务与部署

**目的**：能启动不等于能上线。这一部分补齐评测、容量、稳定性和端侧约束，最终产物是一套能解释成本、守得住 SLO、坏了能恢复的系统。

# 第 18 章 推理系统评测与容量规划

> **开场问题**：压测报告说 QPS 达标，上线后 p99 天天超标，而 GPU 利用率只有 60%。差在哪？

## 18.1 一份可比较的结果必须声明什么

模型、精度与量化方案、硬件型号、并行配置、引擎版本、输入长度分布、输出长度分布、并发或到达率、采样参数、是否命中前缀缓存。少声明任何一项，数字就没法和别人比，甚至没法和自己上周的结果比。

"这张卡上这个模型能跑 3000 tokens/s"是一句没有信息量的话。

## 18.2 闭环压测会骗你

**闭环**（发一个请求、等它返回、再发下一个）永远压不出排队问题：系统慢下来时，压测客户端自动就发得慢了，队列永远不会堆积。它测出的是"系统在自己舒服的节奏下能跑多快"。

**开环**（按设定的到达率持续发，不管前面有没有返回）才能暴露真实的排队行为和 p99。生产流量是开环的，压测也必须是。

另外两个常见自欺：不做 warmup（首次运行含编译、显存分配、图捕获）；反复用同一个 prompt（前缀缓存全命中，数字虚高）。

## 18.3 延迟—吞吐曲线和那个膝点

把并发从低到高扫一遍，画出吞吐和 p99 延迟的曲线。典型形状是：吞吐先线性上升然后饱和，p99 在接近饱和点时突然陡升。

**容量规划要定在膝点之前**，而不是最大吞吐点。因为真实流量有抖动，压在膝点上意味着任何一次小高峰都变成 SLO 事故。留多少余量取决于流量的波动性，通常是把稳态利用率控制在膝点对应负载的 70%–80%。

## 18.4 Goodput：把 SLO 写进指标

只有在 SLO 内完成的请求才算数。TTFT 超过 2 秒的请求，用户可能已经关掉页面了，它消耗的算力是纯浪费。

Goodput = 单位时间内满足 SLO 的请求数（或 token 数）。用它做优化目标，很多决策会反转：比如某个配置吞吐更高但 p99 更差，按 throughput 看是赢的，按 goodput 看可能是输的。过载时主动拒绝一部分请求，按 throughput 看是损失，按 goodput 看是保护。

## 18.5 成本账

最终要能回答：每百万输入 token 多少钱、每百万输出 token 多少钱、每个成功请求多少钱。

算法是：卡的小时成本 ÷ 该小时内的有效 token 产出。但要把这些计入分母之外的损耗——空闲容量（为应对峰值预留的）、失败重试、超出 SLO 的无效产出、以及缓存未命中导致的重复计算。

输出 token 通常比输入 token 贵一个量级（Prefill 可以大批量并行，Decode 每个 token 都要读一遍权重），定价和容量规划都必须分开算。

### 核心问答

**Q：为什么不能只报 tokens/s？** 它可能是靠巨大 batch 堆出来的，对应的单请求延迟完全不可接受；而且没区分输入输出。

**Q：p99 高，先查什么？** 把 p99 请求的时间拆成排队、Prefill、Decode 三段，看哪段长。通常是排队（容量不足或调度不公）或被长 Prefill 打断。

**Q：为什么压测要模拟真实长度分布？** 长度直接决定 Prefill 工作量、KV 占用和 Decode 时长。用固定长度压测得到的结论在真实流量下经常不成立。

**Q：怎么公平比较两个引擎？** 同模型、同精度、同硬件、同长度分布、同到达率，比 goodput 和每百万 token 成本，而不是比峰值吞吐。

# 第 19 章 生产级模型服务

> **开场问题**：半夜流量突增三倍，系统应该慢一点还是拒绝一部分请求？

## 19.1 网关、路由与接纳控制

**网关**做鉴权、配额、协议转换。**路由器**选副本，判断依据不只是负载，还包括前缀缓存命中（把同一会话送回原副本，收益常常大于负载均衡本身）和模型/适配器亲和。

**接纳控制**是最容易被忽略却最重要的一环。队列无限长不是"更宽容"，只是把失败变成超时——用户等了 30 秒才拿到错误，比 1 秒内被拒绝更糟，而且这期间的算力全浪费了。系统应该根据当前队列长度和 KV 余量估算新请求的预期完成时间，超出 SLO 就直接拒绝或降级。

## 19.2 过载时的降级顺序

流量超出容量时要有预设的降级链，而不是临场决策：

1. **关掉投机解码**（第 14 章：高并发下它本来就没收益）
2. **收紧 token 预算**，让调度偏向吞吐
3. **限制单请求的最大输出长度**
4. **按优先级限流**，保低优先级之外的流量
5. **拒绝新请求**，保住已接纳的

每一级都要可观测、可手动触发、可自动回退。降级悄悄发生而没人知道，会变成更难查的问题。

## 19.3 弹性扩缩容和它的滞后

推理服务的扩容不是秒级的：拉起容器、加载几十上百 GB 权重、编译或捕获 CUDA Graph、warmup，全流程可能几分钟。**这意味着按当前指标触发扩容，等新实例就绪时高峰可能已经过去了**。

对策包括：按预测而非当前值扩容、保留一定比例的热备实例、把权重放在本地 SSD 或用共享内存加速加载、以及缩容要比扩容保守得多（缩错了要几分钟才能补回来）。

触发指标也不该用 GPU 利用率——Decode 阶段带宽打满时算力利用率仍然很低。应该用队列长度、TTFT 的 p95、KV 占用率这些直接反映服务质量的量。

## 19.4 故障与重试

流式生成中途失败是个特殊难题：已经吐出去 200 个 token 了，剩下的怎么办？重新生成会得到不同内容（采样有随机性），用户会看到前后不连贯。

系统要按阶段区分处理：还在排队 → 直接换个实例重试，无副作用；Prefill 阶段失败 → 重试，用户只感觉慢了点；Decode 中途失败 → 要么带着已生成内容和固定种子在别处续上（需要 KV 迁移或重算），要么明确告诉用户中断。**默认的无脑重试在这里是错的**。

TP 组内单卡故障会让整组不可用，这是纵向切分的代价；多副本部署下故障只影响一个副本，这是它的优势之一。

## 19.5 可观测性：至少这些指标

按模型和租户维度拆分记录：QPS、输入/输出长度分布、TTFT、ITL、端到端延迟（都要 p50/p95/p99）、队列时间、运行中请求数、batch 大小、KV 占用率、前缀缓存命中率、抢占次数、投机解码的接受长度、拒绝和超时率、OOM 和 GPU/NCCL 错误。

关键在于**能把一次慢请求归因到具体阶段**：trace 要贯穿网关、调度器、worker，并在每个阶段打时间戳。没有这个，p99 上升时只能靠猜。

## 19.6 灰度、回滚与版本

可以改变输出的东西比想象的多：权重、量化方案、引擎版本、采样默认值、对话模板、tokenizer。**它们必须作为一个整体制品打版本**，回滚时一起回滚。只回滚权重而留着新模板，是典型的事故放大方式。

上线流程应该有 shadow traffic（复制真实流量到新版本但不返回结果，对比输出和延迟）和 canary（小比例真实流量），且两者都要看质量指标而不只是性能指标。

## 19.7 多租户

不同租户的优先级、配额、数据隔离要求不同。三个要点：**前缀缓存不能跨越安全边界**（第 11.5 节）；**配额要按实际资源消耗计**，而不是按请求数（一个 100K 上下文的请求抵得上几百个短请求）；**要防止单个大租户长期占满**，通常用按租户的并发上限加上公平调度。

### 核心问答

**Q：为什么 GPU 利用率不适合做扩容指标？** Decode 是带宽受限的，带宽打满时算力利用率可能只有 20%。应该用队列、TTFT、KV 占用这些贴近服务质量的指标。

**Q：过载时为什么要主动拒绝？** 无限接收会让所有请求都超时，goodput 归零。拒绝一部分是为了保住剩下的能正常完成。

**Q：新量化模型上线只测准确率够吗？** 不够。要测各业务切片、长上下文、结构化输出稳定性，还要测延迟和显存变化——量化可能改变最优 batch 配置。

**Q：为什么模板和 tokenizer 要和权重一起版本化？** 它们直接改变模型看到的输入和输出解析，单独变更等于换了个模型，还会让前缀缓存失效甚至串号。

# 第 20 章 端侧模型部署

> **开场问题**：模型文件 4 GB，8 GB 内存的手机为什么跑不动？

## 20.1 端侧的约束是"共享"

和数据中心最大的区别：端侧的内存、带宽、算力都是和整个系统共享的。应用不能把 8 GB 全用掉——操作系统、其他应用、以及你自己应用的 UI 都要占。可用预算通常只有总内存的一小部分，超了会被系统直接杀掉。

峰值内存比模型文件大小重要得多：权重 + KV + 中间激活 + runtime + 应用本身。开场问题的答案通常就在这里。

## 20.2 端侧量化的现实

INT4 是常态，但**格式必须匹配目标 runtime**。同样是 4 bit，group size、对称还是非对称、权重的打包布局、scale 的存储方式，各家 runtime 要求都不同。把数据中心的量化文件直接搬到手机上，大概率加载不了，或者加载了走的是慢速回退路径。

选型顺序和第 16.9 节一样：先确认目标芯片的原生指令和 runtime 支持，再谈算法。

## 20.3 异构执行的陷阱

端侧 SoC 上有 CPU、GPU、NPU。理想情况是把模型跑在 NPU 上，但 NPU 的算子覆盖有限，遇到不支持的算子会回退到 CPU。

**一次回退可能比全程 GPU 还慢**，因为跨设备要拷贝数据，而端侧的各计算单元共享内存带宽。划分子图时必须把边界传输的成本算进去，有时"全部跑在 GPU 上"比"大部分 NPU 加几次回退"更快。

判断方法：逐算子 profile，看有没有意外的设备切换。

## 20.4 交付物是一个整体

端侧交付不是给一个权重文件，而是一个自洽的包：固定的计算图、内嵌的权重、tokenizer、采样逻辑、停止条件、以及版本元数据。

第一册的规则在这里同样适用——**给端侧的应该是一个文件，而不是一堆需要对方自己拼的零件**。任何需要接入方"自己实现一下前后处理"的地方，都是未来 bug 的来源。

## 20.5 持续性能：温度和功耗

手机跑前十个 token 很快，跑十分钟会越来越慢——温控降频是端侧独有的现象。只测短时性能会严重高估实际体验。

端侧的验收必须包含：长时间连续生成的速度曲线、峰值内存、功耗和电池消耗、以及降频后的稳定速度。这几项比首 token 延迟更能决定用户是否愿意持续使用。

## 20.6 端云协同

现实产品大多是混合的：简单请求本地处理（快、省钱、隐私好），复杂请求上云。端侧模型还可以承担意图识别、草稿生成（给云端做投机解码的草稿）、隐私字段过滤等辅助角色。

系统层面要处理的是：断网时的降级路径、端云两侧模型版本不一致时的行为差异、以及切换决策本身的延迟（判断该走哪边也要花时间）。

### 核心问答

**Q：4 GB 的模型为什么 8 GB 内存跑不动？** 还要加 KV、激活、runtime 和应用自身，且系统不会让单个应用占满内存。要按峰值内存而非文件大小规划。

**Q：同一个 INT4 模型在两台手机上速度差三倍，正常吗？** 正常。低比特只是存储格式，是否有原生指令、高效 kernel 和匹配的布局才决定速度。

**Q：NPU 利用率高就说明部署得好吗？** 不一定。如果有频繁的算子回退和设备间拷贝，端到端反而更慢。要看端到端时延，不是单设备利用率。

**Q：端侧最该测什么？** 峰值内存、持续生成速度（不是前十个 token）、温控后的稳定速度、功耗，以及真机上的任务质量。

# 尾声 训练、推理与部署综合设计

第二册的验收不是"会用某个框架"，而是能独立完成下面三道题，并让每个选择都落到数字上。

## 题一：预训练集群

给定 70B 稠密模型、8K 序列、1024 张 GPU、固定 token 预算：

1. 用第 1 章的方法算出单卡放不下的是哪一项。
2. 按第 7.1 节的决策顺序定 TP / CP / FSDP / DP，并说明为什么 PP 用或不用。
3. 选优化器（第 8 章），说明它对显存和收敛的影响，以及学习率要怎么定。
4. 估算每卡显存、每步通信量、step 时间和 MFU。
5. 设计数据管线、检查点周期（用 goodput 求最优）、故障恢复和监控项。

## 题二：在线推理服务

给定一个 MoE 模型、真实的输入输出长度分布、TTFT 和 TPOT 的 SLO：

1. 决定副本数、TP、EP，以及要不要 PD 分离（并说明判据）。
2. 算出权重和 KV 的显存占用，推出最大并发。
3. 设计调度：token 预算、分块 Prefill、前缀缓存策略、接纳控制和降级链。
4. 判断投机解码在哪个并发区间开、哪个区间关。
5. 用 goodput 和每百万 token 成本验收，给出延迟—吞吐曲线和容量建议。

## 题三：端侧交付

给定目标 SoC、可用内存、功耗预算和质量下限：

1. 选量化精度和要保高精度的层，说明依据。
2. 确认 runtime 的算子覆盖，排查可能的回退点。
3. 打包成单一制品（图、权重、tokenizer、采样、版本）。
4. 在真机上完成长时间性能、峰值内存、温控和质量验收。

## 你现在应该能回答

- 这个方案为什么放得下？每一项显存花在哪？
- 它为什么是这个速度？瓶颈是算力、带宽、容量还是排队？
- 流量翻倍，最先坏的是哪里？
- 某项优化省了什么、把代价转移到了哪里、在什么工作点上会反转？
- 出现 OOM、吞吐下降、p99 恶化或质量回退时，按什么顺序排查？

能用数字回答这五个问题，而不是报框架名，才算真正掌握了工业级大模型技术。
