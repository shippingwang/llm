# 第一部分 硬件性能与资源模型

**目的**：训练和推理优化不是背框架参数，而是能判断"GPU 此刻在等什么"。先把显存、算力、带宽和网络说清楚，后面所有技术才有共同语言。

# 第 0 章 GPU 系统与分布式计算基础

> 本章是速查表。熟悉 CUDA 和分布式训练的读者可以跳过，但建议看一眼 0.4 的四个集合通信——本册后面所有并行策略的通信代价都会还原成这四个操作。

## 0.1 存储层级：所有优化的起点

从快到慢、从小到大：**寄存器和共享内存**在计算芯片内部，延迟以纳秒计但总共只有几十 MB；**HBM** 就是通常说的"显存"，几十上百 GB，带宽 TB/s 量级；**CPU 内存**更大更慢，要过 PCIe；**本地盘和对象存储**负责长期保存。

每往下一层，带宽掉一个数量级左右。记住这个梯度，就能理解本册大部分技术的动机：**它们几乎都是在减少跨层搬运**。FlashAttention 是把中间结果留在共享内存不写回 HBM；算子融合是减少 HBM 往返；量化是减少从 HBM 读的字节数；offload 是主动往下层放，用速度换容量。

## 0.2 算力与带宽：两个独立的预算

一张卡有两个独立的上限：每秒能做多少浮点运算（TFLOPS），每秒能从显存搬多少字节（GB/s）。

关键是它们的**比值**。现代 GPU 的算力增长远快于带宽增长，比值通常在每字节数百次浮点运算这个量级。这意味着：如果一个操作每读 1 字节只做几次运算，它必然把 GPU 的算力闲置着——不是你写得不好，是这个操作的性质如此。

大矩阵乘（Prefill、训练）落在算力受限一侧；逐元素算子和单 token 的 Decode 落在带宽受限一侧。分清一个操作在哪一侧，决定了优化方向是"少算"还是"少搬"。2.2 节会把这件事形式化。

## 0.3 GPU 之间怎样通信

同机 GPU 通过 NVLink/NVSwitch 互联，带宽几百 GB/s；跨机走 InfiniBand 或 RoCE，通常低一个数量级，且延迟明显更高。

两个维度都要看：**带宽**决定大张量传输的耗时，**延迟**决定小而频繁的同步的耗时。张量并行每层都要通信且数据量不大，它卡在延迟上，所以必须留在机内；数据并行每步一次大规模 AllReduce，它卡在带宽上，跨机尚可接受。这条区别会在第 5、7 章反复出现。

## 0.4 四个集合通信

- **AllReduce**：所有卡的数据求和（或其他归约），每张卡都拿到完整结果。DDP 同步梯度用它。等价于 ReduceScatter + AllGather，所以实际传输量约为数据量的 2 倍。
- **ReduceScatter**：求和后切开，每张卡只拿走属于自己的那一片。ZeRO/FSDP 聚合梯度用它。
- **AllGather**：把各卡手上的分片拼成完整张量，每张卡都拿到完整的。FSDP 计算前恢复参数用它。
- **AllToAll**：每张卡把不同的数据块发给不同的目标卡，是一次"转置"式的全交换。MoE 专家并行的核心，也是最吃网络的一个。

## 0.5 最低工具栈

要能读懂 PyTorch Profiler 或 Nsight 的时间线（哪段在算、哪段在通信、哪里有空洞），知道 NCCL 是做 GPU 集合通信的库、它的超时和错误日志怎么看，理解 CUDA stream 可以让计算和通信并发执行。

框架名字每年都在变，这些机制不会。

### 核心问答

**Q：显存够了，程序为什么还慢？** 容量只决定能不能跑。速度取决于算力、显存带宽、卡间通信和调度空洞，它们是四个独立的瓶颈。

**Q：NVLink 和 InfiniBand 的区别对我意味着什么？** 通信最频繁的并行维度必须放在机内。这一条决定了张量并行的规模上限。

**Q：为什么 AllReduce 的传输量是数据量的两倍？** 它实际由 ReduceScatter 和 AllGather 两步组成，各传一遍。算通信量时不要少算这个因子。

**Q：框架会把这些细节藏起来吗？** 能藏住正确性，藏不住性能。训练慢或扩展效率差时，最终都要回到通信量和时间线上。

# 第 1 章 训练显存构成与容量分析

> **开场问题**：8B 模型 bf16 只有 16 GB，为什么训练放不进 80 GB 的卡？

## 1.1 把每个参数的字节数算清楚

混合精度训练下，每个参数长期占用的显存是这样构成的：

| 项目 | 精度 | 字节/参数 |
|---|---|---|
| 权重 | bf16 | 2 |
| 梯度 | bf16 | 2 |
| fp32 主权重 | fp32 | 4 |
| AdamW 一阶矩 | fp32 | 4 |
| AdamW 二阶矩 | fp32 | 4 |
| **合计** | | **16** |

8B 参数乘 16 字节就是 **128 GB**，已经超过单卡容量，而这还没算激活。开场问题的答案就在这张表里：**训练显存的大头不是权重，是优化器状态**——它占了 12 字节中的 8 字节，加上主权重是 12。

这张表也解释了后面两章的动机：第 4 章的 ZeRO 切的就是这 12 字节，第 8 章换优化器能直接减掉其中一份 4 字节。

## 1.2 激活：随 batch 和序列长度增长的那一项

反向传播需要前向的中间结果，所以它们必须留着。激活量大致正比于 `batch × 序列长度 × hidden × 层数`，与参数量无关。

这意味着长序列训练时，激活可以轻松超过模型状态本身。而且它是唯一一项**你能通过调 batch 和序列长度直接控制**的显存，所以它通常是 OOM 时第一个被动的地方。

## 1.3 临时张量与碎片

还有一批容易被公式漏掉的：注意力和矩阵乘的 workspace、通信缓冲区、内存分配器为了避免频繁申请而保留的空闲块、以及碎片。

实际经验是**理论算到 70 GB 不代表 80 GB 的卡能跑**。规划时要留 10%–20% 余量，否则会在训练跑了几小时后遇到一次偶发的峰值 OOM。

## 1.4 梯度累积

目标全局 batch 放不下时，把它拆成若干 micro-batch，逐个做前反向并把梯度累加起来，最后统一更新一次参数。

它把峰值激活降到单个 micro-batch 的量，代价是一次参数更新要花好几倍的时间。注意它**不减少权重、梯度和优化器状态的占用**——那些是常驻的。

## 1.5 激活重计算

前向时不保存中间激活，反向需要时重新算一遍。用 FLOPs 换显存，是长序列训练的必备手段。

两种粒度：**整层重算**（每个 Transformer Block 只存输入，反向时整层重算）实现简单，额外计算约 30%；**选择性重算**只丢弃那些"存起来贵、算起来便宜"的中间结果（比如注意力矩阵），保留矩阵乘的输出，性价比明显更好。现代框架默认走后者。

## 1.6 低精度训练

bf16 已经是大模型训练的默认：矩阵乘用低精度跑得快，关键累加和优化器状态保留 fp32 保住精度。之所以选 bf16 而不是 fp16，是因为它的指数位和 fp32 一样多，动态范围足够，不需要 loss scaling 这套额外机制。

**FP8 训练**进一步减少显存和通信，但它不是把 dtype 改个名字那么简单：需要为不同张量维护缩放因子、追踪历史范围、处理溢出，并决定哪些运算保留高精度。它是一整套数值系统。截至 2026 年 FP8 已是大规模预训练的成熟可选项，但依赖硬件支持和细粒度缩放方案；FP4 端到端预训练仍属前沿探索，不能当成默认。

第四部分还会讲 FP8 **推理**量化——和这里的 FP8 训练是两件事，不要混。

### 核心问答

**Q：训练显存为什么远大于推理？** 推理只需要权重和 KV；训练还要梯度、优化器状态和反向所需的全部激活。按每参数字节算，训练是推理的八倍左右。

**Q：为什么优化器状态要用 fp32？** 参数更新量常常比参数本身小几个数量级，低精度下这些小更新会在舍入中直接消失，长期累积的效果就没了。

**Q：OOM 了先开重计算还是先减 batch？** 优先重计算，因为它保住了全局 batch（也就保住了实验的可比性），再微调 micro-batch。但要同时看吞吐，不能只求"能跑"。

**Q：为什么实测显存总比公式高？** 公式漏掉了 workspace、通信缓冲和碎片。按公式规划时留 10%–20% 余量。

# 第 2 章 GPU 性能模型：算力、带宽与通信

> **开场问题**：Profiler 显示 GPU 利用率 100%，为什么实际只达到理论算力的 20%？

## 2.1 "利用率"这个指标在骗你

`nvidia-smi` 里的 GPU utilization 只表示"这段时间里有 kernel 在跑"，不表示跑得好。一个只用了 2% 算力的逐元素算子跑满一秒，利用率也是 100%。开场问题就是这么来的。

真正该看的是三个量：实际达到的 FLOPS（对比硬件峰值）、实际达到的 HBM 吞吐（对比峰值带宽）、以及各类 kernel 的时间占比。前两个里哪个接近峰值，就说明瓶颈在哪一侧；两个都不接近，说明问题在别处（通信或 CPU）。

## 2.2 算术强度与 Roofline

**算术强度 = 这个操作的 FLOPs ÷ 它需要搬运的字节数**。把它和硬件的"峰值算力÷峰值带宽"比一下：低于这个阈值，操作受带宽限制；高于它，才可能受算力限制。

这个简单的除法能省掉大量无效优化。举例：Decode 阶段每生成一个 token 要读全部权重（16 GB），做的计算量却只有 2×参数量×batch。batch=1 时算术强度约等于 2，而硬件阈值在数百——**它离算力受限差了两个数量级**。所以优化 Decode 的方向只有两个：减少要读的字节（量化）或者让更多请求分摊这次读取（增大 batch）。这条结论在第三部分会反复用到。

## 2.3 小算子与启动开销

一个 Transformer Block 里，LayerNorm、激活、残差加、转置、切片各自都是一个 kernel。它们的计算量微不足道，但每个都要完整地从 HBM 读一遍、写一遍，再加上 kernel 启动的固定开销。

累加起来，这些"不干活"的算子可以占掉相当比例的时间。算子融合（第 17 章）就是把它们合并成一个 kernel，中间结果留在寄存器里，把多次 HBM 往返压成一次。

## 2.4 通信与计算重叠

反向传播是从最后一层往前算的，所以最后几层的梯度早早就绪，完全可以一边通信一边继续算前面的层。

**好的系统不只是减少通信量，更是把通信藏到计算后面**。判断藏没藏住的方法很直接：看时间线上通信 kernel 有没有和计算 kernel 在时间上重叠，以及关键路径上暴露出来的通信时长占 step 时间多少。这个技巧从第 3 章的梯度桶一直用到第 6 章的 AllToAll 隐藏。

## 2.5 用时间线定位，而不是猜

优化之前先回答一个问题：**GPU 此刻在算、在搬、在等通信，还是在等 CPU？**

时间线上四种典型形态对应四种修法：连续的计算块但 FLOPS 偏低 → kernel 效率或形状问题；大量 NCCL 块暴露在关键路径 → 通信没藏住；kernel 之间有规律的空洞 → CPU 提交跟不上，考虑 CUDA Graph；step 开头有固定空洞 → 数据管线跟不上。

猜错方向，后面做的所有工作都是白工。这是本册最重要的工作习惯。

### 核心问答

**Q：什么时候优化 FLOPs 是没用的？** 当操作受带宽或通信限制时。此时少算一点，时间几乎不变，因为 GPU 本来就在等数据。

**Q：为什么算子融合常比改算法更有效？** 因为很多算子的成本几乎全在读写 HBM，而不在计算。融合把往返次数降下来，直接命中真正的瓶颈。

**Q：通信量没变，重叠之后为什么能加速？** 总工作量没少，但通信和计算同时发生，关键路径变短了。墙上时钟看的是关键路径。

**Q：性能排查第一步看什么？** 端到端 step 时间，然后是时间线。单独看 GPU 利用率是最容易误判的做法。
