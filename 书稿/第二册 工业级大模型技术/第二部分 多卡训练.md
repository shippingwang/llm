# 第二部分 分布式训练

**目的**：从单卡出发，每当一种资源放不下，就多一种切法。最后把它们组合成真实集群方案，并补上优化器这条决定收敛速度的线。

# 第 3 章 数据并行与梯度同步

> **开场问题**：单卡能跑，但要三年才训完。加卡最直接的办法是什么，它的极限在哪？

## 3.1 最简单的扩展

每张卡保存一份完整模型，各自读不同的数据算出各自的梯度，然后所有卡把梯度求和（AllReduce）并除以卡数，最后各自用同一份平均梯度更新参数。因为初始权重相同，每步用的梯度也相同，各卡的参数始终保持一致，不需要额外同步。这就是 DDP。

它的数学含义很简单：**N 张卡做数据并行，等价于单卡跑一个 N 倍大的 batch**。所以数据并行不改变训练结果，只改变你多快能跑完。

通信量也容易算：每步每张卡要把全部梯度发出去再收回来，AllReduce 的实际传输量约为 `2 × 参数量 × 精度字节`。8B 模型 bf16 梯度是 16 GB，每步每卡要搬约 32 GB——这个数字是后面所有并行策略的比较基准。

## 3.2 全局 batch 是算法超参，不是系统参数

`全局 batch = 每卡 micro-batch × 梯度累积步数 × 数据并行卡数`。

这里有个新手最常踩的坑：卡数从 64 加到 256，如果其他两项不变，全局 batch 也跟着变成 4 倍，学习率，warmup 步数，总步数全都不再匹配，**这已经不是原来那个实验了**。正确做法是先确定目标全局 batch（由算法和数据量决定），再反过来分配卡数和累积步数。

batch 也不是越大越好。超过某个"临界批量"后，梯度已经足够准，再增大只是让同样的梯度信息重复计算，token 效率下降。工业上的做法是把全局 batch 定在临界点附近，剩下的算力用来加卡缩短 wall-clock，而不是继续放大 batch。

## 3.3 梯度桶与通信重叠

朴素实现是等整个反向传播结束再统一 AllReduce，此时 GPU 完全空闲等网络。DDP 的做法是把参数按反向顺序分成若干 bucket（默认 25 MB 量级），某个 bucket 里的梯度全部就位就立刻发起该桶的 AllReduce，同时 GPU 继续算前面的层。

于是通信被藏在计算后面。桶太小，每次通信的数据量不足以摊薄启动开销，且 kernel 数量暴增；桶太大，最后一个桶要等反向全部结束才能发，藏不住。这是第 2 章"通信与计算重叠"在最简单场景下的具体形态。

## 3.4 为什么加卡不是线性加速

四个常见原因，排查时按这个顺序看：通信占比随卡数上升（AllReduce 的延迟项与卡数相关）；数据管线跟不上，GPU 在等数据；CPU 侧的 Python 调度和 kernel launch 成为瓶颈（小模型尤其明显）；集群里有慢卡，同步训练下所有人都得等它。

报告扩展效率时必须固定全局 batch，比较 step 时间的变化。只说"加卡之后总吞吐上升了"没有意义——那是因为 batch 也变大了。

### 核心问答

**Q：DDP 省显存吗？** 不省。每张卡都有完整的权重，梯度和优化器状态，它只提高吞吐。省显存是下一章的事。

**Q：某张卡慢 10% 会怎样？** 整个训练慢 10%。同步训练每步都有全局同步点，最慢的卡决定 step 时间，所以慢节点（straggler）比偶发崩溃更难受——它不报错。

**Q：梯度累积和加卡等价吗？** 对梯度而言基本等价（都是在更多样本上平均），但累积是串行的，不缩短 wall-clock；加卡是并行的。两者常配合使用，共同凑出目标全局 batch。

**Q：什么时候只用 DDP 就够？** 模型加上梯度和优化器状态能装进单卡，数据管线喂得饱的时候。它实现最简单，故障面最小，不要为了"显得专业"去开更复杂的并行。

# 第 4 章 训练状态分片：ZeRO 与 FSDP

> **开场问题**：8B 模型权重只有 16 GB，80 GB 的卡为什么 DDP 起不来？

## 4.1 先看清楚重复在哪

第 1 章算过这笔账：bf16 训练下，每个参数长期占用约 16 字节——bf16 权重 2，bf16 梯度 2，fp32 主权重 4，AdamW 的一阶矩 4，二阶矩 4。8B 参数就是约 128 GB，再加上激活，单卡必然放不下。

关键观察是：**DDP 下这 128 GB 在每张卡上一模一样**。64 张卡存了 64 份完全相同的内容。既然如此，为什么不每张卡只存 1/64？

## 4.2 ZeRO 的三个阶段

- **Stage 1**：切优化器状态。每张卡只保存 1/N 的 fp32 主权重和 Adam 矩，更新时各自更新自己那片，再把更新后的参数 AllGather 回来。省掉了最大的那块。
- **Stage 2**：再切梯度。反向时用 ReduceScatter 代替 AllReduce——每张卡只收到自己负责那片的梯度求和结果，正好够它更新自己那片参数。
- **Stage 3**：连参数也切。每张卡平时只持有 1/N 的权重，**要算某一层时才把这层的完整参数 AllGather 回来，算完立刻丢掉**。

显存从 Stage 1 到 3 递减，通信递增。但增得没有想象中多：DDP 每步的通信量约 2 倍参数量，ZeRO-3 约 3 倍——**只多了 1.5 倍，却换来显存除以 N**。这个性价比是它能成为默认方案的原因。

## 4.3 FSDP 的实际运行过程

PyTorch 的 FSDP 是 ZeRO-3 思路的原生实现。把模型按模块包裹成若干 FSDP 单元，每个单元的生命周期是：前向到这个单元时 AllGather 出完整参数 → 计算 → 立刻释放分片以外的部分 → 反向时再 AllGather 一次 → 算出梯度后 ReduceScatter → 只保留自己那片。

**包裹粒度是这里唯一重要的调参**。包得太粗（比如整个模型一个单元），AllGather 会把全部参数拉回来，等于没切；包得太细（每个 Linear 一个单元），通信次数暴增，每次数据量太小，启动开销吃掉收益。常见做法是按 Transformer Block 包裹，一层一个单元。

旧版 FSDP 以被包裹模块的扁平化参数为分片单位，FSDP2 改成逐参数分片（per-parameter sharding），在混合精度，部分冻结，与编译器配合上都更干净。它们和 ZeRO-3 目标相同但实现不同，写文档时不要当成同义词。

## 4.4 Prefetch：让通信藏进计算

如果算第 i 层时才去 AllGather 第 i 层的参数，GPU 会干等。所以 FSDP 会在算第 i 层的同时预取第 i+1 层的参数，反向同理。

这里有个直接的权衡：预取深度越大，通信越容易被藏住，但同时驻留在显存里的完整参数层数也越多。预取两层就意味着峰值显存多出两层的完整参数——**很多 FSDP 的 OOM 不是分片没生效，而是预取太激进**。

## 4.5 Offload：把状态放到 CPU 或 NVMe

显存仍然不够时，可以把优化器状态甚至参数放到主机内存，需要时再搬回 GPU。它确实能让原本跑不起来的配置跑起来，但代价必须算清楚：PCIe 的带宽比 HBM 低一个数量级以上，**容量问题被转化成了搬运问题**。

实践中它适合两种场景：硬件严重受限时先把流程跑通；或者只 offload 更新频率低，访问模式规整的那部分状态。把它当成常规加速手段会很失望。

## 4.6 分片之后，checkpoint 长什么样

分片训练自然产生分片 checkpoint——每张卡存自己那一片，保存快，恢复快。但这带来两个必须提前想清楚的问题：

第一，**换并行配置还能不能加载**。用 64 卡训的分片 checkpoint，想用 32 卡续训，需要 resharding 能力。很多团队是在故障恢复时才发现自己没有。

第二，**对外发布的权重是另一种格式**。推理引擎要的是完整的，按层组织的权重文件。导出流程应该在训练早期就跑通一次，而不是等训练结束。

### 核心问答

**Q：ZeRO-3 和 FSDP 是一回事吗？** 思路相同（参数，梯度，优化器状态全分片），实现和接口不同。FSDP 是 PyTorch 原生实现，FSDP2 采用逐参数分片。讨论时最好说清是哪一个。

**Q：既然 Stage 3 最省显存，为什么不总是用它？** 通信更多，调度更复杂，小规模训练上额外开销可能超过收益。放得下的时候，简单方案通常更快。

**Q：FSDP 和张量并行的本质区别？** FSDP 平时把参数存成分片，算的时候恢复成完整的，**计算本身还是单卡完整计算**；张量并行是让一个矩阵乘法本身就跨卡执行，任何时刻都没有哪张卡持有完整矩阵。

**Q：开了 FSDP 还 OOM，先查什么？** 按顺序查：包裹粒度是不是太粗，预取深度是不是太大，激活重计算有没有开，有没有哪个不被包裹的大张量（比如巨大词表的 lm_head 输出 logits）。

# 第 5 章 模型内并行：TP，SP 与 CP

> **开场问题**：70B 模型的单层 FFN 权重就有 1.7 GB，ZeRO-3 在前向那一刻仍要把整层 AllGather 到一张卡上。分片救不了"单层本身放不下"。

## 5.1 张量并行在切什么

TP 不是把不同层放到不同卡，而是**把同一个矩阵乘法切开，让多张卡各算一部分**。

以 FFN 为例，`Y = X @ W1`，把 W1 按列切成 N 份分给 N 张卡，每张卡拿到完整的 X 和 1/N 的 W1，各自算出 Y 的 1/N 列。接着 `Z = Y @ W2`，把 W2 按行切成 N 份，每张卡用自己手上那 1/N 列的 Y 乘对应那 1/N 行的 W2，得到完整形状的**部分和**，最后一次 AllReduce 把 N 份部分和加起来就是正确结果。

这套"先列切，再行切，中间不通信"的组合是 Megatron 张量并行的基本单元。注意力部分同理：QKV 投影按头切（每张卡负责若干个头），输出投影按行切，中间的注意力计算各头独立，完全不需要通信。

## 5.2 为什么 TP 不能跨机

数一下通信：每个 Transformer Block 的前向有两次 AllReduce（注意力后一次，FFN 后一次），反向再两次。通信量正比于 `batch × 序列长度 × hidden`，**与参数量无关，与层数成正比**。

把这个数除以 NVLink 带宽（几百 GB/s 量级）和跨机网络带宽（通常低一个数量级），结论自己就出来了：机内尚可接受，跨机则每层都要在关键路径上等网络。所以"**TP 的大小不超过单机卡数**"这条铁律不需要死记，算一遍就明白。

## 5.3 序列并行是 TP 的补丁

开了 TP 之后还有个漏网之鱼：LayerNorm，Dropout，残差这些操作没法按 hidden 维切（它们需要完整的特征向量），于是每张卡都保存了一份**完整序列的激活**，这部分显存没省下来。

序列并行把这些区域按序列维切开，每张卡只处理一部分 token。配合的通信变化是：原本 TP 边界上的 AllReduce 被拆成 ReduceScatter + AllGather 两步，**通信总量不变**，但中间那段的激活显存降到 1/N。

**它不是用来训长文本的**，只是给 TP 补激活显存的漏。这个术语在中文资料里被大量误用。

## 5.4 上下文并行才是长序列的解法

训 128K 上下文时，单条样本的注意力本身就放不下一张卡。CP 把**序列的不同位置**分到不同 GPU，每张卡只持有自己那段的 Q，K，V。

问题是注意力需要每个 query 看到所有 key。两条主流实现：**Ring Attention** 让各卡的 K/V 分块在环上传递，每收到一块就和本地 Q 算一次局部注意力，再用在线 softmax 合并，通信可以和计算重叠；**Ulysses** 在头维度做 AllToAll，把"按序列切"临时转成"按头切"，算完再转回来，实现简单但并行度受头数限制。两者也可以混合使用。

和数据并行的区别要说清楚：DP 是不同卡处理**不同样本**，CP 是不同卡处理**同一条样本的不同片段**。

## 5.5 变长样本与 Packing：一个不报错的坑

预训练语料长短不一，按最长样本 padding 会浪费大量算力，所以工业做法是把多条短样本拼进一个固定长度的序列（packing）。

但拼接之后必须让 attention mask 阻止样本之间互相看见，位置编码也要为每条样本重新从 0 开始。**实现错了不会崩溃，不会 OOM，只是模型学到了跨样本的虚假依赖，loss 降得慢一点。** 几百卡跑了一周才发现这种问题，代价极高。

同类的还有 loss 归一化：变长数据下按样本数平均和按有效 token 数平均不等价，前者会系统性地给短样本更大权重。

## 5.6 什么时候用哪个

按约束选，不要按"框架支持"选：单层放不下 → TP（且不出机）；单样本放不下 → CP；只是训练状态总量放不下 → 优先 FSDP；开了 TP 之后激活还是紧 → 加 SP。

### 核心问答

**Q：TP 为什么必须留在机内？** 每层两次 AllReduce 都在关键路径上，跨机带宽和延迟会直接乘进 step 时间。

**Q：SP 和 CP 到底差在哪？** SP 切的是 LayerNorm/Dropout 这些非 TP 区域的激活，注意力仍在单卡内完整计算；CP 连注意力本身都跨卡，是真正用来训长序列的。

**Q：长上下文为什么不能只靠激活重计算？** 重计算省的是"保存下来的激活"，但单次注意力计算的峰值显存和中间张量仍然放不下。

**Q：TP 开到 16 会怎样？** 首先它跨机了，其次每张卡分到的矩阵已经很小，GEMM 效率下降，通信占比上升。TP 有明确的收益拐点。

**Q：Packing 为什么可能悄悄毁掉训练？** mask 或位置处理错误时不会有任何报错信号，只表现为收敛变慢，而这很容易被归因成"数据质量不好"。

# 第 6 章 流水线并行与专家并行

> **开场问题**：TP 卡在 8，DP 再大也压不住 671B 的参数量。而且一开 MoE，profile 里 40% 的时间是一段叫 AllToAll 的东西。

## 6.1 流水线并行与气泡

PP 把模型按层切成若干 stage，每个 stage 放在不同 GPU 上，数据像流水线一样依次经过。第一张卡算完前 8 层，把激活传给第二张卡，自己接着算下一个 micro-batch。

它的固有代价是**气泡**：流水线填满之前和排空之后，总有卡在空转。气泡率约为 `(P-1)/(M+P-1)`，其中 P 是 stage 数，M 是 micro-batch 数。4 个 stage，4 个 micro-batch 时气泡占 43%；把 micro-batch 提到 32，气泡降到 8.6%。**所以 PP 要求 micro-batch 数远大于 stage 数**，这也是它和大 batch 训练天然搭配的原因。

## 6.2 1F1B 与交错调度

朴素流水线先把所有 micro-batch 的前向做完再做反向，峰值时要同时保存所有 micro-batch 的激活。1F1B（one-forward-one-backward）让每个 stage 在稳态下交替执行一次前向和一次反向，激活驻留量从 M 份降到约 P 份。

交错流水线更进一步：一张卡不再负责连续的若干层，而是负责几段不连续的层（比如第 1–4 层和第 17–20 层），让流水线的"节拍"更密，进一步压缩气泡，代价是通信次数增加，调度复杂。

还有一个实际问题：**stage 不能按层数平均切**。第一个 stage 多了 embedding，最后一个 stage 多了 lm_head 和 loss 计算（词表 15 万时这是一个巨大的矩阵乘，还会产生巨大的 logits 张量）。按层数均分会让首尾两段明显更慢，而流水线的速度由最慢的 stage 决定。

## 6.3 专家并行

MoE 的专家天然可以分到不同卡上。一个 token 经路由决定去哪几个专家后，需要被**发送**到持有那些专家的卡上，算完再**收回**原来的位置——这就是每层两次 AllToAll。

第一册第 8 章讲了 MoE 为什么这么设计，这里讲它要付什么钱：**MoE 省的是 FLOPs，花的是带宽**。AllToAll 的通信量正比于被路由的 token 数乘以 hidden 维度，且每层都要来一次。这也是 MoE 训练对网络要求远高于稠密模型的原因。

## 6.4 Token Dispatch 的工程细节

高性能实现不会简单地"发出去，算，收回来"。它会把 token 按目标专家排序分组（让每个专家收到的 token 连续，才能做一次大 GEMM），把 AllToAll 拆块与本地专家计算重叠，用专门的通信库降低小消息开销。

正确实现一个 MoE 层不难，难的是让它跑得快。**朴素实现和优化实现的差距可以到数倍**，这也是为什么 MoE 训练框架的门槛比稠密模型高。

## 6.5 负载不均是系统问题也是算法问题

即使路由在整个训练集上是均衡的，**单个 batch 内仍可能严重偏斜**。某张卡分到的 token 是别人的三倍，其他卡就得等它——同步训练下这是直接的时间损失。

第一册 8.4 节讲的负载均衡损失和免辅助损失偏置调节，从系统视角看就是为了防止这件事。容量因子（每个专家最多接多少 token）和超出后的丢弃策略，则是在算法效果和系统确定性之间做的取舍：设死容量能保证不出现慢卡，代价是部分 token 没被处理。

### 核心问答

**Q：PP 最大的问题是通信量吗？** 不是。PP 的通信量其实很小（只传 stage 边界的激活），它的问题是气泡和 stage 不均衡。

**Q：为什么 micro-batch 数要远大于 stage 数？** 填充和排空的成本是固定的，micro-batch 越多，这部分固定成本被摊得越薄。公式 `(P-1)/(M+P-1)` 直接给出了这个关系。

**Q：EP 为什么特别吃网络？** 每层两次 token 级 AllToAll，且是全连接式的通信模式，跨机时对带宽和延迟都敏感。

**Q：已经用了 EP，还需要 TP 吗？** 可能需要。EP 只切专家，注意力部分和单个专家内部的矩阵如果还是太大，仍要靠 TP。大模型上常见 EP 和 TP 组合使用。

# 第 7 章 多维并行策略与拓扑映射

> **开场问题**：一份开源大模型的训练配置写着 TP=8, PP=4, EP=32, DP=16。这些数字是怎么定出来的？

## 7.1 从约束倒推，不从缩写出发

按这个顺序问自己，每一步的答案决定下一步：

1. **单层的参数和激活能放进一张卡吗？** 不能 → 开 TP，大小不超过单机卡数。
2. **单条训练样本的序列有多长？** 长到单卡装不下注意力 → 开 CP。
3. **是 MoE 吗？** 是 → 专家必须分布，开 EP，大小由专家数和网络拓扑决定。
4. **上面配完，每卡的训练状态还放得下吗？** 放不下 → 上 FSDP/ZeRO 分片，仍不够再考虑 PP。
5. **剩下的卡全部给数据并行**，并让全局 batch 落在目标值上。

PP 放在最后，因为它引入气泡和最复杂的调度，其他办法够用时没必要。

## 7.2 并行维度要贴着物理网络摆

逻辑上的并行维度必须映射到物理拓扑：通信最频繁的 TP 放在 NVLink 域内（同机 8 卡）；EP 的 AllToAll 流量大，尽量落在同一个高速网络分组里；PP 只在 stage 边界传激活，通信最稀疏，最适合跨机；DP 在最外层，每步一次 AllReduce 且可以和反向重叠。

摆错的代价很直观：把 TP 跨机，step 时间可能翻倍。

## 7.3 一份方案必须能算出这些数

"TP8 PP4 DP16" 不是设计，只是标签。可执行的方案要给出：每卡参数，梯度，优化器状态，激活峰值分别多少 GB；每步各维度的通信字节数；预计 step 时间和 MFU；以及留给碎片和临时张量的余量。

算完之后和实测对比，差距大就说明有理解错误——这是本册最有效的自检方式。

## 7.4 MFU 和 HFU 不是一回事

MFU（模型 FLOPs 利用率）= 按模型定义必须做的计算量 ÷ 硬件峰值算力 ÷ 时间。HFU（硬件 FLOPs 利用率）把激活重计算这类"额外做了一遍"的计算也算进去。

开了重计算之后，HFU 会明显高于 MFU，因为你确实让 GPU 多算了。**跨报告比较数字之前必须先确认对方报的是哪一个**，否则会得出完全错误的结论。业界主流报告的是 MFU，大规模稠密模型训练能做到 40%–50% 已经是不错的水平。

## 7.5 读一份真实配置

把上面的方法用在一个公开的大模型训练配置上，逐个字段解释：为什么 TP 正好等于单机卡数，为什么 micro-batch 数是 stage 数的若干倍，EP 大小和专家总数是什么关系，全局 batch 落在多少 token。

这一节在第二册的作用，等同于第一册第 7 章"逐行读懂一个 8B 模型"——**能逐字段解释别人的配置，才算真的会配**。

### 核心问答

**Q：有没有通用的并行配置模板？** 没有。模型形状，序列长度，集群拓扑，目标 batch 任何一个变了，最优解都会变。但 7.1 的**决策顺序**是通用的。

**Q：为什么不能同时把所有并行都开到最大？** 每多一个并行维度，通信，checkpoint，故障恢复和调试难度都会上升，而收益递减。能用简单方案就别上复杂的。

**Q：MFU 只有 25%，一定有问题吗？** 要看模型和场景。MoE，超长序列，小模型的 MFU 天然偏低。重要的是找到差距在哪：通信没藏住，数据没喂饱，还是 kernel 效率低。

**Q：怎么判断通信是否被藏住了？** 看 profiler 时间线上通信 kernel 是否与计算 kernel 重叠，以及关键路径上暴露的通信时长占 step 时间的比例。

# 第 8 章 大模型优化器：AdamW，Muon 与训练配方

> **开场问题**：同样的模型，同样的数据，同样的卡，换一个优化器能省下三成算力——这件事在 2025 年之后从论文变成了工业实践。

## 8.1 优化器同时管三件事

在大模型语境下，选优化器不只是选收敛速度：

- **收敛效率**：达到同样 loss 需要多少 token 和多少算力。这是最直接的钱。
- **稳定性**：能不能在几万步，上千卡的规模下不出 loss 尖刺。
- **显存**：优化器状态是训练显存的最大单项（第 1 章算过，AdamW 占每参数 8 字节的矩状态，加 fp32 主权重是 12 字节）。

这三件事互相牵制，所以"哪个优化器最好"没有脱离规模的答案。

## 8.2 AdamW 为什么当了十年默认

Adam 为每个参数维护梯度的一阶矩（动量）和二阶矩（梯度平方的滑动平均），更新时用一阶矩除以二阶矩的平方根。这相当于**给每个参数一个自适应的步长**：梯度长期很大的参数步子迈小一点，梯度稀疏的参数步子迈大一点。

这个性质对 Transformer 特别重要，因为不同层，不同模块（attention 与 FFN，embedding 与 norm）的梯度量级差异可能有几个数量级，单一学习率根本不work。AdamW 的改进是把权重衰减从梯度里解耦出来，直接作用在参数上，让正则强度不受二阶矩缩放的影响。

代价就是那两份状态：**每个参数 8 字节（fp32 的 m 和 v）**，8B 模型就是 64 GB，比模型本身还大。

## 8.3 Muon：把"逐参数"换成"逐矩阵"

Muon 的出发点是一个观察：神经网络里绝大部分参数是**二维矩阵**，而 Adam 把它们当成一堆互不相干的标量来处理，丢掉了矩阵结构本身的信息。

它的做法分两步。第一步和 Adam 一样做动量。第二步是关键：**对动量矩阵做一次正交化**，粗略地说，就是把这个更新矩阵的所有奇异值都拉到 1 附近，只保留它的"方向"，抹掉各个方向上量级的悬殊差异。严格做需要 SVD，太慢；实际用 Newton-Schulz 迭代做近似，只需要几次矩阵乘法，可以完全在 GPU 上跑，开销相对整个训练步很小。

直觉上的差别可以这样理解：**Adam 控制的是"每个元素变化多大"，Muon 控制的是"这次更新能把输入向量最多放大多少倍"**（谱范数意义上的步长）。后者更接近我们真正想限制的东西——一次更新对模型输出的扰动。实践中它表现为：同样的 loss 用更少的 token 和算力达到。Moonshot 在 Moonlight 的实验里报告了约两倍的算力效率——这是在他们那套设定下的结果，不是普适常数，换模型形状和数据配比都会变。

三个必须知道的工程事实：

- **它只用于二维矩阵参数**。embedding，lm_head，LayerNorm 的 scale，bias 这些一维或性质特殊的参数仍然用 AdamW。所以真实训练里跑的是一个**混合优化器**，不是纯 Muon。
- **它更省显存**。只需要动量一份状态，比 Adam 少一份二阶矩。
- **分布式实现是主要落地成本**。Newton-Schulz 需要完整的矩阵，而 FSDP/ZeRO 下参数是分片的，必须先把矩阵聚合起来或者设计分布式版本（Moonshot 为此专门做了 distributed Muon）。这是它从"小规模很香"走到"千卡可用"要跨的那道坎。

## 8.4 大规模下的稳定性：MuonClip 这类补丁

换优化器不是无痛的。Muon 在大规模训练上遇到的一个具体问题是 attention logits 爆炸——第一册 4.4 节讲 QK-Norm 时描述过同一个现象。Moonshot 的做法是在 Muon 基础上加 qk-clip，直接约束 query 和 key 的规模，合称 MuonClip，用它完成了万亿参数 MoE 的预训练且全程无 loss 尖刺。

这件事的普适教训比技术细节更重要：**优化器，模型结构的稳定性设计，学习率方案是一套耦合的系统**。换掉其中一个，另外两个大概率要跟着调。

## 8.5 其他值得知道名字的

- **Shampoo / SOAP**：更彻底的二阶方法，为每层维护预条件矩阵。效果好但矩阵求逆开销和显存都重，SOAP 是把 Adam 放到 Shampoo 的特征基上的简化版本。
- **Adafactor**：把二阶矩做低秩分解，显存从 O(参数量) 降到 O(行+列)。显存紧张时的经典选择，代价是效果略逊。
- **8-bit 优化器**：把状态量化到 8 bit 存储，用时反量化。省下大半优化器显存，对效果影响很小，中小规模训练里性价比很高。
- **Lion**：只保留动量，用符号更新。显存省，实现简单，但对超参更敏感，大规模上的表现不如前几者稳定。

## 8.6 判断一个新优化器值不值得换

这个领域论文很多，绝大多数经不起以下三问：

1. **对比是否公平**。很多"超越 AdamW"的结果赢在对方没调好。合格的对比要求双方在同一算力预算下各自调到最优。
2. **验证规模够不够**。小规模上赢，大规模上输的情况极其常见。要看它在你的目标规模附近有没有证据。
3. **工程代价算没算**。分布式实现，checkpoint 兼容，与现有并行策略的配合，以及超参要不要全部重调——这些成本经常超过收益。

对大多数团队，合理的姿态是：**AdamW 仍是安全默认；Muon 已经有大规模成功案例，值得在新项目上认真评估；其余的先观望**。

## 8.7 学习率与 batch：和优化器绑在一起的两个旋钮

学习率调度现在主流是两种：**cosine**（经典，但要求提前知道总步数）和 **WSD**（warmup-stable-decay，中间保持恒定学习率，最后才退火）。WSD 的工程优势很大——中途可以随时从稳定段切出一个分支做退火，得到一个可用模型，而不必重跑；也方便中途加数据或改配比。

需要强调的是：**换优化器之后，最优学习率通常完全不同**，Muon 和 AdamW 的合适取值不在一个量级上。第一册附录 F 讲的 muP 那套超参迁移结论也是针对特定参数化的，不能直接照搬到新优化器上。

### 核心问答

**Q：Muon 和 AdamW 的本质区别用一句话怎么说？** AdamW 逐元素归一化更新，Muon 逐矩阵归一化更新——前者管每个数字变多少，后者管整个矩阵对输出的放大倍数。

**Q：为什么 Muon 不能用在 embedding 上？** 它的正交化操作依赖"这是一个有意义的二维变换矩阵"这个前提。embedding 表和 lm_head 更像是一堆独立的向量，LayerNorm 的 scale 则是一维的，都不适用。实际训练用混合优化器。

**Q：Muon 省显存吗？** 省一份状态（没有二阶矩），每参数少 4 字节。对 8B 模型是 32 GB，不算小，但它的主要卖点仍是收敛效率。

**Q：换优化器要重调哪些超参？** 至少是学习率和权重衰减，通常 warmup 和调度形状也要跟着变。把旧超参直接搬过去做对比，是最常见的错误评测方式。

**Q：为什么优化器放在第二册而不是第一册？** 它不改变模型结构，只改变训练过程——和并行，精度，数据管线一样属于"怎么把它训出来"。第一册只关心模型长什么样。

# 第 9 章 长周期训练工程：数据，容错与 Goodput

> **开场问题**：一次 54 天的训练，硬件层面发生了四百多次中断。如果每次都从上一个检查点重来，实际有多少时间在真正训练？

## 9.1 数据管线

从对象存储读取分片，解压，tokenize，shuffle，packing，预取，最后喂给 GPU。工业训练里 tokenize 通常是**离线**做好的，在线只做读取和组装——否则 CPU 必然成为瓶颈。

三个硬要求：数据顺序必须可复现（否则续训会改变训练轨迹）；全局 shuffle 要在分片层面做好（同一个来源的数据扎堆会造成局部分布偏移）；预取深度要够，GPU 不能等数据。判断数据是否成为瓶颈，看 profiler 里 step 开头有没有固定的空洞。

## 9.2 检查点里必须有什么

只存权重的 checkpoint 是不能续训的。完整的检查点包括：模型权重，优化器状态，学习率调度器的位置，随机数状态，**数据读取到哪里了**，以及当时的并行布局。

工程上的两个要点：异步保存（先把状态拷到主机内存，后台再落盘，把 GPU 停顿从几分钟压到几秒）；以及分布式检查点要支持 resharding，否则改变卡数就无法恢复。

## 9.3 故障谱系

千卡跑几个月，硬件故障是必然事件而非意外。常见的几类，按排查难度递增：**掉卡和进程崩溃**（明确报错，最好处理）；**NCCL 超时**（某张卡没进集合通信，需要定位是谁）；**ECC 错误和静默数据损坏**（可能只表现为某张卡结果异常）；**慢节点**（不报错，只是慢，最阴险）。

对应的检测手段是心跳，集合通信的超时记录，定期的健康检查和逐卡吞吐监控。

## 9.4 Goodput 才是真正的目标函数

MFU 衡量的是"GPU 正常跑的时候效率如何"，但付钱是按 wall-clock 付的。**Goodput = 真正在产出有效训练进度的时间 ÷ 总时间**，它把故障停机，检测时间，重启时间，回滚重算和检查点停顿全部算进去。

这个视角直接给出一个可优化的问题：检查点存得越频繁，日常停顿越多；存得越稀疏，故障后重算越多。已知保存耗时和集群平均无故障时间，最优保存间隔是可以算出来的，而不该拍脑袋定"每 1000 步"。

弹性训练（动态增减节点）听起来很美，实际用得远没有宣传的多——大多数团队的做法仍是准备热备节点加快速重启。

## 9.5 监控什么

至少这些：loss，梯度范数，参数范数，学习率，每卡吞吐，MFU，goodput，通信耗时，数据读取进度，MoE 的专家负载分布。

**只看 loss 会错过一整类问题**：吞吐悄悄降了三成，某张卡在降频，某几个专家已经没有 token 流过，数据管线在重复播放同一批数据——这些都不会立刻反映在 loss 上，但都在烧钱。

梯度范数曲线尤其值得盯：它通常在 loss 尖刺之前就出现异常，是最有用的早期预警。

## 9.6 可复现与实验治理

代码版本，配置，镜像，数据版本，检查点必须能互相追溯。大规模训练最昂贵的失败往往不是 OOM，而是三周后拿到一个不错的权重，却说不清它是用哪版数据，哪个配置训出来的，于是无法复现也无法改进。

### 核心问答

**Q：为什么检查点必须记录数据读取位置？** 否则恢复后会从头重放数据，导致部分样本被训多次，部分从未见过，训练轨迹和预期不符。这也是一个不报错的静默问题。

**Q：检查点多久存一次？** 取决于保存耗时和集群平均无故障间隔，目标是最小化"保存开销 + 故障后期望重算时间"。集群越不稳定，保存越快，就应该存得越勤。

**Q：MFU 很高，项目为什么还是延期？** 因为 MFU 看不到停机。频繁故障，慢恢复，慢节点都体现在 goodput 上，不体现在 MFU 上。

**Q：数据处理到底算第二册还是第三册？** 预训练数据的存储格式，读取，shuffle，packing 属于训练基础设施，在本册；指令数据和偏好数据的构造属于第三册。
