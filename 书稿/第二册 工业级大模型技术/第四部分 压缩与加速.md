# 第四部分 模型压缩与算子优化

**目的**：先分清量化到底压了哪一样东西，省的是哪条瓶颈，再看主流算法各自在解决什么具体困难；最后进入 kernel 与编译，理解为什么"有没有高效算子"经常比算法本身更决定成败。

# 第 15 章 数值表示与量化对象

> **开场问题**：W4A16 把权重压小了四倍，为什么大 batch 下反而比 bf16 还慢？

## 15.1 三个对象，三条瓶颈

"量化"这个词被用得太笼统，实际有三个互相独立的对象，省的东西完全不同：

- **权重量化**：减少权重占的显存，以及 Decode 时每步要读的字节数。它打的是**显存容量和带宽**，正好对准 Decode 的瓶颈。
- **激活量化**：让矩阵乘的两个输入都是低精度，从而能用上低精度的 tensor core。它打的是**算力**，主要收益在 Prefill 和大 batch。
- **KV Cache 量化**：减少每个 token 的 KV 字节数。它打的是**显存容量**，直接换来更大的并发和更长的上下文。

三者可以任意组合，但要各自算账。常见组合 W4A16（权重 4 bit，激活 16 bit），W8A8，FP8 全量化，适用场景完全不同。

## 15.2 数字格式：范围和精度的交换

同样是 8 位，INT8 是均匀的整数网格，FP8 用几位当指数，几位当尾数，牺牲精度换动态范围。FP8 常见两种分配：E4M3（4 位指数 3 位尾数，范围小精度高，适合权重和激活）和 E5M2（范围大精度低，适合梯度）。

4 位这一层，除了 INT4，还有 2024 年之后硬件开始原生支持的 microscaling 格式（如 MXFP4，NVFP4），它们的思路是让一小组元素共享一个缩放因子，在极低位宽下保住动态范围。

**但格式本身不产生加速**。真正决定速度的是目标硬件有没有对应的原生指令，以及推理引擎有没有实现对应的高效 kernel。这一点在 15.5 节展开。

## 15.3 量化粒度

一个 scale 管多少个数，决定了精度和开销的平衡：

- **per-tensor**：整个张量一个 scale。最省，最快，但只要有一个离群值就会把整个网格拉坏。
- **per-channel**：每个输出通道一个 scale。权重量化的常见选择，开销很小，效果明显更好。
- **per-group**：每 32/64/128 个权重一组，各自一个 scale。INT4 的标配，因为 4 位只有 16 个刻度，必须靠细粒度 scale 才能用。
- **per-token**（激活）：每个 token 一个 scale，在线计算。适配激活随输入变化的特性。

粒度越细，量化误差越小，但存储 scale 的额外开销和反量化的计算越多。这也是 INT4 模型实际大小往往大于"参数量除以 4"的原因。

## 15.4 KV Cache 量化的特殊性

KV 量化和权重量化有个本质区别：**权重量化的误差是静态的，可以离线补偿的；KV 的误差会一路参与后续所有 token 的注意力计算**。

它的收益很直接——KV 从 bf16 降到 FP8 就是并发翻倍（回到第 11 章，并发直接等于吞吐）。但质量评估必须专门做长上下文测试，因为误差在长序列上累积，短测试完全看不出来。实践中 FP8 KV 相对安全，INT4 KV 要谨慎，且通常对 K 和 V 采用不同策略（K 参与 softmax，对误差更敏感）。

## 15.5 为什么 W4A16 在大 batch 下会变慢

回到开场问题。W4A16 的实际执行是：权重以 INT4 存在显存里，计算前要**反量化成 bf16**，再做 bf16 的矩阵乘。

小 batch（Decode）时这很划算：瓶颈是读权重，读取量降到 1/4，反量化的那点计算完全被掩盖。

大 batch（Prefill 或高并发）时情况反转：瓶颈已经变成算力，权重读取不再是主要成本，而反量化是**实打实增加的计算**。此时 W4A16 不但没有收益，还比直接用 bf16 多了一道工序。如果目标硬件支持 FP8 或 INT8 的原生矩阵乘，W8A8 在这个工作点上会明显更好——因为它的矩阵乘本身就是低精度的，不需要先还原。

**结论**：量化方案要按目标工作点选。端侧和低并发场景选 weight-only 低位宽；数据中心高吞吐场景优先考虑有原生算子支持的 FP8/INT8 全量化。

### 核心问答

**Q：INT4 一定比 INT8 快吗？** 不一定。显存一定更省，速度取决于 batch，硬件指令支持和反量化开销。大 batch 下常常更慢。

**Q：FP8 和 INT8 怎么选？** 看硬件。数据中心新卡有 FP8 原生支持且动态范围更友好，通常首选；端侧 NPU 的 INT8 生态更成熟。

**Q：KV 量化为什么要单独评测？** 它的误差会持续参与注意力计算并在长序列上累积，短文本测试看不出问题。

**Q：为什么 INT4 模型文件比"参数量÷4"大？** 因为要额外存每个 group 的 scale（有时还有 zero point），group 越小这部分越多。

# 第 16 章 后训练量化：GPTQ，AWQ 与 SmoothQuant

> **开场问题**：同样量化到 4 bit，为什么有的方法困惑度几乎不变，有的直接胡言乱语？

## 16.1 误差从哪来：离群值

把连续的权重映射到 16 个刻度（INT4），误差的主要来源不是"刻度不够密"，而是**少数极端值把刻度撑开了**。

假设一组权重里 99% 都在 ±0.1 之间，但有一个值是 5.0。为了表示得下这个 5.0，整个网格的范围必须拉到 ±5.0，于是那 99% 的正常值全都挤在中间一两个刻度里，信息基本全丢。

大模型的激活里这种离群值特别多，而且集中在固定的少数几个通道上。**几乎所有量化算法都是在处理这一个问题**，区别只在处理方式。

## 16.2 最朴素的 RTN 和它的问题

RTN（round-to-nearest）就是直接四舍五入到最近的刻度。配合 per-group 粒度，在 INT8 上基本够用，在 INT4 上通常会掉点明显。它的问题是**逐个权重独立处理，完全不考虑这个权重对模型输出的影响有多大**。

后面三个算法各自从不同角度修正这一点。

## 16.3 GPTQ：量化完一列，用剩下的列补偿误差

思路是把量化看成一个优化问题：不要求每个权重都量化得准，而要求**这一层的输出尽量不变**。

具体做法是逐列处理权重矩阵：量化第一列，算出这一列因为量化产生的输出误差，然后**调整尚未量化的那些列的数值来抵消这个误差**，再量化第二列，如此往下。调整的依据来自输入激活的二阶信息（Hessian 的近似），也就是"哪些输入方向更重要"。

它需要一批校准数据来估计这个二阶信息，量化过程本身要跑一会儿（几十分钟到几小时，取决于模型大小），但不需要重新训练。它是 INT4 weight-only 场景下的经典方案。

## 16.4 AWQ：保护重要通道，而不是补偿

AWQ 的出发点更简单：不是所有权重同等重要。**用激活的统计量判断哪些输入通道重要**（激活幅度大的通道对应的权重更关键），然后在量化前给这些通道的权重乘一个放大系数，让它们在量化网格里占更多刻度；推理时在激活侧除回去，数学上等价。

它不需要二阶信息，量化速度比 GPTQ 快得多，部署生态也很成熟。核心洞察是"重要性由激活决定，不是由权重自身的大小决定"——只看权重大小来挑重要参数是错的。

## 16.5 SmoothQuant：把激活的难题搬给权重

前两个是 weight-only。想做 W8A8 就必须面对激活量化，而激活的离群值比权重严重得多。

SmoothQuant 的做法很巧：对每个通道，给激活除以一个系数 s，给对应的权重乘上 s。矩阵乘的结果完全不变（因为 `(X/s) @ (s·W) = X @ W`），但**激活的离群程度被削平了，代价是权重的动态范围变大了一点**。因为权重本来就好量化（分布规整，可以离线处理），这笔交换非常划算。

系数 s 按通道计算，由激活和权重各自的幅度共同决定，可以用一个超参控制"迁移多少"。

## 16.6 校准数据怎么选

PTQ 方法都需要一小批校准样本来统计激活分布。三个常见错误：

**分布不匹配**——用通用网页文本校准一个代码模型，代码任务上会明显掉点。校准集应该覆盖真实的任务，语言和格式。

**长度不匹配**——只用短文本校准，长上下文场景的激活分布没被覆盖。

**过度追求数量**——几百到几千条通常就够了，代表性远比数量重要。

## 16.7 混合精度：不要一刀切

实践中从不把整个模型量化到同一精度。通常保持较高精度的部分包括：embedding 和 lm_head（直接影响输出分布），所有 norm 层的参数，MoE 的 router（它的输出决定离散的专家选择，一点误差就可能改变路由结果），以及实测下来特别敏感的少数层。

MoE 还有个专属问题：专家粒度的量化误差分布不均，冷门专家的校准数据天然更少，容易量化得更差。

## 16.8 验收：困惑度不够用

**困惑度几乎不变，业务效果掉一大截**是量化上线最常见的翻车方式。因为困惑度是全体 token 的平均值，而量化的伤害往往集中在少数关键能力上。

一份能用的验收清单：分任务评测（代码，数学，多语言，指令遵循各自单独看），长上下文专项，格式化输出的稳定性（JSON，工具调用），以及最终的线上 A/B。**先塌的总是代码，数学和长上下文**，这三项应该作为量化质量的哨兵指标。

## 16.9 先看有没有 kernel，再挑算法

这是本章最实用的一条。一个量化方案能不能落地，第一决定因素是**目标硬件和推理引擎有没有对应的高效实现**。

算法上更漂亮，压缩率更高，但运行时需要频繁反量化，或者退回通用算子执行，结果往往是"文件小了，服务慢了"。正确的选型顺序是：目标硬件与引擎支持 → 目标工作点上的实测性能 → 任务质量 → 最后才是算法名字。

### 核心问答

**Q：GPTQ 和 AWQ 的核心区别？** GPTQ 是**事后补偿**（量化一列，调整后面的列来抵消误差），AWQ 是**事前保护**（按激活重要性给关键通道放大，让它们量化得更准）。AWQ 更快，GPTQ 在某些场景精度略好，实际选择主要看引擎支持。

**Q：SmoothQuant 为什么能"凭空"改善量化？** 它没有凭空改善，而是把难量化的激活的动态范围转移了一部分给好量化的权重。总难度守恒，但分配得更合理。

**Q：为什么 router 必须保高精度？** 它的输出经过 top-k 变成离散选择，微小的数值误差可能让 token 路由到完全不同的专家，误差被放大成结构性改变。

**Q：只测困惑度会漏掉什么？** 几乎所有集中性的能力损伤——代码生成，多步数学，长上下文召回，结构化输出。这些恰恰是业务最依赖的。

# 第 17 章 高性能 Kernel，图编译与执行后端

> **开场问题**：所有该开的开关都开了，离硬件理论上限还差 25%。这 25% 在哪几个 kernel 里？

## 17.1 先 profile，再动手

模型代码里的一行 `x = x + attn(norm(x))`，在 GPU 上可能是七八个 kernel，每个都要把数据从显存读进来，算完写回去。性能工程关心的从来不是代码行数，而是**最终发射了多少 kernel，每个 kernel 读写了多少字节**。

看 profiler 时间线要回答四个问题：GPU 在算的时间占多少，kernel 之间有没有空隙（CPU 提交跟不上），通信有没有和计算重叠，有没有某个意外的 kernel 占了大头。这四个问题对应四种完全不同的修法，猜错方向做的优化全是白工。

## 17.2 算子融合：主要为了少读写

大量逐元素算子（norm，激活，残差加，RoPE，量化和反量化）的计算量微不足道，成本几乎全在"从显存读进来，写回去"。把它们融合成一个 kernel，中间结果留在寄存器或共享内存里，一次读写解决。

常见的融合包括：RMSNorm + 残差，SwiGLU 的门控乘法，QKV 投影后的 RoPE，以及采样链路上的一串小操作。融合也不是越大越好——寄存器用量超限会导致占用率下降，反而变慢。

## 17.3 FlashAttention 作为方法论

第一册 3.4 节讲过它：分块加在线 softmax，让 n×n 的注意力矩阵从不写进显存。

这里要强调的是方法而不是这个具体算子：**先识别出瓶颈是访存而非计算，再重排计算顺序让数据留在片上，数学结果完全不变**。第 11 章的分页 KV 要求 attention kernel 支持间接寻址，第 14 章的树状验证要求特制 mask，都是在这个框架下的进一步改造。

## 17.4 Decode 阶段需要专门的 kernel

Prefill 和 Decode 的 attention 形状差别极大：Prefill 是 `[n, n]` 的方阵，Decode 是 `[1, n]` 的细长条。同一个 kernel 不可能对两者都最优。

Decode kernel 的核心困难是**并行度不足**：只有一个 query，如果按常规方式并行，大部分 SM 都闲着。解法是沿 KV 长度方向切分（split-K），让多个线程块各算一段，最后归并。GQA 还有额外的优化空间（多个 Q 头共享同一份 KV，可以合并读取）。

MoE 则需要 grouped GEMM：把路由到不同专家的 token 分组，一次 kernel 调用完成多个形状不同的矩阵乘。

## 17.5 CUDA Graph：消掉 CPU 开销

每个 kernel 的启动都要 CPU 参与，一层十几个 kernel，几十层下来就是几百次启动。Decode 阶段单步 GPU 计算可能只有几毫秒，而 CPU 提交这几百个 kernel 也要几毫秒——**CPU 成了瓶颈**。

CUDA Graph 的做法是把一整段 GPU 操作序列捕获下来，之后每次一条命令回放整张图，CPU 开销几乎归零。小模型上收益可以到 30% 以上。

代价是**图要求形状固定**，而在线推理的 batch 和序列长度一直在变。工程上的做法是预先捕获若干个 batch 档位（比如 1/2/4/8/16/32）的图，实际运行时向上取整到最近的档位并 padding。这也是为什么分页 KV 的设计要尽量让形状变化可枚举。

## 17.6 编译栈

`torch.compile` 做图捕获，算子融合和内存规划，对训练和小规模推理都有效；Triton 让你用 Python 风格写 kernel，性能接近手写 CUDA 而开发成本低得多，现在大量新算子首发在 Triton；TensorRT-LLM 这类 AOT 编译引擎做得更彻底，离线编译出高度特化的执行计划，代价是编译耗时长，动态性差。

共同的敌人是**动态形状**：形状一变就可能触发重新编译或退回慢路径。冷启动时间（加载权重 + 编译 + warmup）在弹性扩缩容场景里是实打实的成本，第 19 章会再提到它。

## 17.7 什么时候该自己写 kernel

这是个成本判断，不是技术判断。三个条件同时满足才值得：profiler 证明这个算子长期占据关键路径的显著比例；现有后端确实没有高效实现（先去上游仓库确认一遍，很多时候已经有人在做了）；你有能力持续维护它（硬件换代，模型结构变化都要跟着改）。

大多数团队更划算的做法是：把形状和配置调到能命中现成的高效 kernel，而不是自己写一个。

### 核心问答

**Q：两个引擎跑同一个模型，FLOPs 一样，为什么速度差几倍？** FLOPs 不包含访存量，kernel 启动开销，融合程度和调度效率，而这些才是推理性能的主要构成。

**Q：CUDA Graph 为什么和动态 batch 冲突？** 图捕获时形状就固定了。解法是准备若干形状档位并 padding，用一点浪费换 CPU 开销归零。

**Q：Triton 会取代 CUDA 吗？** 大部分常规热点会被 Triton 覆盖，但极致优化和新硬件特性的首发支持仍需要 CUDA。两者是分工不是替代。

**Q：优化的顺序应该是什么？** 先前缀缓存和调度（消掉工作量），再量化（减少访存），最后才是 kernel 和编译（抠常数项）。很多团队顺序搞反，在最难的地方花最多时间拿最少收益。
