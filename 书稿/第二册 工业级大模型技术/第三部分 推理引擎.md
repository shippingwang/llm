# 第三部分 大模型推理系统

**目的**：第一册解释了模型怎样生成一个 token。这一部分解释成千上万个请求同时到来时，系统怎样管理显存、拼批、跨卡执行，并在延迟目标内持续吐字。

一个判断标准贯穿全部分：**每项技术动的是哪条瓶颈**。只有四条——算力、显存带宽、显存容量、排队。分页动容量，调度动排队，缓存直接消掉工作量，量化动带宽。先定位，再谈优化。

# 第 10 章 推理请求生命周期与性能指标

> **开场问题**：同一张卡、同一个模型，单请求只能到 40 token/s，并发 64 时总吞吐却能到 2000。多出来的性能，单请求时去哪了？

## 10.1 一次请求的完整路径

请求进来后依次经过：网关鉴权与限流 → 调度队列 → tokenize → **Prefill**（把整段 prompt 过一遍模型，写下全部 KV，产出第一个 token）→ **Decode 循环**（每次输入上一个 token，过一遍全部层，产出下一个）→ detokenize → 流式返回。

性能问题必须落在这条时间线的某一段上。"模型慢"不是诊断，"p99 的 TTFT 里有 300 ms 花在队列上"才是。

## 10.2 四个必须分开看的指标

- **TTFT**（首 token 延迟）：排队时间 + Prefill 时间。用户感知为"点了发送之后多久开始有反应"。
- **TPOT**（每 token 时间）：首 token 之后的平均吐字间隔，由 Decode 决定。
- **ITL**（token 间隔分布）：比平均 TPOT 有用得多，因为卡顿是分布问题——平均 30 ms 但偶尔卡 800 ms，体验很差。
- **吞吐**：单位时间处理的 token 数，要区分输入 token 和输出 token。

不同业务的目标函数完全不同：离线批处理只看吞吐；聊天要同时守住 TTFT 和 ITL；Agent 工具调用对 TTFT 极其敏感（一轮对话里可能有十几次模型调用）。

## 10.3 回到第一册的三个公式

开场那个反直觉现象，用第一册第 3 章的结论就能解释。Decode 阶段每生成一个 token，都要把全部模型权重从显存读一遍——8B 模型 bf16 就是 16 GB。一张带宽 2 TB/s 的卡，理论上每秒最多读 125 次权重，也就是 **单请求最多 125 token/s**，与算力无关。

但这次权重读取是**可以被整个 batch 共享**的：batch 里有 64 个请求，读一次权重能同时为 64 个请求各推进一个 token。所以 Decode 的吞吐几乎随 batch 线性增长，直到 batch 大到计算量追上访存量，工作点从带宽受限切换到算力受限。

**这个切换点是推理系统一切设计的原点**：Decode 天然在浪费算力，所以后面所有技术要么把浪费的算力换成别的东西（投机解码），要么想办法让 batch 更大（分页、调度）。

## 10.4 Prefill 和 Decode 是两种不同的负载

Prefill 一次处理几千个 token，是标准的大矩阵乘，算力受限，很容易吃满 GPU。Decode 每步只处理 batch 个 token，矩阵乘退化成瘦长的矩阵向量乘，带宽受限。

两者放在同一个 GPU 上会互相伤害：一个 4000 token 的 Prefill 要占用 GPU 几百毫秒，这期间所有正在 Decode 的请求全部卡住。第 12 章的分块 Prefill 和第 13 章的 PD 分离，都是在处理这个矛盾。

## 10.5 不只是 GPU 在花时间

小模型和短请求上，非 GPU 开销能占到三成：tokenize/detokenize、采样（尤其带 top-p 排序时）、Python 层的调度逻辑、请求序列化、以及 kernel launch 开销。

判断方法很简单：把 GPU 时间加总，和端到端时间比。差距大就说明瓶颈在 CPU 侧，这时优化 attention kernel 毫无意义。CUDA Graph 主要就是解决这类问题（第 17 章）。

## 10.6 怎么压测才不骗自己

四个常见的自欺：只测固定长度（真实负载长度分布极不均匀）；闭环压测（发完一个再发下一个，永远压不出排队问题，应该用开环按到达率发）；不做 warmup（首次运行包含编译和显存分配）；缓存污染（重复用同一个 prompt 压测，前缀缓存全命中，数字好看但不真实）。

**报告结果时必须同时给出：模型、精度、硬件、并行配置、输入输出长度分布、并发或到达率、以及 p50/p95/p99**。缺一项，数字就无法比较。

### 核心问答

**Q：为什么单请求的速度上限和 GPU 算力几乎无关？** 因为 Decode 是带宽受限的。每个 token 都要把全部权重读一遍，速度上限约等于显存带宽除以模型大小。算力再强也没用。

**Q：那为什么并发能提高总吞吐？** 一次权重读取被 batch 内所有请求共享。这是推理系统最重要的经济学：**batch 越大，每 token 的权重读取成本越低**。

**Q：用户抱怨"慢"，先看哪个指标？** 先问是"开始得慢"还是"吐字卡"。前者查 TTFT（排队还是 Prefill），后者查 ITL 分布（是不是被长 Prefill 打断）。

**Q：为什么必须分开统计输入和输出 token？** 它们走完全不同的路径、消耗完全不同的资源。输出 token 的单位成本通常比输入 token 高一个量级，计费和容量规划都要分开算。

# 第 11 章 KV Cache 内存管理：PagedAttention 与前缀缓存

> **开场问题**：显存监控显示还剩 20 GB，为什么再来一个请求就 OOM？

## 11.1 静态预分配为什么浪费

最直白的实现是：请求进来时，按它声明的 `max_tokens` 一次性分配一整块连续显存，形状是 `[层数, 2, KV 头数, 最大长度, head_dim]`。

两个问题立刻出现。**内部浪费**：用户声明 max_tokens=4096，实际生成了 80 个就结束了，剩下 98% 的空间白占了一路。**外部碎片**：不同请求申请和释放不同大小的连续块，久而久之显存被切得七零八落——总量还剩 20 GB，但找不出一块连续的 2 GB，于是新请求分配失败。这就是开场问题的答案。

PagedAttention 论文里测得的数字是：传统实现中 **60%–80% 的 KV 显存被浪费掉**。而 KV 显存直接决定并发数，也就直接决定吞吐和成本。

## 11.2 PagedAttention：借用虚拟内存的思路

操作系统早就解决过一模一样的问题——进程要连续的地址空间，物理内存却是碎的，办法是分页加页表。KV Cache 照搬这套。

**具体是这样做的**：把显存里的 KV 区域预先切成大量固定大小的物理块（block），每块存固定数量 token 的 KV，比如 16 个 token（vLLM 的默认值）。每个请求维护一张自己的 **block table**，记录"我逻辑上的第 0–15 个 token 在物理块 #732，第 16–31 个在物理块 #109，第 32–47 个在物理块 #58"。

于是：请求的 KV 在逻辑上是连续的，在物理上可以散落在显存任何地方；生成到第 17 个 token 时才去申请第二个块，**按需分配**；请求结束时把它占的块全部还给空闲池，立刻可被别人使用，**不产生外部碎片**。唯一剩下的浪费是最后一个块里没用满的部分，平均半个块，也就是 8 个 token——从"浪费 4000 个 token 的空间"降到"浪费 8 个"。

**为什么它叫 PagedAttention 而不只是分页分配器**：因为 attention kernel 必须跟着改。原来的 kernel 假设 K 和 V 在显存里是一整块连续张量，可以直接按步长遍历；现在它必须先读 block table，再按表里的物理块号去一块块地 gather。这是一个真实的 kernel 改写工作，也是这项技术的主要实现成本。

**它不减少 KV 的理论字节数**——模型该产生多少 KV 还是多少。它消灭的是预留浪费和碎片，让同样的显存能装下几倍的并发请求。这也正是它属于第二册而不是第一册的原因：模型一个字节都没改。

## 11.3 块大小怎么选

块太大（比如 128 token），最后一块的内部浪费回升，短请求尤其吃亏。块太小（比如 4 token），block table 变长、每次 attention 要 gather 的次数变多、访存更零碎，kernel 效率下降。

16 是一个在多数场景下平衡得不错的值，但它和 head_dim、KV 头数、具体 kernel 实现都有耦合。换模型或换硬件时值得重测。

## 11.4 共享与写时复制

分页带来一个额外好处：**两个请求如果前缀相同，它们的 block table 可以指向同一批物理块**。系统给每个块维护引用计数，只读时共享，某个请求要在共享块上写入新 token 时，先复制一份再写（copy-on-write）。

最直接的受益场景是并行采样：同一个 prompt 要生成 4 个不同的回答，prompt 那部分的 KV 只需要存一份。往下推，就是下一节的前缀缓存。

## 11.5 Prefix Caching：唯一不损精度还能省一个量级的优化

真实负载里重复内容多得惊人：所有请求共享同一段系统提示词；few-shot 例子每次都一样；多轮对话里第 N 轮的前缀就是第 N−1 轮的全文；RAG 反复引用同一批文档；Agent 每次工具调用都把完整轨迹重新带一遍。

既然这些前缀的 KV 已经算过，就别再算。实现上通常有两条路：**块级哈希**（对每个块覆盖的 token 序列做哈希，查表命中就直接复用那个物理块）和 **radix tree**（把所有活跃序列组织成前缀树，天然支持最长前缀匹配）。

收益的量级值得强调：一个十轮的 Agent 会话，如果每轮都全量重算 Prefill，总 Prefill 计算量是 O(n²)；有了前缀缓存，每轮只算新增的那部分，降到 O(n)。**在 Agent 和多轮场景下，这是所有优化里收益最大的一项，而且完全不损失精度**。很多团队把它排在量化和 kernel 优化之后，顺序搞反了。

代价在正确性上，缓存键必须包含所有会影响 KV 数值的东西：token 序列本身、模型版本、对话模板、tokenizer 版本、位置编码配置、LoRA 适配器、多模态输入的内容哈希。少一项就会串号——把 A 用户的上下文接到 B 用户的回答里，这是最严重的一类线上事故。跨租户共享还会泄漏"某个前缀是否存在"这一信息，安全边界必须显式设计。

## 11.6 装不下的时候：驱逐、换出还是重算

显存紧张时调度器要做取舍。**驱逐**（丢掉某个请求的 KV，之后需要时重新 Prefill）实现最简单；**换出**（把 KV 搬到主机内存，之后再搬回来）保住了计算成果，但要过 PCIe。

判据是一次带宽账：搬运 1 GB 的 KV 过 PCIe 需要多久，重新 Prefill 这段 prompt 又需要多久。**很多情况下重算比搬运更快**，因为 Prefill 是算力受限的，而 GPU 算力相对 PCIe 带宽极其充裕。所以"换出到 CPU"不是无脑更优的选项。

## 11.7 混合模型带来的新问题：两套状态

第一册第 12、13 章讲的混合架构（GDN 或 Mamba 层加少量标准注意力层）在推理侧制造了一个全新的工程问题。

线性层保存的不是 KV，而是一个**固定大小的循环状态**。它不随序列增长，看起来很美好——但它**不能按 token 分页**（它是历史的压缩混合物，没有"第 17 个 token 的状态"这种东西），**不能做前缀缓存的任意拼接**（两段前缀的状态无法合并），驱逐之后也**不能只重算一部分**。

于是引擎要同时维护两套内存管理：标准注意力层的分页 KV（可分页、可共享、可部分驱逐）和线性层的固定状态（整体分配、整体迁移、要么全有要么全无）。抢占、前缀缓存命中、请求迁移这些操作在两套状态上的语义都不一样。这是 2025 年之后才浮现的问题，前几年的推理系统设计里完全没有。

### 核心问答

**Q：PagedAttention 到底省了什么？** 省的是预留浪费和外部碎片，不是 KV 本身的大小。模型该产生多少 KV 还是多少，但同样的显存能装下几倍的并发。

**Q：block table 里存的是什么？** 一个数组，第 i 项记录"本请求逻辑上第 i 块 token 的 KV 存在哪个物理块里"。attention kernel 每次都要先查它。

**Q：为什么 attention kernel 必须重写？** 因为 KV 不再是连续张量，kernel 要按 block table 做间接寻址和分块 gather。这是分页方案的主要实现成本。

**Q：前缀缓存为什么该优先做？** 它直接消掉计算，不是把计算搬来搬去，而且完全无损。在多轮和 Agent 负载下收益可达一个数量级，远超 kernel 层面的百分之几十。

**Q：线性注意力的状态能不能也分页？** 不能按 token 切分。它是压缩后的历史，只能作为整体管理。混合模型需要引擎里有两套内存语义。

# 第 12 章 在线调度：连续批处理与 Chunked Prefill

> **开场问题**：一个 4000 token 的长 prompt 进来，为什么正在流式输出的其他用户会集体卡一下？

## 12.1 静态批处理的三种浪费

传统批处理是：凑够 N 个请求，一起跑完，全部返回，再凑下一批。三个问题都很致命。

**等齐才开始**：先到的请求要干等后来的。**等最慢的才结束**：batch 里有个请求要生成 3000 token，其余 63 个生成 50 token 就完了，但它们的显存和 batch 槽位被占着直到最后。**中途不能加人**：新请求只能等下一批。

于是 GPU 大部分时间在为已经完成的序列做无意义的 padding 计算。

## 12.2 连续批处理：以迭代为单位重组

关键转变是把调度粒度从"一批请求"降到"一次前向"。

每一步 Decode 前向本质上是：batch 里每个序列各贡献一个 token，一起过一遍模型，各自拿到自己的下一个 token。既然如此，**这个 batch 的成员完全可以每一步都不同**。于是引擎的主循环变成：每次迭代开始前，把已完成的序列移出，从等待队列里挑新的请求加入，然后执行这一步前向。

效果是 GPU 永远满载，且新请求平均只需等待一步（几十毫秒）就能加入，而不是等一整批结束。这是现代推理引擎与上一代最本质的区别，其他优化都建立在它之上。

实现上的关键是变长支持：batch 里各序列长度不同，不能用规整的四维张量，而要用 ragged 布局（把所有序列的 token 首尾相连，另外用一个数组记录每条序列的起止位置），配合支持变长的 attention kernel。

## 12.3 分块 Prefill：不让长 prompt 霸占 GPU

连续批处理解决了 Decode 之间的调度，但 Prefill 仍然是个大块头。一个 8000 token 的 Prefill 要占 GPU 几百毫秒，这期间整个 batch 的 Decode 全部暂停——所有用户同时卡一下，这就是开场问题。

分块 Prefill 的做法是：把长 prompt 切成若干块（比如每块 512 token），**每次迭代只处理一块，穿插在正常的 Decode 迭代之间**。因为是因果注意力，后面的块本来就要看到前面块的 KV，分块处理在数学上完全等价，不需要任何近似。

代价是这个长请求自己的 TTFT 变长了（它要等好几轮才 Prefill 完），换来的是其他所有请求的 ITL 保持平稳。**这是一个明确的公平性取舍**：牺牲一个长请求，保护一群短请求。

## 12.4 Token 预算：吞吐和延迟之间那个旋钮

实现上，调度器每轮给自己设一个 token 预算，比如"这一步最多处理 8192 个 token"。先把所有活跃的 Decode 请求装进去（每个占 1 个 token），剩余预算用来装 Prefill 的块。

预算调大：每步干的活多，吞吐高，但单步耗时长，ITL 变差。预算调小：吐字更平滑，但吞吐下降。**这是在线服务最重要的一个调参**，应该由 SLO 反推，而不是取框架默认值。

## 12.5 排队论只需要知道这一点

系统利用率接近 100% 时，吞吐不再增长，而排队延迟会急剧上升——这是排队论的基本结论，不是工程实现问题。实践含义很直接：**不要把推理集群压到 95% 利用率**。

正确做法是画出延迟—吞吐曲线，找到 p99 开始陡升的那个膝点，把容量规划在膝点之前留出余量。流量有抖动，压在膝点上意味着任何一次小高峰都会变成一次 SLO 事故。

## 12.6 抢占与公平

显存不够时要踢人：踢最新来的（保护已经等了很久的）、踢最长的（释放最多显存）、还是踢优先级最低的？被踢的请求是丢弃 KV 重算，还是换出到主机内存？

还要防饥饿：如果总是优先短请求，长请求可能永远排不上；如果按 FCFS，一个超长请求会把后面所有人堵住。生产系统通常按 SLO 分级加上老化机制（等待越久优先级越高）来平衡。

### 核心问答

**Q：连续批处理和动态 batch 的区别？** 动态 batch 只是在开始前灵活凑批，一旦开跑成员就固定了；连续批处理在**每一步生成**都可以加人和踢人。

**Q：分块 Prefill 会影响输出结果吗？** 不会。因果注意力下分块计算和一次算完在数学上完全等价，纯粹是调度层面的切分。

**Q：调度器为什么必须知道剩余 KV 块数？** 因为接纳一个请求意味着承诺给它持续供应 KV 块。接纳太多，中途必然要抢占，反而造成抖动和重算。

**Q：为什么不能把 GPU 压满？** 排队系统在接近满载时延迟指数上升。追求 95% 利用率的代价是 p99 失控，最终 goodput 反而更低。

# 第 13 章 多 GPU 推理与 Prefill/Decode 分离

> **开场问题**：模型能装进 8 卡，但 TP=8 的吐字速度并没有比 TP=4 快多少，问题出在哪？

## 13.1 先问为什么要多卡

两个完全不同的动机，导出的配置完全不同。

**装不下**：模型权重加上 KV 超过单卡显存，必须切。这时目标是可行性，配置以"刚好装下并留足 KV 空间"为准。

**嫌太慢**：模型装得下，但单请求的 TPOT 不达标。Decode 是带宽受限的，把权重摊到 N 张卡上，每张卡只需读 1/N 的权重，理论上 TPOT 可以降到 1/N。这时目标是延迟。

第三种情况最常见也最容易搞错：**只想要吞吐**。这时通常应该部署多个独立副本而不是加大 TP——多副本的路由简单、故障隔离好、没有跨卡通信开销。

## 13.2 张量并行的收益为什么会饱和

TP 在推理里的通信模式和训练一样：每个 Transformer Block 两次 AllReduce。区别在于 Decode 阶段每次通信的数据量很小（只有 batch 个 token 的 hidden），**这时通信的瓶颈不是带宽而是延迟**——每次 AllReduce 的固定开销几乎不随数据量变化。

于是 TP 从 4 加到 8：权重读取减半（好），但通信次数不变、每次的固定延迟不变，而每张卡的计算量已经小到无法摊薄这个开销。开场那个现象就是这么来的。TP 在 Decode 上有明确的收益拐点，且强烈依赖卡间互联质量——NVLink 域内尚可，跨 PCIe 或跨机基本没有收益。

## 13.3 流水线并行在推理里的定位

PP 在推理里主要用于"跨机装下超大模型"，而不是提速。单请求在 PP 下是严格串行经过各 stage 的，延迟不降反升；只有当并发足够多、能把流水线填满时，吞吐才上得去。

它的优点是通信量极小（只在 stage 边界传激活），适合互联较差的环境。缺点是 KV 分散在不同 stage、调度复杂、单请求延迟高。在线交互服务里通常是最后选择。

## 13.4 专家并行与 MoE 推理的真实瓶颈

MoE 推理必须把专家分散到多卡（第一册 8.6 节讲过，显存要按**总参数**算，不是激活参数）。这带来两个 Decode 阶段特有的问题。

**GEMM 太小**：Decode 每步只有 batch 个 token，经路由分散到几十上百个专家上，每个专家可能只分到几个 token。矩阵乘退化成极瘦的形状，GPU 效率极低。这就是为什么 MoE 推理往往达不到理论上"激活参数少所以快"的预期。

**AllToAll 在关键路径上**：每层两次，且 Decode 每步都要来一遍。加上热专家（某些专家被选中的概率显著偏高）造成的负载不均，部分卡会成为每一步的瓶颈。工程上的对策包括冗余部署热专家、专家放置优化，以及让注意力部分走数据并行而专家部分走 EP 的组合布局。

## 13.5 多副本服务：经常是正确答案

模型能装进单卡（或单机）时，横向复制通常优于纵向切分：请求级路由、故障只影响一个副本、没有跨卡通信、扩缩容简单。

路由器需要做的判断比"轮询"复杂一点：要看各副本的队列长度、KV 剩余量，以及**前缀缓存命中情况**——把同一个会话的后续请求送到已经缓存了它前缀的那个副本上，收益往往比负载均衡本身还大。

## 13.6 Prefill / Decode 分离

10.4 节的矛盾是根本性的：两个阶段的资源特性相反，放一起必然互相干扰。PD 分离把它们放到不同的 GPU 池，各自用最适合的批策略和并行配置，还能按实际负载独立扩缩容。

核心难点是 **KV 传输**：Prefill 节点算出的整段 KV 要送到 Decode 节点。数据量不小（8B 模型、4K prompt 约 600 MB），需要 RDMA 并做成逐层流式传输，让传输和后续层的计算重叠，否则传输时间会把省下的收益吃回去。

**什么时候不该做 PD 分离**：输出很短（Decode 占比小，收益有限）、prompt 很短（Prefill 本来就不碍事）、模型较小、互联带宽不足、或者只有单机部署。这些情况下分块 Prefill 更简单也更有效。它是超大规模在线服务的方案，中小规模照搬大厂架构只会徒增复杂度。

### 核心问答

**Q：模型装得下单卡，还要不要开 TP？** 先问目标。要吞吐，用多副本；要低延迟，才考虑 TP，且要实测收益拐点。

**Q：为什么 TP 在 Decode 上收益会饱和？** Decode 每步通信量很小，瓶颈是通信的固定延迟而非带宽。卡数翻倍减不了通信次数，计算量却已经小到摊不薄开销。

**Q：MoE 推理为什么没有想象中快？** Decode 阶段每个专家分到的 token 太少，GEMM 形状差；加上每层两次 AllToAll 和热专家导致的负载不均。激活参数少只在算力上占便宜，访存和通信都不省。

**Q：训练和推理的并行配置必须一致吗？** 不必。权重可以重分片，但要有可靠的转换和验证流程，尤其 MoE 的专家布局变化时。

# 第 14 章 投机解码的系统实现

> **开场问题**：论文说加速 2–3 倍，为什么线上一开并发收益就没了，甚至更慢？

## 14.1 先算清楚这笔账

第一册第 14 章讲了原理：草稿猜 k 个，大模型一次前向并行验证，接受前面连续对的部分。系统视角要把它写成一个能判断"开了会不会更慢"的式子。

一轮投机的成本是：草稿生成 k 个 token 的开销，加上一次验证前向的开销（比普通 Decode 前向略贵，因为要同时算 k+1 个位置）。收益是这一轮产出的 token 数，等于**期望接受长度**。

于是三个量决定一切：期望接受长度（越高越好）、草稿成本占比（越低越好）、验证的额外开销（k 越大越贵）。任何一项失衡，加速比就掉到 1 以下。

## 14.2 草稿从哪来，各自的系统代价

**独立小模型**：用同系列的小号模型。接受率取决于两个模型的分布接近程度，但它要占显存、占算力，还要自己的 KV 管理和调度，是最重的方案。

**自投机头（Medusa / Eagle / MTP）**：在主模型上挂额外的头。不需要第二套权重和 KV。Medusa 各头独立预测不同位置，接受率一般；Eagle 在特征层面做自回归，接受率明显更高；MTP 是预训练阶段就带的（第一册 14.4 节），质量最好且零额外训练成本。

**无模型方法（n-gram / prompt lookup）**：直接从上下文里找重复片段当草稿。零成本，在代码补全、文档改写、RAG 这类重复度高的场景意外地有效，值得作为默认兜底。

## 14.3 树状候选与 KV 回滚

多个草稿头会产生分叉：位置 +1 有 2 个候选，各自的 +2 又有 2 个……把它们组织成一棵树，用一个特制的 attention mask 让每个候选只能看到自己那条路径上的祖先，就能**在一次前向里同时验证多条路径**，最后保留被接受的最长前缀。

树越宽接受率越高，但无效计算也越多——这又是一个要按负载调的参数。

KV 管理上，被拒绝的分支写进去的 KV 必须回收，被接受的前缀要提交为主序列的一部分。分页 KV 在这里帮了大忙：分支共享前缀块、拒绝时按块回收，都是现成的能力。

## 14.4 和连续批处理的冲突

这是开场问题的答案。投机解码的前提是"Decode 阶段有富余算力"，而这个前提在**大 batch 下不成立**——连续批处理已经把 batch 堆起来，算术强度上去了，工作点接近算力受限，此时再塞投机验证的额外计算，就是纯粹的负担。

还有一个二阶问题：batch 内各请求每轮接受的 token 数不同，序列进度参差不齐，调度器按请求数凑批的假设被打破，需要按预计验证成本来组批。

所以生产系统的正确姿态是**动态开关**：低并发时开，并根据近期接受率自适应调整草稿长度；并发上来后自动关掉。把它当成永远打开的开关，高峰期会反噬。

## 14.5 它买的是延迟，不是吞吐

这条结论值得单独强调：投机解码用算力换延迟。在 GPU 有富余算力时（低并发、交互式、长思维链推理），它能显著改善 TPOT；在追求最大吞吐的离线批处理里，它几乎没有价值，甚至有害。

第一册尾声提到的长思维链模型让它的价值上升了——生成几万 token 的思考过程，TPOT 的改善会被放大很多倍。

### 核心问答

**Q：投机解码什么时候反而更慢？** 并发高（算力已经不富余）、接受率低（草稿不准）、草稿成本高（小模型太大）、或者验证 kernel 实现不好。

**Q：为什么代码补全特别适合？** 重复片段多，连 n-gram 这种零成本草稿都有很高的接受率。

**Q：它会改变输出质量吗？** 不会。接受—重采样规则保证输出分布与逐 token 生成完全一致。但要注意：这个保证依赖实现正确，上线前应该做分布一致性验证。

**Q：应该报告什么指标？** 只报"加速 2 倍"没有意义。要给出：接受长度、不同并发下的 TPOT 和吞吐变化、额外显存占用，以及在什么并发区间应该关闭。

# 专题 后训练系统：Rollout、权重同步与策略版本

> SFT、DPO、RLVR 的算法属于第三册，但强化学习需要的运行系统横跨训练和推理两侧，必须在第二册把接口讲清，否则读者会以为第三册的 RL 是纯算法问题。

## T.1 为什么 RL 训练需要一个完整的推理引擎

在线强化学习的每一轮是：用当前策略模型批量生成大量 rollout（可能是几万条、每条几千 token）→ 用奖励模型或验证器打分 → 把样本送给训练 worker 更新权重 → 同步新权重回生成端。

**生成阶段通常占整个 wall-clock 的 60%–80%**。这意味着 RL 训练的效率首先是推理效率问题，用训练框架里那个朴素的 `generate()` 会慢一个数量级。现代 RL 框架的做法是直接把 vLLM/SGLang 这类引擎嵌进训练流程。

长思维链的兴起让这件事更极端：一条 rollout 可能生成三万个 token，生成侧的成本进一步压倒训练侧。

## T.2 Colocate 还是分离

**Colocate**：生成和训练轮流使用同一批 GPU。省去跨集群权重传输，硬件利用率高，但要在两种模式间反复切换显存布局（推理引擎的 KV 池和训练的优化器状态不能同时占满显存），工程上很讲究。

**分离**：生成池和训练池各自常驻。两边都能持续满载、可独立扩缩容，但权重要跨集群同步，而且必然引入策略滞后。

选择取决于生成和训练的耗时比例。比例悬殊且稳定时分离更好；比例接近或波动大时 colocate 更省。

## T.3 权重同步是主要工程难点

训练侧更新完参数，要尽快让生成侧用上。三个现实问题：

**传输量大**。几百 GB 的权重，走文件系统会慢到不可接受，成熟做法是走 RDMA 直接做 GPU 到 GPU 的传输。

**布局不同**。训练侧可能是 FSDP 分片加 TP=8，生成侧可能是 TP=4，同步时要在线重分片。

**频率是个权衡**。同步越频繁，生成用的策略越新（更符合 on-policy 假设），但停顿和传输开销越大。

## T.4 异步与策略滞后

为了不让两边互相等待，工业做法通常是异步：生成端一直在产出，训练端一直在消费，两者用的策略版本相差若干步。

**系统侧的责任是让这件事可追踪**：每条样本必须标记它是由哪个策略版本生成的。至于允许滞后多少步、旧样本要不要重要性加权或直接丢弃，那是第三册的算法问题。系统不做这个决定，但必须提供做决定所需的信息。

## T.5 分工

本册回答：rollout 怎么高吞吐生成、资源怎么摆、权重怎么同步、版本怎么追踪。第三册回答：奖励怎么定义、优势怎么估计、策略怎么更新、多旧的样本还能用。

两者混写会让算法假设和系统实现都说不清楚——这也是很多 RL 复现失败的原因：照搬了算法，却没有对齐系统层面的同步语义。

### 核心问答

**Q：为什么不用训练框架自带的生成？** 它为大 batch 前反向优化，没有连续批处理、分页 KV 和变长调度，生成吞吐可能差一个数量级。而生成占 RL 的大头。

**Q：Colocate 一定更省吗？** 不一定。切换有开销，且当生成和训练的耗时比例失衡时，总有一边在闲置。

**Q：权重必须每步同步吗？** 不必。这是通信成本和策略新鲜度的权衡，由算法的容忍度决定，系统负责把两种模式都支持好。

**Q：为什么样本一定要标策略版本？** 否则无法判断数据有多旧，异步训练的正确性就无从谈起。这是系统必须提供的最小保证。
